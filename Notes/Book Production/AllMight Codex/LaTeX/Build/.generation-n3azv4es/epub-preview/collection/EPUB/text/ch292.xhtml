Teach the complete journey, then break one assumption at a time

Start with the physical panel and end with an engine boundary:

  1. Interpret imported corner tuples as points in a declared frame and unit system.
  2. Subtract points to obtain edge vectors; compare numerical resolution with the panel scale.
  3. Check usable area, then derive the face normal and a surface frame.
  4. Solve the sensor’s barycentric coordinates and check that its plane residual is acceptable.
  5. Interpolate the temperature and texture coordinates; distinguish linear constraints from unit-length promises.
  6. Transform the panel points, tangents, and normals with their appropriate laws.
  7. Compute reflected or transmitted light with explicit direction conventions.
  8. Query collision shapes through a common coordinate frame and support contract.
  9. Project visible points through homogeneous clip coordinates, then divide and map to the viewport.
  10. Encode the destination buffer according to its measured layout, not the CPU class’s name.

Now ask what happens if one input changes. Mirror the panel: which orientation signs change while distances stay the same? Collapse two corners: which quantities remain meaningful and which become undefined? Move the workcell to a huge coordinate: did information disappear during storage or arithmetic? Change the basis to a slanted one: which formulas need its Gram matrix? Reverse incident-ray conventions: where must the signs change?

These questions are better than asking a learner to repeat a formula. They require the mechanism and its domain to remain connected.

The mathematical table needs an explicit storage agreement

A matrix’s mathematical shape says how many entries it has. It does not specify their addresses. For an R -by- C matrix, compact row-major storage puts each row contiguously, using element index r C + c . Compact column-major storage puts each column contiguously, using index c R + r . These are memory mappings. Our column-vector mathematical convention can use either storage arrangement as long as the accessor and boundary agreement match.

A compact two-by-three matrix with rows ( a , b , c ) and ( d , e , f ) has row-major sequence a b c d e f and column-major sequence a d b e c f. Neither sequence changes the equation y = M x . A transpose changes the logical relation between indices, M r c T = M c r ; reinterpreting bytes without the matching access contract can accidentally produce a transpose, but storage conversion and mathematical transposition are not definitions of one another.

Own actual arrays rather than inventing array bounds between members

For fixed-size matrices, an actual array provides the element sequence that indexing requires. A pointer to one separately declared scalar member does not become a pointer to a four-element array merely because nearby members happen to be adjacent in one ABI. The source’s illustrative (&m00)[r*2+c] crosses that language boundary; use the source’s array-based alternative instead.

#include <array>
#include <cstddef>
#include <limits>
#include <stdexcept>

template<std::size_t Rows, std::size_t Cols>
struct Matrix {
    static_assert(Rows > 0 && Cols > 0);
    static_assert(Rows <= std::numeric_limits<std::size_t>::max() / Cols);
    std::array<double, Rows * Cols> data{}; // zero is the default contract

    double& operator()(std::size_t r, std::size_t c) {
        if (r >= Rows || c >= Cols)
            throw std::out_of_range("matrix index");
        return data[r * Cols + c];
    }
    const double& operator()(std::size_t r, std::size_t c) const {
        if (r >= Rows || c >= Cols)
            throw std::out_of_range("matrix index");
        return data[r * Cols + c];
    }
    static Matrix identity() requires (Rows == Cols) {
        Matrix result;
        for (std::size_t i = 0; i < Rows; ++i)
            result(i, i) = 1;
        return result;
    }
};

This small teaching type uses checked access and a stated zero default. A tuned internal loop may use an unchecked accessor with a proven precondition, but should not claim it is bounds-checked. The square-only factory prevents an accidental request for a rectangular identity under this API. Mat2, Mat3 and Mat4 can be aliases or dedicated wrappers with role-specific operations. Matrix multiplication can encode compatible inner dimensions in templates, while runtime matrices must check them at the boundary.

A fixed matrix owns its entries inline. Copying it copies numerical values; moving it usually does not avoid that entry transfer because there is no separate buffer to adopt. “Inline” does not require a stack location: a matrix can be a member of a heap object, stored in an array, or optimized into registers. Similarly, “typically 64 bytes for sixteen 32-bit floats” is a measured/assumed representation statement, not a portable theorem about every C++ float or every padded wrapper.

A Mat2 is useful when the operation acts on two-dimensional vectors: its four entries may encode planar rotation, shear or scaling. A Mat3 naturally acts on ordinary three-dimensional directions and can hold a basis, a general linear deformation, or an inverse-transpose normal map. A Mat4 acts on four-component homogeneous representatives and can encode three-dimensional affine and projective maps. These are roles selected by an API; the same mathematical two-by-two table could instead describe two measurements of two unrelated signals. Matrix dimensions alone do not establish a geometric meaning.

That distinction also explains initialization. A zero matrix annihilates every input; identity preserves it. Neither is an interchangeable harmless default. Identity can make sense for an unmodified transform, while zero can make sense for an accumulator. An explicit identity() factory keeps the intent visible. Before multiplying, initialize the result to zero when accumulating contributions; starting at identity would add an unintended diagonal. Before publishing a transform, establish the exact intended state rather than hoping a default happens to match it.

Alignment is a starting-address requirement, while padding changes spacing or total size. A three-by-three matrix may use nine scalars compactly, or three padded four-scalar rows for a chosen SIMD/backend contract. The latter consumes more storage but may simplify specific loads. Neither choice automatically matches a shader buffer’s layout. Verify stride, offsets, component format and enabled backend rules at the upload boundary.

Runtime views borrow a layout as well as a lifetime

A stride is the physical distance between logical neighbors along a dimension. For a general two-dimensional view, the index can be written r s r + c s c , where s r is row stride and s c is column stride, both in elements. A compact row-major matrix has s r = C and s c = 1 . A padded row-major matrix can have s r > C . A transposed view can exchange the logical dimensions and the two strides while keeping the same underlying entries.

For Figure M7, indexing the second row with the view’s width three would read j k l instead of l m n. The shape tells us which logical indices exist; the stride tells us where they live. Both are necessary metadata.

A view is a non-owning description of those entries. It should retain a backing-span/bounds contract, dimensions and strides rather than a bare pointer with unexplained capacity. For a nonempty row-major view with unit column stride and nonnegative row stride, the last accessed element has offset ( R − 1 ) s r + ( C − 1 ) , so the backing region needs at least ( R − 1 ) s r + C elements. Check that multiplication and addition do not overflow before using that formula. Decide separately how empty views are represented; do not evaluate R − 1 when R = 0 .

Dimension checks also belong before allocation. A request for rows * cols elements can wrap an unsigned size calculation before the container sees it, turning an enormous requested shape into a small allocation. Validate multiplication against the chosen container’s limits first. A row stride shorter than the logical width may describe intentional overlapping rows in a very general view, but it violates an ordinary non-overlapping row-major contract. Choose which layouts the type accepts and validate that promise at construction, rather than hiding an accidental overlap in a permissive accessor.

Bounds on the descriptor do not extend the owner’s lifetime. Destroying, reallocating or otherwise invalidating the owner’s buffer can dangle the view. Moving an owner or swapping buffers also needs the container’s actual guarantees; a pointer does not follow the meaning of a variable name. Mutation through overlapping views is another contract: C = A * B needs either an output independent of the inputs or a safe temporary when C aliases them. Arithmetic can be correct while in-place overwrite destroys values still needed by later iterations.

SIMD and loop order change the execution schedule, not the matrix question

SIMD means single instruction, multiple data. A four-lane operation may multiply four corresponding scalar pairs at once. For a row dot vector, lane products still need to be added into one result. That addition is a horizontal reduction, because several lanes contribute to one scalar. A lane-wise result and a reduction have different data movement and rounding behavior.

For matrix multiplication, another strategy computes a whole output row from scaled rows of the right operand:

C i , : = A i 0 B 0 , : + A i 1 B 1 , : + A i 2 B 2 , : + A i 3 B 3 , :

for four-by-four matrices. Each A i k can be broadcast into all lanes, then multiplied by one four-lane row of B . That describes a computational organization; it does not change our use of column-vector mathematics. Fused multiply-add may reduce instruction count and round a product-plus-sum once, while shuffles, horizontal reductions and register spills can erase a benefit. Benchmark the actual workload, compiler flags and target rather than promoting “SIMD-friendly” into an unmeasured speed claim.

Classical scalar multiplication uses C i j = ∑ k A i k B k j . For row-major arrays, an i-j-k loop walks one row of A but a column of B in its inner loop. The B accesses jump by a row stride. Reorder to i-k-j and the inner loop walks a row of B and a row of C , while reusing one A i k across them:

// C is initially zero and does not alias A or B.
for (std::size_t i = 0; i < rows; ++i)
    for (std::size_t k = 0; k < inner; ++k) {
        const double aik = A(i, k);
        for (std::size_t j = 0; j < cols; ++j)
            C(i, j) += aik * B(k, j);
    }

Both schedules perform the same classical order of growth, Θ ( n 3 ) for square matrices. Their cache traffic can differ substantially. A cache line transfers a block of neighboring bytes; an illustrative 64-byte line contains sixteen 32-bit floats. Walking adjacent entries can use those neighbors before eviction. Walking widely separated entries may bring in many unused neighbors. Exact cache-line size, alignment effects and reuse depend on the machine.

For a tiny Mat4, the working set is already small, so unrolling, instruction scheduling and register use may dominate. For large arrays, blocking or tiling works on smaller submatrices so loaded blocks can serve many arithmetic operations before eviction. Arithmetic intensity is the amount of arithmetic performed per byte transferred at the memory level being discussed. Increasing reuse can increase that ratio without changing the mathematical operation or the classical asymptotic work count.

Floating-point execution still matters. Different reduction trees, reassociation or FMA contraction can change final bits even when the real-number identities agree. Reproducibility requirements therefore constrain the allowed execution schedule and compiler settings. A fast result needs an accuracy contract and a measurement protocol, just as a correct-looking transformation needs declared coordinate endpoints.

The practical reconstruction test is now concrete: read a frame’s columns and origin; derive which inverse changes coordinates; trace one valid point through model, view, clip and NDC; explain why a normal uses the inverse transpose; locate a subview’s entries using its actual strides; and predict which data a multiplication loop reuses. Each answer joins geometry to the memory and lifetime model rather than treating matrix code as sixteen unexplained numbers.

A complete scalar laboratory makes the contracts observable

The following C++20 program is a standalone teaching laboratory. Copy its whole fence into one source file. It uses actual array storage and checked logical indices; encodes rectangular product dimensions; performs pivoted Gauss–Jordan inversion with an explicit scale-relative rejection policy; and implements Hamilton orientation, stable matrix conversion, shortest-path SLERP, homogeneous point transformation and rigid dual-quaternion composition. The tests exercise both valid relationships and defined rejection paths.

The inverse routine is deliberately small: its pivot threshold is a laboratory policy, not a certified condition estimator. It rejects nonfinite inputs and finite matrices whose row sums overflow; a production solver would need more careful scaling, factorization and error estimates. The axis-angle constructor accepts finite nonzero axes and normalizes them with max-component scaling, including tiny axes whose direct norm could underflow. Quaternion rotation and matrix conversion require the documented finite-unit/proper-rotation preconditions. The SLERP API here accepts only interpolation fractions in [0,1]. The homogeneous helper checks an exactly zero or nonfinite divisor; application-specific clipping and near-plane tolerances remain separate.

The program does not implement an engine scheduler, GPU upload ABI, general polar/SVD decomposition, dynamic strided-view class or animation system. Those have been explained as contracts above. Its purpose is to give a small executable witness for the mathematics rather than inherit the source excerpts’ production-ready label.

template <std::size_t N> double normInf(const Mat<N, N> &a) {
  double m = 0;
  for (std::size_t i = 0; i < N; ++i) {
    double s = 0;
    for (std::size_t j = 0; j < N; ++j)
      s += std::abs(a(i, j));
    m = std::max(m, s);
  }
  return m;
}
template <std::size_t N> std::optional<Mat<N, N>> inverse(Mat<N, N> a) {
  double m = normInf(a);
  if (!(m > 0) || !std::isfinite(m))
    return std::nullopt;
  for (double x : a.a)
    if (!std::isfinite(x))
      return std::nullopt;
  // Normalize global scale; threshold is a laboratory rejection policy,
  // not a certified condition-number estimator.
  for (double &x : a.a)
    x /= m;
  auto b = identity<N>();
  for (std::size_t k = 0; k < N; ++k) {
    std::size_t p = k;
    for (std::size_t i = k + 1; i < N; ++i)
      if (std::abs(a(i, k)) > std::abs(a(p, k)))
        p = i;
    if (std::abs(a(p, k)) <= 64 * std::numeric_limits<double>::epsilon())
      return std::nullopt;
    for (std::size_t j = 0; j < N; ++j) {
      std::swap(a(k, j), a(p, j));
      std::swap(b(k, j), b(p, j));
    }
    const double pivot = a(k, k);
    for (std::size_t j = 0; j < N; ++j) {
      a(k, j) /= pivot;
      b(k, j) /= pivot;
    }
    for (std::size_t i = 0; i < N; ++i)
      if (i != k) {
        double f = a(i, k);
        for (std::size_t j = 0; j < N; ++j) {
          a(i, j) -= f * a(k, j);
          b(i, j) -= f * b(k, j);
        }
      }
  }
  for (double &x : b.a) {
    x /= m;
    if (!std::isfinite(x))
      return std::nullopt;
  }
  return b;
}

struct Q {
  double w, x, y, z;
};
Q operator+(Q a, Q b) { return {a.w + b.w, a.x + b.x, a.y + b.y, a.z + b.z}; }
Q operator*(Q a, double s) { return {a.w * s, a.x * s, a.y * s, a.z * s}; }

Q operator*(Q a, Q b) {
  V av{a.x, a.y, a.z}, bv{b.x, b.y, b.z};
  V c = add(add(scale(bv, a.w), scale(av, b.w)), cross(av, bv));
  return {a.w * b.w - dot(av, bv), c[0], c[1], c[2]};
}
std::optional<Q> unit(Q q) {
  const double m =
      std::max({std::abs(q.w), std::abs(q.x), std::abs(q.y), std::abs(q.z)});
  if (!(m > 0) || !std::isfinite(m))
    return std::nullopt;
  q = {q.w / m, q.x / m, q.y / m, q.z / m};
  const double n = std::sqrt(qdot(q, q));
  if (!std::isfinite(n))
    return std::nullopt;
  return q * (1.0 / n);
}
Q axis(V a, double theta) {
  if (!std::isfinite(theta))
    throw std::invalid_argument("nonfinite angle");
  const double m = std::max({std::abs(a[0]), std::abs(a[1]), std::abs(a[2])});
  if (!(m > 0) || !std::isfinite(m))
    throw std::invalid_argument("invalid axis");
  a = {a[0] / m, a[1] / m, a[2] / m};
  const double n = std::hypot(a[0], a[1], a[2]);
  if (!std::isfinite(n))
    throw std::invalid_argument("invalid axis");
  a = scale(a, std::sin(theta / 2) / n);
  return {std::cos(theta / 2), a[0], a[1], a[2]};
}
// Precondition for rotate and rotation: finite unit quaternion.
V rotate(Q q, V v) {
  V u{q.x, q.y, q.z};
  V t = scale(cross(u, v), 2);
  return add(v, add(scale(t, q.w), cross(u, t)));
}

// Input contract: finite proper orthogonal matrix, independently checked
// by caller. This routine is not a matrix-to-rotation repair algorithm.
Q fromRotation(const Mat<3, 3> &m) {
  Q q{};
  const double tr = m(0, 0) + m(1, 1) + m(2, 2);
  if (tr > 0) {
    double s = 2 * std::sqrt(1 + tr);
    q = {s / 4, (m(2, 1) - m(1, 2)) / s, (m(0, 2) - m(2, 0)) / s,
         (m(1, 0) - m(0, 1)) / s};
  } else if (m(0, 0) > m(1, 1) && m(0, 0) > m(2, 2)) {
    double s = 2 * std::sqrt(1 + m(0, 0) - m(1, 1) - m(2, 2));
    q = {(m(2, 1) - m(1, 2)) / s, s / 4, (m(0, 1) + m(1, 0)) / s,
         (m(0, 2) + m(2, 0)) / s};
  } else if (m(1, 1) > m(2, 2)) {
    double s = 2 * std::sqrt(1 + m(1, 1) - m(0, 0) - m(2, 2));
    q = {(m(0, 2) - m(2, 0)) / s, (m(0, 1) + m(1, 0)) / s, s / 4,
         (m(1, 2) + m(2, 1)) / s};
  } else {
    double s = 2 * std::sqrt(1 + m(2, 2) - m(0, 0) - m(1, 1));
    q = {(m(1, 0) - m(0, 1)) / s, (m(0, 2) + m(2, 0)) / s,
         (m(1, 2) + m(2, 1)) / s, s / 4};
  }
  return *unit(q);
}
Q slerp(Q a, Q b, double t) {
  auto na = unit(a), nb = unit(b);
  if (!na || !nb || !std::isfinite(t) || t < 0 || t > 1)
    throw std::invalid_argument("invalid interpolation");
  a = *na;
  b = *nb;
  double d = qdot(a, b);
  if (d < 0) {
    b = b * (-1);
    d = -d;
  }
  d = std::clamp(d, -1.0, 1.0);
  if (d > .9995)
    return *unit(a * (1 - t) + b * t);
  double th = std::acos(d);
  return *unit(a * (std::sin((1 - t) * th) / std::sin(th)) +
               b * (std::sin(t * th) / std::sin(th)));
}
Mat<4, 4> affine(const Mat<3, 3> &l, V t) {
  auto a = identity<4>();
  for (int i = 0; i < 3; ++i) {
    for (int j = 0; j < 3; ++j)
      a(i, j) = l(i, j);
    a(i, 3) = t[i];
  }
  return a;
}
V point(const Mat<4, 4> &a, V p) {
  V r{};
  double w = a(3, 3);
  for (int j = 0; j < 3; ++j)
    w += a(3, j) * p[j];
  if (!std::isfinite(w) || w == 0)
    throw std::domain_error("invalid homogeneous divide");
  for (int i = 0; i < 3; ++i) {
    r[i] = a(i, 3);
    for (int j = 0; j < 3; ++j)
      r[i] += a(i, j) * p[j];
    r[i] /= w;
  }
  return r;
}

Implementation kernels and shape reasoning

A practical result need not materialize a dense diagonal Σ . Store singular values as a vector and store U and V T in documented full, thin, or compact shapes. For compact rank r , the contract is typically U : m × r , σ : r , and V T : r × n . Then applying the factorized matrix to x ∈ R n can be done as three clear operations:

z = Vt * x          // r coefficients; Vt is r by n
for i in 0 .. r-1:
    z[i] *= sigma[i]
y = U * z           // m outputs; U is m by r

The result is y ∈ R m . It costs O ( r n + r m ) arithmetic instead of multiplying a reconstructed dense m × n matrix by x . When the factors are retained for repeated transforms, this can save storage and work. Validate dimensions at the boundary: input length must equal n , output length is m , and the shared rank dimension must agree between U , σ , and V T .

A pseudoinverse application should also avoid constructing A + . For b ∈ R m , compute c = U T b (length r ), divide c i by every exact positive σ i for the mathematical A + , then return x = V c . Under a deliberate numerical cutoff, divide only when σ i > τ and set the coefficient to zero otherwise; expose the threshold and the fact that this computes A τ + . The output has length n . The reduction must distinguish exact positivity from threshold selection rather than silently hard-code a rank policy.

For a thin or compact factorization, U T b is not necessarily the entire coordinate vector of b in the codomain; it contains projections onto the range directions. The omitted orthogonal component is unreachable and becomes part of the least-squares residual. This observation helps avoid a common shape error: do not pad or truncate vectors casually to make products type-check. The factor dimensions encode domain, codomain, and retained subspace.

Numerical validation should check reconstruction ‖ A − U Σ V T ‖ with a stated norm and scale, orthogonality of the returned bases, nonnegative descending singular values, and convergence status. Full factors can be checked against identity; thin factors should satisfy U t T U t = I and V t T V t = I on their retained columns. A rank- r compact representation should be assessed against its claimed rank and residual. These checks answer different questions and should not be collapsed into one vague “valid” flag.

Dense SVD computation is costly compared with a triangular solve or Cholesky factorization, so compute a full decomposition only when its information is needed. A result contract should state full versus economy shapes, convergence status, workspace or allocation behavior, threshold policy if rank is reported, and whether the method is approximate. Reusable scratch storage can avoid repeated allocation, but must have explicit ownership, size, alignment, and concurrency rules. For large sparse or structured problems, selected singular triplets or randomized low-rank methods may be more appropriate than a full dense decomposition. Algorithm choice is workload dependent; the factorization’s geometric definition does not certify speed or accuracy of any particular implementation.

An implementation review checklist grounded in the map

Before trusting an SVD API, trace one vector end to end. Confirm that a column of V is read as a domain vector of length n , the corresponding u i has codomain length m , and applying the map returns σ i u i . For the 2 × 2 rotation example above, verify both singular vectors individually and verify the input trace ( 1 , 0 ) ↦ ( c , − c ) ↦ ( 4 c , − 2 c ) ↦ ( 3 , 1 ) . Reconstruction alone may not expose a transposed-factor convention if the same convention is used consistently in both factor generation and application; the vector trace forces the documented orientation to be explicit.

Test shape policy separately on tall, square, and wide inputs, and include rank-deficient cases. A thin decomposition of a wide matrix should not be mistaken for a full right basis: it may omit the nullspace completion, even though the compact factors reconstruct A . If a caller needs a nullspace basis, the API must return a full V or offer a separate nullspace operation. Likewise, if a caller needs the left nullspace, the full U completion matters. This is why “economy” is a storage decision, not a claim that all geometric subspaces have been returned.

Finally, keep mathematical exactness separate from numerical policy in names and output. An exact pseudoinverse divides by every strictly positive singular value. A thresholded operation should report τ , whether it is absolute or relative, the number of retained values, and whether a positive value was discarded. A low-rank approximation should report k and a residual measure. A solver should distinguish convergence from nonconvergence and exact consistency from least-squares fit. Such outputs let a caller decide whether the result matches the meaning of the data rather than infer a guarantee from a type name.

Householder reductions turn a dense SVD into a bidiagonal problem

A dense SVD algorithm does not normally make an arbitrary matrix diagonal in one leap. It first reduces A to bidiagonal form with left and right orthogonal transformations. Bidiagonal means only the main diagonal and one neighboring diagonal can be nonzero, for example upper bidiagonal B i i = d i , B i , i + 1 = e i . Write B = Q L T A Q R , so A = Q L B Q R T . Singular values are preserved: B T B = Q R T A T A Q R , which is an orthogonal similarity of A T A and therefore has the same eigenvalues, namely the squared singular values.

Alternating Householder reflectors create this band structure. At stage k , a left reflector acting on rows k through m − 1 maps the active column tail to one leading value followed by zeros. A right reflector acting on columns k + 1 through n − 1 then maps the remaining active row tail to one superdiagonal value followed by zeros. These operations leave earlier completed bands alone. Continue on the trailing submatrix. For a small visual trace, a 4-by-4 dense matrix first becomes a shape with only column 0’s diagonal entry nonzero below the first row; the right reflector removes row 0’s entries from column 2 onward. The next left step clears column 1 below its diagonal, and the next right step clears that row beyond its superdiagonal. Repeating leaves exactly the diagonal and superdiagonal. A later iteration can now work on this narrow matrix instead of a dense one.

The reflector is represented compactly as H = I − τ v v T . Store the vector tail and scalar τ , not a full m × m reflector. Applying it to a matrix block is H A = A − τ v ( v T A ) , a projection followed by a rank-one update. A reduction may overwrite the input: the final bidiagonal diagonal and superdiagonal occupy their positions, while unused lower/upper regions retain left/right reflector tails. This is an encoded factorization state, not a conventional matrix at every intermediate moment. Accumulating the reflectors yields Q L and Q R if vectors are requested. The dense Householder bidiagonal reduction is often called Golub–Kahan bidiagonalization in the direct SVD context. There is also a related Golub–Kahan–Lanczos recurrence for large sparse partial-SVD problems, which generates Krylov vectors and a small bidiagonal projection rather than reducing the entire dense matrix. They share a bidiagonal structure but are distinct algorithms; the latter is not a synonym for the dense reflector reduction.

The aspect ratio affects the route. A common direct bidiagonal backend is designed for tall or square input ( m ≥ n ). For a wide m × n matrix with m < n , compute a thin SVD of the tall transpose A T = U ~ Σ t V ~ T , where U ~ : n × m , Σ t : m × m , and V ~ T : m × m . Then A = V ~ Σ t U ~ T , so the original thin factors are U A = V ~ , V A T = U ~ T , with shapes m × m and m × n . Do not transpose a full rectangular Σ without also specifying its dimensions. In particular, an m × n matrix with m < n cannot have n orthonormal columns in U ∈ R m × n , because at most m vectors in R m are independent and orthonormal. A thin form uses r = min ( m , n ) triplets: U : m × r , σ : r , V T : r × n . Full outputs add orthonormal completion columns to square U and V factors. Rank deficient or zero columns still need a valid completion if full orthogonal factors are promised; such added columns are arbitrary orthonormal bases of the remaining complement, not extra observed singular directions.

Jacobi SVD removes column coupling pair by pair

A second route is Jacobi rotation. Two-sided Jacobi alternates left and right plane rotations to simplify local 2-by-2 blocks and drives U T A V toward diagonal form. It maintains orthogonality on both sides and can give accurate singular vectors, though dense production algorithms often favor bidiagonal reduction followed by specialized iterations for speed. One-sided Jacobi is especially direct: copy A into a working matrix B , initialize accumulated right factor V = I , and rotate pairs of columns of B until the columns are mutually orthogonal. The same right rotations are applied to V , so the invariant B = A V is maintained. If the final columns are orthogonal, set σ j = ‖ b j ‖ 2 and u j = b j / σ j for nonzero columns. Then A V = U Σ , or A = U Σ V T . This gives the factors from lengths and directions without diagonalizing a formed normal-equations matrix.

Fix one convention to avoid sign confusion. Let the selected column pair be p , q , and use

J = [ c s − s c ] , c = cos ⁡ θ ,   s = sin ⁡ θ .

Right multiplication [ p   q ] J produces p ′ = c p − s q and q ′ = s p + c q . Their 2-by-2 Gram matrix is G = [ α γ γ β ] with α = p T p , β = q T q , and γ = p T q . The new cross product is the off-diagonal element of J T G J :

p ′ T q ′ = ( α − β ) c s + γ ( c 2 − s 2 ) .

Set it to zero, let t = s / c , and divide by c 2 to obtain γ t 2 + ( β − α ) t − γ = 0 . Directly forming α = p T p , β = q T q , and γ = p T q can overflow. A safer scalar calculation scales both columns by a shared g = max ( ‖ p ‖ 2 , ‖ q ‖ 2 ) and forms the Gram values from p / g , q / g using safe dot products; the common scale cancels from the rotation ratio. Let δ = β − α . For δ ≠ 0 , compute the small root in the equivalent form t = 2 γ / ( δ + copysign ( hypot ( δ , 2 γ ) , δ ) ) , where hypot avoids squaring overflow. For δ = 0 , choose one of the equal-magnitude roots consistently, such as t = 1 ; if γ = 0 , skip the rotation. This avoids first forming a potentially overflowing τ = δ / ( 2 γ ) and avoids 1 + τ 2 . Then use c = 1 / hypot ( 1 , t ) and s = t c . As a numeric check, take α = 4 , β = 2 , γ = 1 . Then t = − ( 2 − 1 ) ; substitution into the cross product formula gives zero. A transpose of J or a swapped coordinate update changes signs, so formulas from another convention cannot be copied piecemeal.

An actual sweep visits column pairs ( 0 , 1 ) , ( 0 , 2 ) , … , ( n − 2 , n − 1 ) , computes their Gram entries, skips already orthogonal pairs, rotates the two columns of B , and applies the same rotation to columns p , q of V . Repeated sweeps reduce all pairwise correlations. Once converged, compute each column norm with a scaled stable norm, sort singular values descending while permuting matching columns of U and V , and set U columns by normalized working columns. A zero-norm column cannot be normalized; it corresponds to a zero singular value and null-space direction. For a thin rank- r output one may omit null directions based on a declared rank threshold; for a full orthogonal output, construct a deterministic or documented orthonormal completion in the remaining complement. In a wide case, use a tall backend on A T and swap factors rather than trying to construct an impossible m × n column-orthonormal U .

A pedagogical one-sided Jacobi loop is not a production SVD. Its naive dot products and squared norms can overflow or underflow, it may require scaling and safe accumulation, rank policy is application dependent, zero-column completion and wide-matrix handling are nontrivial, and convergence is not guaranteed within a fixed sweep budget. Mature numerical libraries use carefully tested algorithms and workspace policies. The useful claim here is the derivation and invariant, not that a short loop replaces those implementations.

Scale-aware convergence and output conventions make results interpretable

For one-sided Jacobi, a useful normalized measure for columns p , q is their absolute cosine ρ p q = | p T q | / ( ‖ p ‖ 2 ‖ q ‖ 2 ) . Avoid computing α β because the product can overflow or underflow even when each column norm is representable. Compute stable scaled norms and a dot product of separately normalized columns, ρ = | ( p / ‖ p ‖ ) T ( q / ‖ q ‖ ) | , with safe accumulation. It is dimensionless and does not depend on column units. A stopping rule checks all relevant pairs against a tolerance and also has a maximum sweep count. Raw | p T q | is misleading: the same dot product could be negligible for huge columns and large relative to tiny columns. Near-zero columns require separate rank/zero handling because normalized correlation is undefined. The criterion should state its behavior for them rather than divide by zero.

Check approximate singular triplets ( u i , σ i , v i ) with both residuals r i = A v i − σ i u i and s i = A T u i − σ i v i . Scale residual norms against a safe expression involving ‖ A ‖ , σ i , and vector norms. For a bidiagonal iteration, convergence appears as superdiagonal entries becoming negligible relative to neighboring diagonal scale; deflation then separates blocks. Also check reconstruction and orthogonality independently: small residual alone does not prove the full factor matrices are orthogonal, and reconstruction alone may hide compensating factor errors. Iteration count, tolerance, scaling, and nonconvergence status belong in the result contract.

Singular values are nonnegative and commonly sorted σ 1 ≥ ⋯ ≥ 0 . When reordering, apply exactly the same permutation to paired columns of U , V ; otherwise reconstruction changes. Signs are not unique: replacing both u i and v i by their negatives leaves σ i u i v i T unchanged. With repeated singular values, any orthogonal basis of that repeated singular subspace is valid; with zero values, the corresponding left and right null-space completions can be selected independently subject to orthogonality. Therefore two valid runs can return different columns. In animation or tracking, arbitrary sign flips can make axes jump; aligning signs to a previous frame helps for isolated singular values, while repeated-value clusters require subspace alignment rather than sign correction alone.

Numerical stability and conditioning must be separated. Householder and Givens factors are orthogonal, so they preserve 2-norm and have condition number one; Jacobi rotations share that property. They avoid artificial scaling during reduction. A very small singular value, however, means the input nearly erases a direction; inversion along that direction is intrinsically sensitive. Forming A T A to compute singular values squares the condition number: if singular values are 1 and 10 − 10 , the squared problem contains eigenvalues 1 and 10 − 20 , which can lose relative information in finite precision. The computation may also overflow when squaring values near 10 300 or underflow near 10 − 300 . Use scaled norm and dot-product strategies. Tiny singular values need both absolute and relative interpretation: a computed 2 × 10 − 12 for a true 10 − 12 has tiny absolute error but 100% relative error, which may change rank or pseudoinverse results. A backward-stable algorithm returns an exact answer to a nearby input; if the original problem is ill-conditioned, that small input perturbation can still yield a large forward change.

Independent reconstruction and orthogonality checks test the SVD invariants

For a thin factorization of A ∈ R m × n with r = min ( m , n ) , store U as m × r , the singular values as a length- r vector, and V T as r × n . Since Σ is diagonal, it need not be stored densely. Reconstruct entry ( i , j ) by A ^ i j = ∑ k = 0 r − 1 U i k σ k V k j T . The Frobenius norm is the Euclidean norm of all entries, ‖ M ‖ F = ( ∑ i j M i j 2 ) 1 / 2 . Relative reconstruction error is ‖ A − A ^ ‖ F / ‖ A ‖ F : it measures aggregate reconstruction discrepancy compared with input scale. For the zero matrix, the denominator is zero, so define a separate absolute-error policy or use a safe scale; do not silently divide by zero. For extreme magnitudes, compute norms with scaling rather than directly summing squares.

Thin left singular vectors must satisfy U T U = I r ; right vectors satisfy V V T = I r when stored as V T with r orthonormal rows, equivalently V r T V r = I r if stored as V r . Measure the Gram-matrix defects, such as ‖ U T U − I r ‖ F and ‖ V r T V r − I r ‖ F . A diagonal defect means columns are not unit length; an off-diagonal defect means two vectors are not perpendicular. Checking norms alone is insufficient: two identical unit columns pass individual length checks. Check nonnegative sorted singular values, both singular-triplet residuals, reconstruction, and orthogonality. These invariants expose different failures and should not be collapsed into one success boolean.

A matrix object must describe shape, ownership, and workspace

Dynamic matrices need one owned contiguous allocation, explicit row and column counts, and a stride contract. A std::vector<std::vector<double>> gives each row a separate allocation, weakens locality, and complicates interfaces. A non-owning matrix view borrows storage and must not outlive it. For row-major storage, element ( i , j ) at a view’s base pointer is data[i * stride + j]; the stride is the number of stored elements from one row start to the next, which may exceed the logical column count.

Before allocating m n elements, check that size multiplication does not overflow. Check indexing and shape compatibility at API boundaries or encode them in a validated type. Empty matrices are not automatically invalid; define which shapes are accepted by each factorization and what outputs they produce. In-place algorithms may overwrite the input with factors, which saves memory but changes ownership and aliasing expectations. Out-of-place algorithms preserve input and simplify failure handling but require additional storage. A safe API names this choice.

Numerical routines often need scratch workspace. Repeatedly allocating inside an iteration can cost time and fragment memory. A caller-provided workspace or reusable arena can improve predictability, but it needs size, alignment, lifetime, reentrancy, and thread-safety rules. Do not hide shared mutable scratch in a global singleton. GPU routines may require device-specific workspace and synchronization rules that a CPU matrix view does not express.

An SVD result type should expose the actual shape and status, not only three unlabelled buffers. It should say whether factors are full or thin, what threshold or algorithm was used, how many iterations occurred, whether convergence succeeded, and how the residual/orthogonality checks were evaluated. An approximate result can still be useful if its quality is visible.

Dynamic matrix storage makes factorization dimensions and lifetimes explicit

Decomposition input sizes are runtime values, so fixed Mat3 types are not enough. An owning dense matrix should keep dimensions and one contiguous allocation. For row-major storage, element ( i , j ) is at offset i ⋅ s + j , where s is the row stride and equals the number of columns for tightly packed storage. A non-owning view needs a pointer, row count, column count, row stride, and extent/capacity information sufficient to verify that the last referenced element is within the allocation. std::vector<std::vector<double>> is usually a poor dense numerical layout: rows may have separate allocations, rows are not guaranteed adjacent, and pointer chasing impedes cache use and library interoperability.

A checked owner can guard multiplication before allocating:

#include <cstddef>
#include <limits>
#include <stdexcept>
#include <vector>

class Matrix {
public:
    using size_type = std::size_t;

    Matrix(size_type rows, size_type cols)
        : rows_(rows), cols_(cols),
          data_(checkedCount(rows, cols), 0.0) {}

    size_type rows() const noexcept { return rows_; }
    size_type cols() const noexcept { return cols_; }
    size_type stride() const noexcept { return cols_; }
    size_type size() const noexcept { return data_.size(); }
    double* data() noexcept { return data_.data(); }
    const double* data() const noexcept { return data_.data(); }

    double& operator()(size_type i, size_type j) {
        if (i >= rows_ || j >= cols_) throw std::out_of_range("matrix index");
        return data_[i * cols_ + j];
    }
    double operator()(size_type i, size_type j) const {
        if (i >= rows_ || j >= cols_) throw std::out_of_range("matrix index");
        return data_[i * cols_ + j];
    }

private:
    static size_type checkedCount(size_type r, size_type c) {
        if (r != 0 && c > std::numeric_limits<size_type>::max() / r)
            throw std::length_error("matrix element count overflow");
        const size_type count = r * c;
        if (count > std::vector<double>{}.max_size())
            throw std::length_error("matrix exceeds vector max_size");
        return count;
    }
    size_type rows_ = 0, cols_ = 0;
    std::vector<double> data_;
};

The overflow check must happen before multiplication; otherwise unsigned arithmetic can wrap and allocate too little. A view over an existing allocation also needs an extent check. For nonzero dimensions and row stride s , the largest addressed offset is ( r − 1 ) s + ( c − 1 ) ; checked arithmetic must confirm this is less than the available element count, and require c ≤ s . Empty views need a deliberate policy because no element is addressed, and null pointers can be permitted only when the extent is zero.

class MatrixView {
public:
    using size_type = std::size_t;
    MatrixView(double* p, size_type rows, size_type cols,
               size_type stride, size_type extent)
        : p_(p), rows_(rows), cols_(cols), stride_(stride), extent_(extent) {
        if (p == nullptr && extent != 0)
            throw std::invalid_argument("null view pointer requires zero extent");
        if (cols > stride) throw std::invalid_argument("width exceeds stride");
        if (rows != 0 && cols != 0) {
            if (rows - 1 > (std::numeric_limits<size_type>::max() - (cols - 1)) / stride)
                throw std::length_error("view extent calculation overflow");
            const size_type last = (rows - 1) * stride + (cols - 1);
            if (last >= extent)
                throw std::out_of_range("view exceeds backing storage");
        }
    }
    double& operator()(size_type i, size_type j) const {
        if (i >= rows_ || j >= cols_) throw std::out_of_range("view index");
        const size_type offset = i * stride_ + j; // safe after constructor bound proof
        if (offset >= extent_) throw std::out_of_range("view storage extent");
        return p_[offset];
    }
private:
    double* p_; size_type rows_, cols_, stride_, extent_;
};

The view’s extent argument is the number of accessible elements from its starting pointer, not the entire parent’s capacity unless the start pointer is the parent base. A submatrix beginning at row i 0 , column j 0 has base offset i 0 s + j 0 and still uses the parent’s stride; its remaining extent is parent size minus that offset. A view owns nothing. Its lifetime cannot exceed the owner’s, and vector reallocation, move, resize, or destruction can invalidate it. A safe API documents this borrow and avoids retaining views past calls that may resize the owner. Row-major and column-major are storage choices, distinct from mathematical row/column conventions. One-sided Jacobi streams columns, so column-major storage may suit it; other kernels may prefer another layout or blocking. Factorization routines also overwrite storage with encoded reflectors, so specify whether an API copies input or mutates it.

A result type should make output shape and status inspectable instead of returning an undocumented tuple. For a thin SVD it can own U , a singular-value vector, and V T , plus convergence status and iteration count. Rank is not an exact floating-point fact: if reported, its threshold policy and scale must be documented. Full SVD requires square orthogonal completions; thin SVD may include all r = min ( m , n ) directions including zero singular values, or a compact rank- k output after a rank policy. Those are different contracts. Never claim U ∈ R m × n has orthonormal columns when m < n ; instead route through a tall algorithm on A T and swap factor roles. For zero columns and full outputs, construct an orthonormal complement and label those vectors as completion directions. Zero dimensions, allocation failure, overflow, and nonconvergence all need defined outcomes.

The connection across these ideas is now operational: center samples to uncover data variation; diagonalize covariance or factor the data to find principal directions; regroup SVD factors to separate stretch and orientation; reduce dense input orthogonally to bidiagonal form or orthogonalize columns with Jacobi; test normalized convergence and independent decomposition invariants; then represent the result with checked dimensions, strides, extents, and lifetimes. The derivations explain why the algorithm works, while the storage and validation contract states what a caller can safely trust. This is an implementation teaching model, not evidence that a short educational routine is a complete production SVD.

Zero singular directions require deliberate orthonormal completion

Suppose a tall m × n matrix has rank k < n . Its compact nonzero SVD needs k paired singular vectors. A thin shape that returns all n singular values also needs n − k zero-singular directions. The right vectors for those zeros span the null space of A ; the left vectors may span any orthogonal directions completing the range in R m . For reconstruction, any such orthonormal completions are valid because their singular values are zero, so their outer-product terms vanish. They still matter to APIs that promise orthogonal factors or expose null-space bases.

A simple completion method starts from standard basis candidates e 1 , e 2 , … , subtracts projections onto all existing columns, and accepts a candidate only if the remaining norm exceeds a scale-aware threshold. Normalize the accepted remainder and continue until the requested number of orthonormal vectors is reached. If a candidate nearly lies in the existing span, it is rejected to avoid normalizing roundoff noise. This is Gram–Schmidt in a constrained complementary subspace and may need reorthogonalization for robustness. A full square U needs m orthonormal columns; full V needs n . A wide matrix can be handled by factoring A T with a tall method and swapping left/right roles, preserving the feasible dimensions. The completion vectors are mathematically valid choices but can vary across implementations, especially near repeated or zero singular values. Any consumer requiring temporal continuity or a domain-specific null-space orientation must add its own selection rule.

Matrix views need checked address arithmetic as well as a stride

For a non-owning view with base pointer p , rows r , columns c , row stride s , and accessible extent e elements starting at p , the address calculation is p [ i s + j ] . Bounds on logical indices alone do not prove the address is within the backing allocation. Require c ≤ s for nonempty row-major views. When r , c > 0 , the last accessed offset is ( r − 1 ) s + ( c − 1 ) ; before evaluating it, check multiplication/addition overflow, then require the offset to be less than e . For a subview starting at offset o into a parent allocation, pass the pointer p + o and extent e − o , not the original extent, or the view’s bounds check may incorrectly permit reaching beyond the parent. Empty views should have an explicit rule: they access no elements, so one may allow null data and avoid all pointer arithmetic, while still retaining meaningful row/column metadata.

The owner and view types have distinct responsibilities. The owner allocates, controls capacity, and may move; a view borrows and must not extend that lifetime. Returning a view from a temporary owner is unsafe. Resizing a vector-backed matrix can reallocate and invalidate every view, even when the dimensions look similar. A factorization that creates a trailing-submatrix view must ensure no resize occurs until the operation ends. For const correctness, provide separate mutable and read-only views so a function that only validates A cannot accidentally overwrite its input. These rules are part of numerical API correctness because an otherwise sound reflector update becomes memory corruption if its strided block points outside the allocation.

Factorization is also a memory and lifetime decision

Calling factor(A) raises an API question before an arithmetic one: will the caller’s original matrix still exist afterward? An out-of-place routine accepts a read-only view, copies or otherwise reads the input, and writes factors to owned result storage. An in-place routine treats the input buffer as scratch and returns an encoded factorization. Both choices can be correct, but an ambiguous choice is dangerous.

For LU, packed storage puts U on and above the diagonal and the strict lower part of L beneath it; the unit diagonal of L is implicit. After factorization, an entry below the diagonal is a multiplier, not the corresponding original coefficient. A caller that continues to interpret the array as A will use the wrong matrix. For Householder QR, the upper triangle stores R , while the lower region stores reflector tails and a separate τ vector describes the reflectors. That buffer is not a regular matrix of Q or R ; it is a compact representation of both factors.

An out-of-place call such as factorLU(ConstMatrixView A) can preserve source data for later diagnostics, retries, or comparison. It costs an O ( m n ) copy and a second matrix-sized allocation. For square dense LU, factorization work is O ( n 3 ) , so the copy is asymptotically smaller, but its memory bandwidth and peak storage matter for large matrices. In-place factorization reduces peak memory and can be essential when a dense matrix already occupies several gigabytes. It also means a mid-factorization failure has partially mutated the caller’s buffer. That failure behavior belongs in the contract.

Aliasing must be stated with equal care. If multiply(A, B, A) is permitted, the algorithm must guarantee that writing output does not destroy an input value still needed later. A factorization may accept one mutable buffer because it is explicitly destructive, but an output view must not overlap scratch or source in ways the implementation cannot handle. A simple API can prohibit overlap and validate it; an advanced API can document exact supported alias patterns. const communicates the input mutation promise, while names like factorInPlace make destructive behavior conspicuous.

Factor objects also have a lifetime. A returned view into a caller buffer must not outlive that buffer. A workspace-backed result must not be used after its arena resets. An owned result can outlive the call but costs allocation and copy/move behavior. A library should make these choices visible in the types or function names, because memory lifetime errors can masquerade as numerical corruption.

Workspace allocation is part of the solver contract

Numerical algorithms need scratch: permutation indices, temporary columns, reflector coefficients, norm estimates, block buffers, convergence flags, or temporary right-hand sides. Allocating a fresh vector inside every sweep or iteration creates allocator overhead, latency spikes, and possible fragmentation. A useful routine either owns a single predictable allocation or accepts caller-controlled workspace.

One common lifecycle is: query the required workspace size from dimensions and options; allocate an arena once; pass the arena into one or more numerical calls; reset or reuse it only after results that depend on it are no longer needed. This fits a frame arena, task arena, or long-lived per-thread scratch object. It also lets real-time code reserve memory before the hot path.

A byte arena must align every allocation for the requested type. Conceptually, for cursor c and required alignment a , the aligned start is c ′ = ⌈ c / a ⌉ a . Before reserving n objects of size s , validate both multiplication and addition: reject if n > ⌊ SIZE\_MAX / s ⌋ before computing n s , then reject if c ′ > capacity or n s > capacity − c ′ . These checks prevent integer overflow from making an undersized buffer appear large enough. The storage base itself also needs the requested alignment; aligning only the offset is insufficient if the underlying pointer is misaligned.

The implementation of the alignment formula needs its own overflow care. Rather than blindly calculating c + a - 1, compute the remainder, derive the padding, and verify padding <= capacity - c before advancing. Also validate that a is nonzero and meets the allocator’s supported alignment rules. These details are part of memory safety even though they do not change the numerical equations.

This sketches a contract, not a finished allocator. The caller owns the storage and must keep it valid, sufficiently large, correctly aligned, and exclusive for the call’s duration. A reusable workspace cursor should reset at a clearly stated point. Do not use a hidden global scratch vector: simultaneous calls, recursion, and thread reentrancy can overwrite one another. A thread-safe routine can still use caller-provided, per-call or per-thread workspaces without locks.

Small fixed-size kernels often use stack arrays, which avoid allocation. Dynamic matrices can require scratch too large for a safe stack allocation; they need heap storage, an arena, or caller memory. GPU routines introduce a separate device workspace: host pointers cannot be treated as device buffers, device allocation is expensive, and stream/lifetime synchronization matters. CPU and GPU requirements should be distinct in the API, even if the mathematical operation has the same name.

Sparse problems change the economics of solving

Dense storage keeps every entry, even zeros. Sparse matrices arise when each constraint interacts with only a few variables: meshes, graph neighborhoods, finite-element systems, and large network problems are common examples. Coordinate (COO) storage records row, column, value triples and is convenient for assembly. Compressed sparse row (CSR) stores row offsets, column indices, and values for efficient row traversal and matrix-vector products.

Sparse is not automatically faster. Index overhead can exceed the cost of storing a small dense matrix, and fill-in during sparse direct factorization may make factors much denser than the input. Direct methods provide a finite sequence of factorizations and solves; iterative methods build an approximate solution through repeated matrix-vector products. For huge sparse systems, iteration can be practical when convergence is suitable and preconditioning works, but it must report residual and stopping status.

Conjugate gradient applies to symmetric positive-definite systems. In exact arithmetic it minimizes an energy error over expanding Krylov subspaces; in finite precision, loss of conjugacy and conditioning affect behavior. Preconditioning changes the effective spectrum and can accelerate convergence, but a preconditioner must be chosen for the matrix, memory, and workload. For general nonsymmetric systems, other Krylov methods are used. Warm starts can help when successive frames or timesteps change only slightly, but stale or invalid initial state must not be mistaken for convergence.

Sparse storage changes the cost model

Sparse systems occur when interactions are local: mesh neighborhoods, graph edges, finite elements, Laplacians, bundle adjustment, and constraints. A dense million-by-million double matrix would require roughly eight terabytes; a matrix with seven nonzeros per row has about seven million values and is practical in sparse form. Sparse does not mean “store dense with zeros skipped in a loop”; it needs indices and a representation matched to operations.

Coordinate (COO) format stores triplets ( r o w , c o l u m n , v a l u e ) and is simple during incremental assembly. It may contain duplicate coordinates that must be combined before some operations. Compressed sparse row (CSR) stores a flat value array, corresponding column indices, and row offsets. For A = [ 4 0 2 0 5 0 1 0 3 ] , values=[4,2,5,1,3], columns=[0,2,1,0,2], rowOffsets=[0,2,3,5]. Row i traverses offsets rowOffsets[i] through rowOffsets[i+1]-1. With x = ( 1 , 2 , 3 ) T , its product is A x = ( 10 , 10 , 10 ) T .

CSR matrix-vector multiplication is:

for row in 0 .. rows-1:
    sum = 0
    for k in rowOffsets[row] .. rowOffsets[row+1]-1:
        sum += values[k] * x[columnIndices[k]]
    y[row] = sum

Its arithmetic cost is O ( nnz ) . The indirect gather from x can make it memory-bandwidth and latency bound. Tiny matrices can be slower in sparse form because index and branch overhead outweigh saved zero arithmetic. Sparse direct factorization can also create fill-in: zero entries become nonzero in L or U . Reordering variables (nested dissection, approximate minimum degree, and related methods) can reduce fill; here permutation is also a memory/performance algorithm. sparse and iterative solvers need different data structures and contracts than dense kernels.

Direct and iterative solvers suit different workloads

Direct methods such as LU, Cholesky, and QR build factors through a finite sequence of operations. They often suit moderate dense systems or many right-hand sides sharing a matrix. Iterative methods begin from x 0 , compute residual r 0 = b − A x 0 , and improve the estimate until a stopping rule or iteration limit. They may need only matrix-vector products and so avoid storing factors, which matters for huge sparse or matrix-free problems.

For SPD A , Conjugate Gradient (CG) solves by generating A -conjugate search directions and, in exact arithmetic, minimizes ϕ ( x ) = 1 2 x T A x − b T x over successively larger Krylov subspaces. The k th Krylov space is K k ( A , r 0 ) = span { r 0 , A r 0 , … , A k − 1 r 0 } , and CG minimizes error in the energy norm ‖ e ‖ A = e T A e . Its standard recurrence is:

r 0 = b − A x 0 , p 0 = r 0 ; α k = r k T r k p k T A p k , x k + 1 = x k + α k p k , r k + 1 = r k − α k A p k , β k = r k + 1 T r k + 1 r k T r k , p k + 1 = r k + 1 + β k p k .

Before entering the recurrence, compute the residual and stop successfully if the scaled residual already meets the tolerance; otherwise an exact initial solution would cause 0 / 0 in the first step. At each step, treat nonpositive or nonfinite p k T A p k as breakdown, and stop on convergence before forming the next β if the new residual is zero or small. The denominator is positive for nonzero p k when A is SPD. In exact arithmetic CG terminates in at most n steps; finite precision can lose conjugacy. Convergence depends on the eigenvalue distribution and condition number. A classic bound behaves like 2 ( ( κ − 1 ) / ( κ + 1 ) ) k in the energy norm: clustered spectrum and small condition number help. CG is not an all-matrix method: symmetric indefinite problems may use MINRES; nonsymmetric ones may use GMRES or BiCGSTAB.

Preconditioning chooses an easy-to-apply approximation M . For CG, use a symmetric positive-definite preconditioner through the standard preconditioned-CG recurrence, equivalently the symmetric transformed system M − 1 / 2 A M − 1 / 2 y = M − 1 / 2 b with x = M − 1 / 2 y . Do not apply the unpreconditioned recurrence directly to the left-preconditioned operator M − 1 A , which need not be symmetric in the Euclidean inner product even when M and A are SPD. The goal is a more favorable spectrum, not merely a matrix that looks numerically smaller. Jacobi/diagonal scaling, incomplete factorizations, and multigrid are families with distinct cost and assumptions. A preconditioner can dominate iteration speed and must be included in the workload contract.

Stopping must inspect residuals with scale, iteration count, and finite-value checks. A recursive CG residual may drift from the true residual due to rounding, so periodically recompute b − A x when assurance matters. The true residual r = b − A x ^ and solution error e = x − x ^ obey A e = r , hence e = A − 1 r and ‖ e ‖ ≤ ‖ A − 1 ‖ ‖ r ‖ . A small residual alone does not establish small solution error when the system is ill-conditioned. A good report includes convergence status, iteration limit, chosen norm/tolerance, final true residual, and perhaps an error/condition estimate where feasible.

Warm starts use a prior solution as x 0 , which can be effective in frame-to-frame simulation or slowly changing constraints. They do not excuse stale state: validate dimensions and current-system residual, and fall back or continue iterating if the prior answer is no longer useful. Direct methods and iterative methods therefore trade factorization cost, fill/memory, repeated right-hand sides, convergence, preconditioner setup, and hardware behavior. Choose a factorization from structure and the requested answer

“Square” alone does not imply LU. For dense general square systems, pivoted LU is a practical general choice. Symmetric positive-definite systems usually favor Cholesky. Symmetric indefinite systems need pivoted block L D L T . Full-rank least squares favors QR; if rank is uncertain or minimum norm matters, SVD is more revealing. Symmetric eigenproblems have specialized orthogonal eigensolvers. Huge sparse systems may favor iterative methods if convergence and preconditioning work, while sparse direct factorization may be preferable for moderate problems or many right-hand sides when fill remains controlled.

For least squares, do not explicitly invert normal equations. Forming A T A squares the 2-norm condition number in full column rank: κ 2 ( A T A ) = κ 2 ( A ) 2 . QR avoids this squaring; SVD exposes weak directions. Ask whether every singular value or eigenpair is needed: partial/iterative methods are more suitable if only leading components matter. The same matrix with one right-hand side versus thousands can have a different best strategy because one factorization can be amortized. Hardware also matters: dense matrix-matrix kernels make blocked algorithms fast; sparse gathers are memory bound; triangular solves have dependencies; GPU workspaces and transfer costs enter the calculation.

QR fits noisy samples without changing the residual measure

Fit y = a + m x through ( 0 , 1 ) , ( 1 , 2 ) , ( 2 , 2 ) . The columns of A are ( 1 , 1 , 1 ) T and ( 0 , 1 , 2 ) T . Their means are one and one, so centering gives slope m = 1 / 2 and intercept a = 5 / 3 − 1 / 2 = 7 / 6 . Predictions are ( 7 / 6 , 5 / 3 , 13 / 6 ) ; the residual is ( − 1 / 6 , 1 / 3 , − 1 / 6 ) . Its dot product with both columns is zero, proving that no small change to intercept or slope reduces squared error. The squared residual length is 1 / 6 . QR performs this fit by an orthogonal change of output coordinates followed by a triangular solve. It avoids explicitly squaring the condition of the design matrix as normal equations do.

Power iteration needs a visible starting component

For A = diag ( 4 , 2 ) and initial x 0 = ( 1 , 1 ) T , one unnormalized step gives ( 4 , 2 ) T . The ratio of first to second components is now two. Each further multiplication doubles that ratio, so normalization makes the vector approach the first coordinate axis. That axis is the eigenvector for eigenvalue four. But if the initial vector is ( 0 , 1 ) T , its dominant component is exactly absent and the method stays on the second axis. Iterative methods have starting assumptions, convergence criteria, and failure states; the word “iteration” does not remove them.

An SVD separates input directions from output directions

Consider the rectangular map

A = [ 3 0 0 2 0 0 ] = I 3 [ 3 0 0 2 0 0 ] I 2 T .

The input basis direction e 1 becomes 3 e 1 in output space; e 2 becomes 2 e 2 . For x = ( 1 , 1 ) T , A x = ( 3 , 2 , 0 ) T , so the input length is 2 and output length is 13 . The map has no single scale factor. Its largest stretch is three and smallest nonzero stretch is two. The third output coordinate is never reached. This small decomposition makes the full, thin, and rectangular dimension bookkeeping concrete.

Pseudoinversion states what to do with an impossible target

Let A = diag ( 3 , 0 ) and b = ( 6 , 5 ) T . There is no exact solution because the second row can only produce zero. The least-squares residual must retain a vertical component of magnitude five. Every x = ( 2 , t ) T gives that same residual, so the minimum-norm answer is ( 2 , 0 ) T . The SVD pseudoinverse produces it by inverting three and setting the zero singular direction to zero. If the zero were merely tiny, deciding whether to invert it would require a scale-aware rank threshold.

PCA tells geometry only after centering and choosing units

The samples ( − 1 , 0 ) , ( 0 , 0 ) , ( 1 , 0 ) are already centered. With sample divisor N − 1 = 2 , their covariance is diag ( 1 , 0 ) . The first principal direction is horizontal; the second has zero variance. Adding slight vertical measurement noise makes that eigenvalue small rather than exactly zero. If the data’s mean were not subtracted first, an offset cloud could make the first component describe its location instead of its shape. If one feature is measured in millimetres and another in metres, rescaling one feature changes PCA’s answer unless a deliberate standardization policy is applied.

Orthogonal factors support clearer error statements

For A = diag ( 3 , 2 ) , ‖ A ‖ 2 = 3 , ‖ A ‖ F = 13 , and κ 2 ( A ) = 3 / 2 . The spectral norm asks for the largest single-direction gain; the Frobenius norm combines squared gains over all directions. Replacing the second entry by 10 − 8 leaves the matrix invertible but makes its condition number 3 × 10 8 . A small residual then does not guarantee that a small change in the measurements causes only a small change in the recovered answer.

An SVD API begins with shapes and guarantees

For A ∈ R m × n , let r = min ( m , n ) . A thin SVD returns U ∈ R m × r , a length- r nonnegative singular-value vector σ , and V T ∈ R r × n , such that A ≈ U Σ V T . Do not allocate a dense rectangular Σ ; only its diagonal vector is needed. A full SVD instead returns square U of shape m × m and square V T of shape n × n , with extra orthonormal basis vectors. Full and thin have different storage and caller use cases.

State whether the API stores V or V T . If it stores Vt, rows are right singular vectors, and the compact orthogonality check is V t V t T ≈ I r . If it stores a thin V, columns are right singular vectors and V T V ≈ I r . Mixing these conventions causes transposition and dimension errors that can look like numerical failures.

The output contract should include singular values sorted in descending order, unconditional rejection of nonfinite input, convergence status, sweep/iteration count, residual or final coupling measure, selected factor shapes, numerical rank threshold, and workspace requirements. NoConvergence is a useful numerical outcome even if invalid dimensions are exceptions. An output with plausible values but no status is difficult to trust. A “success” status means the selected stopping rule was met; it does not imply every downstream task is well-conditioned.

This is an interface design, not a backend. NotRun is the default so an empty default-constructed result cannot falsely report success; a backend sets Success only after satisfying the requested stopping rule. The simple call rejects nonfinite input and returns descending triplets unconditionally. Zero tolerances request documented scale-aware defaults; negative or nonfinite tolerances and maxSweeps == 0 report InvalidOptions. The result retains the effective numerical-rank threshold and input scale used so downstream rank-sensitive operations can make the policy visible. Return owned factors in a simple path; advanced paths can return views into caller-owned buffers with explicit lifetime. A workspace-size query should include overflow-checked bytes and alignment. The routine must describe whether output may overlap input, whether the call mutates input, and whether scratch is host or device memory.

Numerical policies must share one rank decision

An absolute magic tolerance such as 10 − 6 is not scale-independent. A default threshold might be proportional to max ( m , n ) ϵ σ max , with a documented algorithm-dependent multiplier. Applications can override it when units or noise models justify another decision. Numerical rank can be defined as the count of σ i > τ . The same threshold policy should feed pseudoinverse, condition estimates, and rank reporting; inconsistent cutoffs make the library’s own results disagree.

If rank is full over the relevant dimensions, a 2-norm condition estimate is σ max / σ min . If rank is deficient, report infinity or a separate rank-deficient state rather than dividing by a value the policy has discarded. Nonfinite values should be rejected or explicitly propagated according to a documented option; otherwise NaNs can poison norm comparisons and cause false convergence.

Triplet sorting must apply the same permutation to each singular value, corresponding column of U , and corresponding row of Vt. Sign is also nonunique: ( u i , v i ) and ( − u i , − v i ) encode the same term. An optional deterministic sign rule can make logs repeatable but cannot make repeated-singular-value bases unique. Tests for a repeated singular subspace should compare its projector, not individual arbitrary basis vectors.

A call lifecycle makes ownership reviewable

A simple out-of-place lifecycle is: create a read-only matrix view; validate dimensions and finite inputs; query or allocate results and scratch; call the SVD; inspect status and shapes; compute diagnostics; consume or move owned outputs. A destructive lifecycle is: provide mutable input storage and nonoverlapping output/workspace views; accept that the input becomes packed/intermediate data; ensure workspace remains alive for the entire call; then interpret output only through the returned layout contract. These paths should not share an ambiguous name.

Algorithm dispatch may use specialized stack-based methods for 2 × 2 through 4 × 4 graphics matrices, a dense backend for medium matrices, and a partial sparse algorithm for huge matrices when only leading singular vectors are requested. Do not silently densify a huge sparse matrix. Backend choice can also depend on whether singular vectors are needed, factor mode, target hardware, workspace, and convergence requirements. A high-level API may dispatch; its status and numerical guarantees remain common.

Validate reconstruction, orthogonality, and triplets separately

A validator should be separate from the computational kernel so expensive checks can run in tests or debug builds but be disabled in hot release paths. For thin U and Vt, check normalized reconstruction

e r e c = ‖ A − U Σ V t ‖ F max ( ‖ A ‖ F , s ) ,

where s is an explicit safe scale for the zero matrix case. Reconstruct entrywise as a ^ i j = ∑ k U i k σ k V t , k j ; there is no need to materialize Σ .

Check left orthogonality via ‖ U T U − I r ‖ F for a thin factor. For a stored thin Vt, check ‖ V t V t T − I r ‖ F ; its rows are the right singular vectors. For full factors, check the corresponding square orthogonality. Separately check triplet residuals A v i − σ i u i and A T u i − σ i v i . Reconstruction, orthogonality, and triplet residual diagnose different failure modes.

Test matrices should include zero and identity matrices; diagonal known spectra; rectangular tall and wide cases; exact and near rank deficiency; repeated singular values; strong scaling; orthogonal inputs; one-row and one-column shapes; empty-dimension policy; NaN/Inf policy; and matrices constructed from known U Σ V T . Compare to a trusted reference where possible. Avoid exact entrywise comparisons of singular vectors because signs and degenerate subspaces vary.

Debug in invariant order. NaN singular values suggest input screening or scaled norm problems. Plausible singular values with poor orthogonality point to incomplete Jacobi convergence or faulty normalization. Orthogonal factors but bad reconstruction suggest rotation order or mismatched sorting. Good reconstruction but unsorted output is ordering policy. Tiny singular-value disagreement may be conditioning and threshold policy. Sign flips or rotations within a repeated subspace are often valid nonuniqueness. The library boundary is part of numerical correctness

A graphics math library can reasonably target small and medium dense matrices used for PCA, polar decomposition, local fitting, pseudoinverse, least squares, and diagnostics. It need not compete with LAPACK or GPU scientific libraries for enormous matrices unless that is an explicit project goal. Dense and sparse matrices have different access costs; CPU and GPU workspaces have different lifetimes; full SVD and leading-vector SVD return different amounts of information. A good boundary states supported shapes, ownership, storage, statuses, tolerance policy, and performance intent without promising universal accuracy.

Across Parts 786–800, the same rule repeats: describe the representation as carefully as the algebra. A factorization may overwrite input; a workspace may expire; a norm chooses what “small” means; a matrix function may have a branch; an iterative method may stop without solving accurately; an SVD may return a valid but nonunique basis. A numerical API earns trust by making those choices visible and by checking independent mathematical invariants.

Close the journey with an algorithm-selection conversation

When a system arrives, use the matrix promises to choose a method, then ask in order:

  1. What are the matrix dimensions, units, storage layout, and intended meaning of rows and columns?
  2. Is the system square, overdetermined, or underdetermined? Is the target in the reachable column space, approximately so, or unknown?
  3. Is the matrix symmetric, positive definite, sparse, rank-deficient, or reused across many right-hand sides?
  4. Is the goal an exact solve, a least-squares fit, a minimum-norm answer, selected eigenpairs, every singular value, a low-rank approximation, or a matrix function?
  5. Which decomposition matches those promises, and what failure status will it return if a promise is false?
  6. What scaled residual, orthogonality check, backward-error measure, or convergence report will make the result observable?
  7. Which perturbations make the answer sensitive, and what threshold or regularization policy expresses the application’s tolerance for that sensitivity?

For a small dense square system with many right-hand sides, pivoted LU is often appropriate. For symmetric positive-definite structure, Cholesky is cheaper. For least squares with known full column rank, QR avoids the normal-equation condition penalty. If rank is uncertain, an SVD or rank-revealing method makes weak directions explicit. For a large sparse problem, representation, fill-in, iterative convergence, and preconditioning dominate. For matrix functions, distinguish the mathematical definition from the stable algorithm that evaluates it.

The key implementation distinction is between a method name and a result contract. “SVD succeeded” should mean the routine returned factors of the promised shapes, a clear convergence status, and diagnostics that a caller can inspect. “Solve succeeded” should distinguish exact consistency from approximate least squares and should not hide rank thresholds or conditioning concerns. A CPU scalar demonstration is not GPU verification, performance benchmarking, a production library, or a guarantee for every floating-point input.

struct Welford {
    std::uint64_t n = 0;
    double mean = 0.0;
    double m2 = 0.0;

    void add(double x) {
        if (!std::isfinite(x)) throw std::domain_error("sample must be finite");
        if (n == std::numeric_limits<std::uint64_t>::max())
            throw std::overflow_error("sample count overflow");
        ++n;
        const double delta = x - mean;
        mean += delta / static_cast<double>(n);
        const double delta2 = x - mean;
        m2 += delta * delta2;
    }
    double populationVariance() const {
        if (n == 0) throw std::domain_error("empty sample");
        return m2 / static_cast<double>(n);
    }
    double sampleVariance() const {
        if (n < 2) throw std::domain_error("need two samples");
        return m2 / static_cast<double>(n - 1);
    }
};

double normalCdf(double x, double mu, double sigma) {

double binomialPmf(unsigned n, unsigned k, double p) {
    if (!std::isfinite(p) || p < 0.0 || p > 1.0)
        throw std::domain_error("invalid probability");
    if (k > n) return 0.0;
    if (p == 0.0) return k == 0 ? 1.0 : 0.0;
    if (p == 1.0) return k == n ? 1.0 : 0.0;
    const double nn = static_cast<double>(n);
    const double kk = static_cast<double>(k);
    const double logChoose = std::lgamma(nn + 1.0) -
                             std::lgamma(kk + 1.0) -
                             std::lgamma(nn - kk + 1.0);
    return std::exp(logChoose + kk * std::log(p) +
                    (nn - kk) * std::log1p(-p));
}

double poissonPmf(unsigned k, double lambda) {
    if (!std::isfinite(lambda) || lambda < 0.0)
        throw std::domain_error("invalid Poisson mean");
    if (lambda == 0.0) return k == 0 ? 1.0 : 0.0;
    const double kk = static_cast<double>(k);
    return std::exp(kk * std::log(lambda) - lambda -
                    std::lgamma(kk + 1.0));
}

struct Cov2 {
    double xx, xy, yy;
    bool isPsd() const {
        return std::isfinite(xx) && std::isfinite(xy) && std::isfinite(yy) &&
               xx >= 0.0 && yy >= 0.0 && xx * yy >= xy * xy;
    }
    bool isPositiveDefinite() const {
        return isPsd() && xx > 0.0 && xx * yy > xy * xy;
    }
};

using Vec2 = std::array<double, 2>;

struct Normal2D {
    Vec2 mean;
    Cov2 cov;
    double l00, l10, l11;
    double logDet;

    Normal2D(Vec2 mu, Cov2 sigma) : mean(mu), cov(sigma) {
        if (!std::isfinite(mean[0]) || !std::isfinite(mean[1]) ||
            !cov.isPositiveDefinite())
            throw std::domain_error("need finite mean and positive-definite covariance");
        l00 = std::sqrt(cov.xx);
        l10 = cov.xy / l00;
        const double schur = cov.yy - l10 * l10;
        if (!(schur > 0.0) || !std::isfinite(schur))
            throw std::domain_error("covariance is singular or numerically invalid");
        l11 = std::sqrt(schur);
        logDet = 2.0 * (std::log(l00) + std::log(l11));
    }

    double logPdf(Vec2 x) const {
        const double y0 = (x[0] - mean[0]) / l00;
        const double y1 = ((x[1] - mean[1]) - l10 * y0) / l11;
        const double mahalanobis2 = y0 * y0 + y1 * y1;
        return -std::log(2.0 * std::numbers::pi)
               - 0.5 * logDet - 0.5 * mahalanobis2;
    }

    Vec2 sample(std::mt19937_64& engine,
                std::normal_distribution<double>& standard) const {
        const double z0 = standard(engine);
        const double z1 = standard(engine);
        return {mean[0] + l00 * z0,
                mean[1] + l10 * z0 + l11 * z1};
    }
};

Rung 1 — Decode a bounded asset

Problem. The file begins with a fixed 16-byte header: four ASCII magic bytes TXR1, a 32-bit little-endian width, a 32-bit little-endian height and a 32-bit little-endian format code. Format code 1 means tightly packed RGBA8: four unsigned eight-bit channels per texel, in red, green, blue, alpha order. Other format codes are unsupported in this exercise. The payload therefore requires 4 w h bytes. A corrupt file may request dimensions whose product overflows size_t, truncate the payload, or contain an unknown format.

Exercise. Write a decoder that takes a read-only span of bytes and returns either an owned Texture or a named DecodeError. In C++23 that result can use std::expected; a C++20 solution can use an explicit tagged success/error result. Reject short headers, wrong magic, zero dimensions, unsupported formats, arithmetic overflow and a payload length other than exactly 4 w h . Explain why copying the first bytes into a C++ struct is not a portable decoder.

Worked solution. Read each integer byte-by-byte after checking that its range is inside the input. Before computing the pixel count, require w≤⌊SIZE_MAX/h⌋w \le \lfloor\text{SIZE\_MAX}/h\rfloor; before multiplying by four, require wh≤⌊SIZE_MAX/4⌋wh \le \lfloor\text{SIZE\_MAX}/4\rfloor. Call the validated payload length N = 4 w h . Require N ≤ SIZE _ MAX − 16 before forming the total, then require input.size() == 16 + N. Separately enforce the application’s declared maximum dimensions and allocation budget: arithmetic safety does not make a very large request affordable. Only after these tests construct an owned texture. The solution preserves the invariant that every later texel index is below a validated extent. Struct copying would additionally assume host endianness, padding, alignment and object representation match the file contract.

Check your work. Hand-trace width w = 2 and height h = 3 : payload length must be 24 bytes. Flip one magic byte, remove the last payload byte, set width to zero, and choose dimensions that overflow multiplication. Each failure must be reported before allocation.

Rung 2 — Give the panel a stable identity and a safe borrow

Problem. The editor stores panels densely in a vector. Deleting one panel and adding another can reuse its slot; vector growth can also move every object. A raw pointer or array index retained by an asynchronous upload callback may now refer to a different panel or to dead storage.

Exercise. Implement a handle with {slot, generation} and a registry whose get(handle) returns a checked borrow. Removing an item invalidates its generation; reusing a slot must not make an old handle valid. State exactly how long a returned pointer may be kept.

Worked solution. Separate logical identity from dense storage. Each logical slot stores a generation and either a dense-array index or an unoccupied marker; each dense value stores its owning slot. A handle resolves only when its slot is in range, occupied, and has the matching generation. When deleting by swapping the last dense value into a hole, update the moved value’s logical slot to its new dense index. Removing an array element without this reverse update leaves a valid-looking handle pointing at the wrong object. Increment the generation on removal, with an explicit policy for generation exhaustion (retire that slot rather than wrap). The simplest safe borrow contract is “valid until the next registry mutation”; callers needing longer use a copied value or a separately owned stable object. The upload callback captures the handle and resolves it on the main thread when publishing, rather than capturing a pointer into a growable vector.

Hand trace. A occupies logical slot 0, generation 0, dense index 0; B occupies slot 1, generation 0, dense index 1. Delete A, move B to dense index 0, update slot 1 to index 0, and increment slot 0 to generation 1. Creating C may reuse slot 0 with generation 1 and dense index 1. A’s old {0,0} handle fails; B’s {1,0} still resolves to B.

Failure test. Create h0, remove its object, reuse the slot to create h1, then require get(h0) to fail and get(h1) to succeed. Force vector growth after obtaining a borrow and verify that the old borrow is never dereferenced.

Rung 3 — Publish asynchronous work without racing ownership

Problem. A worker decodes a texture while the main thread edits or deletes its panel. A successful decode does not imply that the result still belongs to a live object, and a GPU upload submission does not imply that the GPU has finished reading the staging bytes.

Exercise. Draw a state timeline from request through decode, upload, completion and publication. Identify the owner of each buffer and the event that permits its reuse.

Worked solution. The request owns immutable input bytes. The worker owns a decode result and publishes a value message containing the panel handle plus a request/version number. The main thread rejects the message if either the handle is stale or a newer version was requested. It transfers the validated pixels to an upload operation. The staging allocation remains alive until the fence/timeline value for that submission is complete; only then may it be recycled. The destination image remains alive until all submitted work that references it has completed. The main thread publishes the new texture descriptor only at a frame boundary where the renderer’s resource-version contract permits the change.

The state progression is therefore Requested -> Decoded -> Submitted(value) -> Complete(value) -> Published; failures branch to a recorded error and release only resources whose completion conditions are satisfied. A cancellation flag alone cannot free storage already referenced by submitted GPU work.

Rung 4 — Reconstruct a measured panel position

Problem. A camera reports a pixel location for the panel’s known world point. We want to estimate a small two-dimensional translation q = ( t x , t y ) from noisy image measurements while keeping coordinate conventions explicit.

Exercise. For a pinhole camera looking along negative camera z , use a point ( X , Y , Z ) with Z < 0 , focal lengths ( f x , f y ) and principal point ( c x , c y ) . In this small exercise, both camera y and image coordinate v increase upward; an image buffer whose rows increase downward needs the corresponding sign change. Derive the pixel prediction and its Jacobian with respect to translation parallel to camera x , y . For observations z i , set residual r i ( q ) = π i ( q ) − z i and solve a weighted least-squares step.

Worked derivation. With translated camera-space point ( X + t x , Y + t y , Z ) ,

u = f x X + t x − Z + c x , v = f y Y + t y − Z + c y .

Thus the local Jacobian is

J i = [ − f x / Z 0 0 − f y / Z ] .

Stack the residuals and Jacobians, and let W contain the declared inverse pixel-variance weights. A Gauss–Newton step solves ( J T W J ) δ = − J T W r ; compute it through the whitened least-squares system A = W 1 / 2 J , b = − W 1 / 2 r , solving A δ ≈ b with QR or SVD rather than explicitly inverting J T W J .
