### NES-01 — A cartridge is a contract, not merely a bag of bytes

We have just learned that a pattern of bits cannot explain its own meaning. The first time that observation becomes a serious engineering problem is when our program receives bytes from outside itself. Consider an NES cartridge image: an emulator may read a file that is truncated, mislabeled, generated by a newer format, or crafted to produce the wrong sizes. If it guesses what the bytes mean and immediately constructs CPU or graphics state, it has confused an untrusted description with a validated object.

This is the first recurring **C++23 KairoNES project milestone**. The preceding lessons on bits, binary arithmetic, masks, shifts, fields and representation are retained intact. Here we put those ideas to work in a runnable subsystem. The lab is deliberately independent of the graphical window, so its tests can run without the complete emulator.

The project draws from the actual [KairoNES repository](https://github.com/swayam8624/NESEmulator). Its [cartridge loader](https://github.com/swayam8624/NESEmulator/blob/main/NESEmulator/Cartridge.cpp), [bus](https://github.com/swayam8624/NESEmulator/blob/main/NESEmulator/Bus.cpp) and [CPU](https://github.com/swayam8624/NESEmulator/blob/main/NESEmulator/cpu6502.cpp) are study references rather than unquestionable solutions. We will derive their contracts independently and only later integrate the corrected pieces into the growing machine.

#### Start with sixteen bytes, not with a C++ class

A legacy iNES 1.0 cartridge image begins with a sixteen-byte header. Its first four bytes are 4E 45 53 1A in hexadecimal: N, E, S, followed by byte 0x1A. That signature identifies the declared file format. Header byte 4 counts program-ROM banks of 16,384 bytes each, while byte 5 counts character-ROM banks of 8,192 bytes each. A count acquires a size only once its unit of measurement has been specified. Program ROM supplies instructions and data reachable through cartridge mapping; character ROM commonly supplies tile graphics accessible to the picture processing unit.

Header byte 6 contains several independent meanings: bit 0 specifies a basic mirroring convention, bit 1 indicates battery-backed memory, bit 2 announces an optional 512-byte trainer, bit 3 specifies four-screen video memory, and bits 4–7 carry the low four bits of the mapper identifier. Byte 7 contains the high four mapper bits at positions 4–7. The mapper number is

$$
m=(h_6\gg4)\mathbin{|}(h_7\mathbin{\&}0xF0),
$$

where h_i is header byte i. The right shift moves the upper nibble of h6 into bits 0–3; the AND discards unrelated low bits of h7; the OR joins the two portions. For h6=0x17 and h7=0x20, the mapper ID is 0x21. The same byte 6 also retains the trainer, battery and mirroring flags. Extracting one field must not destroy the others.

The optional trainer immediately follows the header. If t is the trainer flag, p the PRG bank count, and c the CHR bank count, the locations of the two payload regions are

$$
\begin{aligned}
o_{\mathrm{PRG}} &= 16+(t?512:0),\\
s_{\mathrm{PRG}} &= 16384p,\\
o_{\mathrm{CHR}} &= o_{\mathrm{PRG}}+s_{\mathrm{PRG}},\\
s_{\mathrm{CHR}} &= 8192c.
\end{aligned}
$$

Offsets count bytes from zero and the end of a region is exclusive. In the one-PRG, two-CHR, trainer-present case, the PRG bytes begin at offset 528 and occupy 16,384 bytes. The CHR bytes then begin at 16,912 and occupy another 16,384 bytes, giving 33,296 bytes as the minimum total size. Derive those quantities yourself before running the reference program. A truncated final CHR byte must be rejected; any attempt to quietly load it is a failed contract.

A zero CHR-ROM bank count normally indicates CHR RAM provided by the emulated cartridge hardware, not an 8 KiB region that must be read from disk. Allocating runtime RAM is not equivalent to receiving ROM file bytes. Later mapper-specific lessons will define the exact amount and behavior of that RAM. This distinction between external encoding and live object state is one of the chapter's most important lessons.

#### Build an explicit C++23 trust boundary

A tempting implementation declares a C++ header struct and reads file bytes straight into its object representation. Doing so conflates the on-disk schema with compiler-specific object layout and still leaves the short-read problem. The learner's first parser instead reads format fields at their declared offsets, explicitly checks the header, and verifies every payload region before a mapper is created.

The parser accepts `std::span<const std::uint8_t>`: a bounded **borrowed view** into externally owned bytes. The original byte buffer must remain alive and must not be invalidated while inspection occurs. The parser returns `std::expected<Layout, ParseError>`. A successful layout names verified sizes, offsets and flags; a failure names a rejected condition. `std::expected` belongs to C++23, and the same principle will recur when we implement loaders, asset caches and streaming systems later in the series.

The dangerous operation is not the bit shift but the **bounds proof**. Before reading a region of length L starting at offset O, first establish O <= input-size and then prove L <= input-size - O. Checking O + L <= input-size without guarding overflow is not a generally sound strategy when attacker-controlled sizes can become large. Once the PRG region has been validated, it is safe to compute the CHR start and validate the next region. The complete reference implementation lives in [tools/labs/ines_header_cpp23_lab.cpp](../../tools/labs/ines_header_cpp23_lab.cpp).

Here is the small, central part worth tracing by hand:

```cpp
// The offset has already been proved to fall within the input.
// Test the remaining capacity using subtraction.
if (image.size() - offset < prg_size) {
    return std::unexpected(ParseError::truncated_prg);
}

const auto chr_offset = offset + prg_size;
// We reach this point only after proving the entire PRG region fits.
if (image.size() - chr_offset < chr_size) {
    return std::unexpected(ParseError::truncated_chr);
}
```

A span cannot validate a file format on its own; it merely carries size and ownership assumptions that must still be respected. A typed error cannot prove that the list of error conditions is complete; that requires derivation, tests and an explicit scope of supported formats.

We deliberately reject headers declaring NES 2.0. That format reinterprets size and mapper fields, so treating it silently as iNES 1.0 would be incorrect. Older files may also have ambiguous reserved header bytes. A robust future loader needs an explicit compatibility policy rather than guessing that every historical image uses one clean convention.

#### From storage bytes to CPU-visible memory

The cartridge file is **not** the NES CPU's memory map. The console's CPU uses 16-bit addresses, while the base system has 2 KiB of internal RAM repeated through address 0x0000–0x1FFF. The index within that physical RAM is

$$
\text{ramIndex}=\text{cpuAddress}\mathbin{\&}0x07FF.
$$

There are 2^11=2048 possible low-bit combinations. Thus addresses 0x0001, 0x0801, 0x1001 and 0x1801 refer to the same physical RAM byte. The mask belongs specifically to this RAM region, not to every CPU, cartridge or PPU access. The PPU register bank has different mirroring, and cartridge addresses are interpreted through mapper rules. This is why a correct emulator needs a bus and independently modeled devices rather than a single flat byte array.

The project sequence must therefore be: validate the header and payload, identify a supported mapper, establish owned cartridge storage, connect the mapper to the CPU/PPU bus, and only then run instructions. The lifetime, format and address-mapping contracts have distinct owners. Later chapters make the boundary between borrowed buffers and long-lived cartridge storage explicit.

#### Study the real code's weaknesses, not just its features

The currently inspected `NESEmulator/Cartridge.cpp` reads the local header without checking the extraction length; it reads PRG and CHR payloads without verifying that the stated bytes were obtained; the CHR-RAM branch also attempts an on-disk CHR read; and the mapper switch lacks a general unsupported-mapper failure yet later marks the cartridge valid. This creates the possibility of a valid-looking object without a usable mapper. The corrective lesson is not to replace the whole emulator blindly, but to isolate and test the trust boundary before making any production change.

The standalone laboratory constructs only synthetic, zero-filled cartridge images and does not rely on commercial ROMs. Eleven fixed cases cover a normal cartridge, trainer/mapper flags, CHR RAM, bad signature, short header, truncated trainer, truncated PRG, truncated CHR, rejected NES 2.0, zero PRG banks, and four-screen mode. Compile-time assertions also check address mirroring. These successes do **not** establish complete compatibility, instruction timing, sound emulation or frame correctness.

Expand the exercise once the fixed cases are passing: generate a range of valid bank counts and check that the reported sizes are correct multiples of the bank sizes; truncate each generated image one byte before a required region ends and demand a typed failure; vary independent flag bits to prove that extracting a mapper does not alter mirroring or battery semantics; and enable ASan/UBSan where supported. Finally, explain why parsing and constructing the cartridge must be separate operations and how `std::expected` changes the caller's failure-handling obligation.

**A reconstruction gate, not a page-count gate.** The learner completes NES-01 when they can derive the header layout without copying code, explain each mask and offset, implement the parser in C++23, reproduce the synthetic cases, describe the borrowed-buffer lifetime, and demonstrate that short reads do not create usable runtime cartridge state. The next stages add RAM/bus and ownership (NES-02), a traceable 6502 CPU (NES-03), interrupt and cycle evidence (NES-04), graphics (NES-05), audio and controllers (NES-06), mapper compatibility (NES-07), and system-level regression/performance evidence (NES-08). **These stages extend the same evolving machine.**

**Reference and verification limits.** Compare the file and memory rules with [NESdev iNES](https://www.nesdev.org/wiki/INES), [NESdev NES 2.0](https://www.nesdev.org/wiki/NES_2.0), and [NESdev mirroring](https://www.nesdev.org/wiki/Mirroring). Passing the local parser tests is not proof that the complete emulator works or that every historical board is supported.
