### NES-09M — The scheduler can order a texture upload without making one byte visible

Our NES project has reached a boundary where a schedule can be perfectly valid and a device operation can still be invalid. The previous chapter created a directed acyclic graph for cartridge validation, CPU instruction execution, RGBA8 texture preparation and hypothetical transfer, compute and graphics stages. Kahn's algorithm gave us a topological order; hazard analysis supplied read-after-write, write-after-read and write-after-write edges; generation-aware asset handles prevented old CPU identities from being mistaken for new ones. Yet **an edge in a host-side graph is not a Vulkan memory dependency, a Metal command synchronization primitive, a completed upload, or a proof that a texture's pixels have ever been initialized**.

We will now give that missing contract an executable form. The new `tools/labs/nes_course/gpu_memory_contract_oracle.hpp` is a carefully scoped C++23 **CPU reference model**, not a graphics backend. Its `MemoryContractOracle` tracks virtual allocations, byte-range initialization, conceptual producer and consumer visibility, resource roles, layout intent and simulated completion tickets. The companion executable `tools/labs/nes_gpu_memory_contract_cpp23_lab.cpp` imports a real TXR4 texture through our existing `Spec<TextureTag>` and `GenerationalAssetRegistry`, reads the Pass 08 DAG's prerequisites, and walks a host-written staging source through conceptual transfer, compute and graphics use. Every successful byte comparison takes place in ordinary CPU memory. That is exactly why the project can expose invalid assumptions before we pretend to compile and dispatch native shader work.

This is an additive companion to Chapter 09's existing material, which already covers device/global memory, unified memory, caches, coalescing, divergence, wave/subgroup operations, atomics, memory ordering, threadgroup synchronization, multi-dispatch scans, general compute, radix sorting and computational workload structure. We preserve that narrative. The new passage fits **after the original memory, divergence and ordering section and before the existing “GENERAL COMPUTE & PARALLEL ALGORITHMS” section**, where a complete concrete example lets the reader connect the two without restating them as detached definitions.

#### A resource has several facts that no single handle can express

Imagine our texture loader has returned a typed handle to a 2×1 RGBA8 image. Its decoded CPU payload contains eight bytes. The handle proves that the current registry contains an asset of the intended type and generation **at the moment of lookup**. It does not prove that a GPU allocation exists, how many bytes that allocation contains, whether a copy operation was submitted, whether its contents are initialized, whether writes are visible to a shader, or whether a queued draw has finished using the allocation.

These questions belong to different systems. Let a conceptual device resource be described by

$$
R = (I, B, O, S, A, L, Q, V, T).
$$

Here $I$ is a logical resource identity, $B$ the allocation base offset, $O$ the logical byte extent, $S$ the reserved storage extent where relevant, $A$ the required alignment, $L$ the current intended layout or use classification, $Q$ the current execution-role owner in our *simplified oracle*, $V$ the per-byte visibility state for modeled consumers, and $T$ the last outstanding completion ticket associated with use of the allocation. Some of these fields would be represented very differently by a real backend. A Vulkan image has subresource ranges, layouts and queue-family rules; a Metal texture has distinct storage, residency and command synchronization contracts. We do **not** claim that this tuple is the literal native handle representation for either API.

The key architectural lesson is that **a resource name is not an initialized resource**. A graphics API's object handle may be valid while the contents or the access path are not. Even an allocation that was physically zero-filled by an implementation cannot generally be treated as initialized application data unless the relevant API contract guarantees that. The CPU oracle therefore constructs byte storage but marks every byte *uninitialized* until an explicit successful write occurs. Its tests reject a read of an untouched byte even though the underlying `std::vector` happened to be initialized to zero for the convenience of the host model.

Likewise, a successful decode does not prove that a native GPU buffer or image can represent the source format. The earlier TXR4 teaching codec specifies width, height and RGBA8 payload; the real GPU path must separately choose a supported texture format, allocate memory with correct constraints, decide on row pitches and image layouts, preserve source lifetime through upload, and set up the relevant synchronization before sampling. CPU ownership, device storage and shader readability are three different guarantees.

#### Checked virtual allocation teaches what an alignment actually promises

A resource allocator must produce a start offset that satisfies its chosen alignment. If the current virtual arena cursor is $c$ and the alignment $a$ is a positive power of two, the usual bitwise round-up is

$$
\operatorname{alignUp}(c,a)=
(c+a-1)\mathbin{\&}\neg(a-1).
$$

The formula is valid for that power-of-two alignment contract **only if the addition $c+a-1$ is representable**. It is unsafe to apply it blindly to an untrusted size or a cursor close to `SIZE_MAX`. Our oracle checks both that $a$ is a positive power of two and that the addition cannot overflow before performing the bitmask. It then verifies the new offset and requested size fit within its declared arena byte budget using subtraction-based bounds checking rather than calculating a potentially overflowing end address first.

For the small test, the first eight-byte staging allocation starts at offset 0 with alignment 16. A second eight-byte texture allocation, aligned to 64, starts at offset 64 rather than 8. A third eight-byte compute output, also aligned to 64, begins at 128. The next cursor is 136, even though only 24 payload bytes are in use. The skipped regions are alignment gaps. This distinction between **payload size, allocated range and arena high-water mark** matters when evaluating fragmentation, upload ring capacity and transient GPU memory budgets.

The experiment also rejects zero-length allocations, a non-power-of-two alignment, duplicate resource identities and a request that would exceed the arena. A rejected operation must not advance the cursor. The implementation builds its per-resource metadata and byte vectors before publishing a new map record and committing the virtual cursor. Standard host `std::bad_alloc` can still propagate when temporary allocations fail, but the model does not claim that an allocation that never succeeded published a resource. Allocation failures are not equivalent to invalid source files; the caller must preserve that distinction.

The allocator is intentionally **monotonic and virtual**. It reserves distinct offsets for its teaching records but stores the actual bytes in separate host vectors. It does not create a Vulkan `VkDeviceMemory` allocation, a Metal heap, placed resources, sparse bindings or a physical GPU address. Retiring a record does not reuse its old offset. Consequently this laboratory does not establish transient-memory alias safety or prove that an allocation could be rebound while queued commands remain active. Those are important separate problems for later graphics chapters.

#### A byte-range check is stronger than an allocation-size check

Suppose an eight-byte resource has only its first two bytes initialized. A read of bytes 0 and 1 is permitted by our host oracle. A read of bytes 0 through 2 is rejected because byte 2 has not been written. The allocation is large enough for the requested read in both cases; **bounds validity and initialization validity are not the same property**.

For an access of length $\ell$ beginning at offset $o$ in an allocation of size $n$, the safe bounds condition is

$$
0\le o\le n \quad\land\quad 0\le\ell\le n-o.
$$

This formulation avoids computing $o+\ell$ until the subtraction has already shown that it fits. The test writes two bytes, confirms the exact read result, attempts a two-byte write at offset seven, and checks that the latter fails without altering the originally written values. A zero-filled host vector or a valid resource handle is never accepted as a substitute for this proof.

Real GPU resources complicate the unit of the check. A buffer uses byte offsets; an image's shader-facing view uses pixels, mip levels, array layers and format blocks. Compressed formats operate on blocks, and the physical memory layout of a tiled image is not generally a simple row-major sequence. Treating a compressed 4×4 texel block as if it consisted of ordinary per-pixel RGBA8 bytes would be a representation error. Our format is deliberately **uncompressed eight-byte CPU test data**, and all its access ranges are byte intervals.

The oracle's range bookkeeping is useful but not a complete GPU subresource model. Its layout and conceptual role ownership apply to the **whole allocation**, and its transitions require a whole-allocation range when they change either. Byte-range visibility exists inside that simplified state. A production backend must add precise buffer intervals, image aspect/mip/layer ranges and real queue/device ownership. We should not silently turn “the teaching model checked eight bytes” into “the renderer correctly synchronized all subresources.”

#### Execution order and memory visibility are separate claims

The Pass 08 task graph may require task A to precede task B. But on a parallel device, two commands can have a defined execution relationship without all the relevant producer writes necessarily being available to the consuming memory domain under the required API scopes. Synchronization must establish the appropriate **memory** dependency in addition to execution constraints when the access hazard demands it. Vulkan's synchronization model makes this distinction explicit. A well-scoped memory dependency carries producer and consumer stage/access semantics, with availability and visibility operations as specified by the Vulkan memory model; queue-family transfers and image layout transitions add further conditions where applicable. 

Our oracle illustrates the consequence using *conceptual execution roles*: `host`, `gpu_transfer`, `gpu_compute` and `gpu_graphics`. These values come from the same Pass 08 work-graph `Domain` enumeration; they are not literal Vulkan pipeline stages or Metal queue objects. An eight-byte source buffer is written by the host role. Attempting to read it immediately through the transfer role fails, even though the memory bytes exist and the DAG contains a prerequisite edge. The host must first record the oracle's explicit visibility/role transition from host to transfer for the entire source buffer.

The destination starts uninitialized and in an `undefined` layout classification. The transfer role cannot read it as if it were a source. Instead the oracle transitions it into `transfer_destination`, checks the source's transfer-readable state, and performs a CPU copy into the destination's stored byte vector. Only then can a later transfer→compute visibility/layout transition make that byte vector available to the conceptual compute consumer. Finally the compute role produces a separate output and the compute→graphics transition makes that output readable under the shader-read-only classification.

This sequence is a **counterexample factory** for missing contracts. Omitting the host→transfer transition rejects the read. Using the wrong source role rejects a barrier. Attempting to read the output from graphics before its compute→graphics transition rejects the access. Passing the transfer-destination layout as though it were shader-read-only is likewise a typed layout error. The permitted path yields exact bytes equal to the original registered texture and a deterministic transformed output produced by ordinary CPU arithmetic.

The oracle does not execute native cache flushes, invalidate caches, invoke `vkCmdPipelineBarrier2`, signal `MTLEvent` or run a compute kernel. Its “barrier” operation *assigns a visibility fact inside the host reference model*. That is useful for understanding an abstract contract; it is not an interchangeable implementation of any actual API's synchronization. The exact backend implementation must be derived from the stages, accesses, queue family, layout, residency and operations involved.

#### The same phrase “ownership” names different responsibilities

In previous chapters, **C++ ownership** meant that a vector or smart pointer controlled the lifetime of a host object and could destroy it when its owner died. Our generational asset registry used **logical owner namespaces** to distinguish resources from different stores. Vulkan's **queue-family ownership** is a separate concept governed by sharing mode and queue-family transfer rules. Metal's resource management and synchronization use their own device and command structures. Those three meanings cannot be substituted for one another.

The oracle's `owner` field is deliberately a simplified **execution-role permission**. Transferring it from `gpu_transfer` to `gpu_compute` means only that our model will now accept the compute role for the specified resource. It does not claim that the physical GPU has distinct transfer and compute queues, or that the correct Vulkan release/acquire ownership transfer has been performed. Many real devices allow multiple stages on the same queue family; synchronization scopes do not automatically correspond one-to-one to ownership changes.

This is why the Pass 08 graph's GPU-edge list is titled `gpu_edges_requiring_backend_review` rather than `ready_barriers`. An edge touching two GPU-domain tasks is a prompt to analyze a concrete hazard. Some WAR cases require execution ordering without a producer-write visibility operation. Some RAW/WAW hazards require memory availability and visibility. Some cases require image layout changes, and some may already be covered by an appropriate existing dependency. A planner that blindly emits one identical barrier for every edge will likely be both inefficient and wrong. Khronos's current synchronization examples distinguish WAR ordering from data-visibility requirements. 

The Metal 4 command model is another reason not to reuse outdated API assumptions. Apple's current documentation distinguishes synchronization within an `MTL4CommandQueue` from cross-queue event coordination; an event or shared event may be needed to connect particular queues. Older Metal command-buffer and fence examples cannot be copied uncritically into the newer model. We also must not assume that shared Apple-silicon DRAM makes all resource access automatically coherent at every command boundary. Refer to the supported API generation and declared usage rather than the physical marketing label “unified memory.” 

#### A visible value has a version in the model

To make the visibility distinction testable, each initialized byte in the oracle carries a write-epoch number. When a role writes a byte, that byte receives a newer epoch. Its current writer role can observe the newly written value; other roles must receive a modeled visibility transition before their read can be accepted. The consumer checks that its visible epoch for every requested initialized byte is at least the byte's current write epoch.

This is not a cache simulator. An epoch is a logical token indicating which writes the reference model allows a particular consumer to observe, not a representation of a cache line state, real memory-order relation or hardware transaction sequence. Nevertheless, it rules out an important erroneous argument: “I can inspect the bytes in a debugger, therefore a shader is allowed to sample them.” The host buffer's actual payload and the consumer's visibility eligibility are separate values.

The oracle's partial-range test checks initialization, while role/layout-changing transitions currently require a whole allocation. Such a restriction is intentional for an introductory reference model: it cannot accidentally claim that a buffer-range dependency also transitions an image subresource's layout in a real API. A later version can keep this byte-epoch oracle while adding subresource-specific geometry and accurate backend state transitions.

A further limitation is that the model's barriers immediately establish their declared state. Real asynchronous execution and queue submission do not work by making a C++ enum assignment. A CPU submit call may return while a GPU task is still pending, and the availability or visibility guarantees of a particular synchronization command depend on how it is recorded and executed. Our oracle validates an **intended before/after state transition**; the native backend must demonstrate the real mechanism and its completion conditions.

#### Logical invalidation does not authorize immediate GPU deallocation

Now consider a common editor action. The user deletes an RGBA8 texture from the generational registry while a hypothetical graphics command is still scheduled to use a corresponding GPU resource. The registry correctly marks the old handle stale. This prevents future CPU-side lookups from mistaking the old asset for another occupant of its slot. But the native GPU allocation may still be read by already-submitted work. Invalidating the CPU handle is therefore necessary for logical correctness and insufficient for physical resource lifetime.

Our reference model separates these events. The GPU resource can be marked as having a conceptual **in-flight use ticket**. An attempt to retire it before the ticket is observed complete returns `completion_pending` and leaves the resource live. Observing completion through a smaller ticket does not release it. Once the simulated completed counter reaches the ticket, retirement is permitted. The allocation becomes a permanent tombstone under its original logical identity, refusing subsequent reads or a second allocation with the same identity.

The tests use ticket seven. Completion through six is insufficient; through seven is sufficient. This simple monotonic rule is analogous to tracking a submission's point of completion, but the model has **no actual fence or event attached to hardware**. The caller could lie to the model by reporting a completion that never happened. A real backend must obtain the completion observation from its actual queue/device mechanism and must specify which uses a ticket covers. A single global numeric ticket also does not automatically encode unordered, independent hardware queues; a multi-queue renderer requires a real completion relation, possibly a vector of queue timelines or explicit cross-queue dependencies.

The virtual arena intentionally does not recycle retired offsets. A newer generation can allocate a different region, but that teaches only identity separation, not safe transient aliasing. A production transient allocator that reuses physical ranges must prove the old resource's GPU uses are complete and that new uses satisfy all relevant aliasing, synchronization and layout requirements. A frame graph that knows two logical lifetimes do not overlap on paper must still account for actual device execution and outstanding submissions.

#### Coalescing is a workload property, not a declaration on a buffer

The existing chapter explains that adjacent lanes accessing adjacent addresses often achieve better memory-transaction efficiency than lanes performing sparse gathers. Rather than claiming a specific memory bandwidth improvement on unseen hardware, we add a deliberately simplified **transaction-segment proxy** to the CPU laboratory.

For eight hypothetical lanes, suppose each reads a four-byte item beginning at addresses

$$
0,\ 4,\ 8,\ 12,\ 16,\ 20,\ 24,\ 28.
$$

If our *illustrative* segment width is 32 bytes, these start addresses all belong to the same aligned 32-byte region. By contrast, start addresses $0,32,64,\ldots,224$ occupy eight distinct regions. The helper computes unique aligned segments for chosen **start addresses**, showing one versus eight. The test intentionally rejects zero or non-power-of-two segment sizes in this model.

These counts are **not measured GPU memory transactions**. A real access can straddle a transaction boundary, a cache can satisfy requests from earlier work, transaction granularity can differ by GPU and access type, and a subgroup may have fewer or more lanes. Coalescing of actual memory operations depends on operation width, alignment, active-lane mask, architecture and cache state. Our proxy is valuable as a simple geometry-of-addresses exercise but is not a performance claim about Apple, NVIDIA or AMD hardware.

There is a deeper connection to our previous mesh and texture loaders. A texture represented as tightly packed RGBA8 bytes may be efficiently copied in contiguous runs on the CPU, but a shader texture sample uses the GPU's texture addressing and filtering system. We should not assume that manual linear-buffer fetches replicate texture-cache behavior. Similarly, mesh vertex gathering may be limited by indexed access locality even when its buffer is contiguous. Resource type and access pattern jointly determine the relevant memory question.

#### Divergence can invalidate a barrier even when every memory address is in range

A conditional branch may cause lanes of one subgroup or workgroup to follow different paths. Sometimes divergence only affects performance: different lanes execute different instructions or have different active masks, and the hardware schedule must accommodate them. At a synchronization point, however, the question can be one of **correctness**: do all intended workgroup participants reach the barrier as required by the shading language and operation's uniformity rules?

Consider an educational workgroup of eight invocations. If all eight execute a required workgroup barrier, the participation pattern is structurally uniform. If only the first two execute it while the remaining six skip it, the program cannot assume that the barrier properly coordinates shared-memory writes among the entire workgroup. Depending on the exact shader language and control-flow rules, nonuniform barriers can be invalid or yield behavior that cannot satisfy the intended data-sharing contract.

Our `barrier_participation` helper classifies the simple cases as **everybody**, **nobody**, or **divergent**. The test passes masks of eight ones, two ones plus six zeros, and eight zeros. This is not a device-level uniform-control-flow verifier. More subtle shaders have nested loops, subgroup masks, early exits and nontrivial control-flow reconvergence, and the legality of specific barrier operations depends on language/API rules. The helper is a targeted reminder that a true synchronization obligation cannot be fulfilled merely by placing a function call under a condition where only some intended participants execute it.

For a partially filled tile, the safe general teaching pattern is to assign neutral values to out-of-range elements while keeping the required participants on the common barrier path. For example, a matrix multiplication tile may load zero for invalid source coordinates but still participate in the threadgroup synchronization that protects the shared-memory tile. Once the tile is consumed, a second barrier may be needed before any lane overwrites values that slower consumers still need. This is **two different ordering obligations**—complete production before consumption, then complete consumption before reuse.

A workgroup barrier is not a global device barrier across arbitrary independently scheduled groups. A multi-block prefix scan requires phase decomposition, such as block-local scan, scan of block totals and offset addition, with actual cross-dispatch or other valid global dependencies. A host-side planner can specify those phases; the GPU backend must execute and synchronize them. No amount of source-level wishful thinking turns one workgroup rendezvous into device-wide completion.

#### Atomics protect individual operations; publication requires a memory-order story

The lesson's other experimental component uses actual C++ host threads, but **not GPU shader threads**. This distinction is important: C++ `std::atomic` and GPU shader atomics have related conceptual problems, yet their exact scopes, address spaces, supported orders, guarantees and hardware mapping are different.

Suppose one host thread writes a normal non-atomic payload and then publishes a flag. Another thread waits for the flag before reading that payload. If the threads coordinate incorrectly, the read may race with the write or observe an unintended state. Simply changing the flag to an atomic variable with relaxed ordering is not sufficient to create a *synchronizes-with* relationship that publishes the surrounding non-atomic payload.

Our test uses a **release/acquire handshake** in both directions. The producer waits until the flag indicates the previous message has been consumed, writes the next ordinary payload, and performs a release store to publish the ready state. The consumer performs an acquire load that observes the ready state, reads the payload, checks its expected value, and performs a release store to acknowledge consumption. The producer's later acquire load of the acknowledgment establishes the next iteration's ordering so it does not overwrite the payload while the consumer is still using it.

Formally, a release operation on an atomic object synchronizes with an acquire operation that reads the value from the relevant release sequence under the language rules. The producer's payload write is sequenced before release; the consumer's payload read is sequenced after acquire. Thus the write **happens before** the read, allowing the payload to remain non-atomic in this properly synchronized single-slot message exchange. The acknowledgment creates the converse happens-before relation needed to safely reuse the slot.

The executable runs 512 such handshakes and checks that every payload equals its expected sequence number. This is runtime evidence for the implemented protocol on the tested host, not a substitute for the standard's memory-model proof. The reasoning is needed even if a particular x86-64 run “never fails” under a weaker design. We deliberately do not run an unsynchronized non-atomic counterexample: executing a data race to demonstrate that it is dangerous can itself make the test have undefined behavior.

The host handshake's flag is analogous to publication metadata, not to a GPU render-graph barrier. C++ `memory_order_release` and `memory_order_acquire` do not automatically substitute for Vulkan `srcStageMask`/`dstStageMask` or the visibility mechanisms required by Metal shaders and command queues. Nor does a GPU atomic increment guarantee that another thread sees arbitrary adjacent payload bytes at the desired time. One must separately establish the memory scope and synchronization that covers those payload writes.

#### The NES texture pipeline connects the two sides of the boundary

Our eight-byte texture starts as a legitimate owned `TextureRgba8` imported through the generational registry. The source file can be discarded. The testing code then gives the staging source and device texture **different resource kinds** even though their other identity fields refer to the same logical texture generation; they are different allocations with different access roles.

The Pass 08 graph describes four operations: host pixel preparation, conceptual transfer, conceptual compute and conceptual graphics read. Its edges include the intended resource producer/consumer constraints, but the graph returns only task order and GPU review obligations. The Pass 09 oracle then performs the stronger **memory eligibility** steps: allocate, initialize, transition staging to transfer-source, transition destination to transfer-destination, copy, transition destination to compute-readable, generate output under compute's general-write classification, and make the output graphics-readable.

For clarity, the host model's compute operation is simply a bytewise XOR with `0xFF`, not a shader or filter. It is chosen because its expected output can be computed independently by hand. From the first source byte `0x12` the model produces `0xED`; from the last source byte `0x44` it produces `0xBB`. The final consumer verifies those bytes after the modeled visibility transition. If we replaced that phase with a real GPU kernel, we would need its binary/shader source, device format/storage rules, command dispatch and synchronization. The CPU oracle only supplies reference values and a state machine against which those new operations can be checked.

The lifetime test then deliberately erases the registry texture handle. The logical asset is no longer resolvable, but the virtual device allocation still exists. A completion ticket prevents its retirement until the specified conceptual use is complete. The test demonstrates why **logical deletion**, **device synchronization**, and **physical release** are distinct events. Our earlier generic asset and registry work was necessary to ask that question accurately; simply teaching queue semaphores without a meaningful resource identity would have hidden the bug.

#### What is proved by tests, what is still not tested

The new C++23 test executable covers invalid allocation size and alignment, aligned virtual offset arithmetic, duplicate identity, monotonic byte budgets, uninitialized and partially initialized ranges, out-of-bounds writes, rejected partial role transitions, wrong-domain reads, incorrect source roles, correct staged byte transfer, computed-byte comparison, graphics visibility, stale logical asset handles, pending/completed ticket retirement, identity tombstones, theoretical segment counts and workgroup barrier-participation masks. The final host-thread experiment tests a real release/acquire synchronization protocol for 512 payload publications.

These cases constrain the reference implementation's behavior. They **do not** measure cache throughput, simulate actual warp/wave divergence, compile GPU shaders, establish Vulkan queue-family transfers, validate Metal 4 command synchronization, allocate device memory, observe a real GPU timestamp, or certify that the user's present Kairo or Maveb projects implement these exact rules. The chapter's broader GPU material remains intact; this project is one rigorous, portable prerequisite for a later hardware-backed implementation.

A second explicit bound concerns source truth. The current chapter contains project-derived commentary about Kairo and Maveb's GPU kernels and multi-dispatch scans. Those statements may describe previously supplied snapshots. We have not silently promoted them into freshly audited present-day repository facts. When integrating the real code later, inspect the exact renderer and compute implementations, determine their backend/API versions and verify the relevant barrier, layout and memory rules against those actual source revisions. The backend's memory-model requirements are determined by what commands genuinely execute, not by the prose alone.

#### Reconstruct the experiment and attack its assumptions

A learner should first derive the allocation-alignment formula and prove which overflow checks are needed before allocating anything. Then construct an eight-byte virtual resource, mark only a two-byte prefix initialized, and show why the allocation's existence alone cannot validate a three-byte read. Build separate source and destination identities for the same logical texture. Deliberately omit the host→transfer transition and predict the typed rejection before reading the output. Add the transition, copy, then attempt compute use without a transfer→compute transition and predict the second rejection.

Next, explicitly model a completion relation and demonstrate that CPU registry erasure does not release an in-flight native allocation. Make the old handle stale and verify it remains stale after a new generation is created. Explain why the monotonically allocated virtual offset is intentionally *not* a real aliasing allocator. Build the 32-byte segment proxy and calculate the difference between contiguous and strided starts, then state why those counts cannot stand in for a GPU benchmark.

For the concurrency component, draw the host producer/consumer sequence including each payload access, the release publication, acquire observation, acknowledgment release and the producer's following acquire. State the happens-before edges and why a plain non-atomic payload is legal under those edges. Contrast that with a GPU command writer and shader consumer: specify what extra device stage/access, scope, layout or event conditions are needed instead of copying the C++ flag literally.

Finally, write a backend-specific test plan for an actual Vulkan or Metal texture upload. The plan must name device and resource creation, physical memory/storage constraints, source bytes and row pitches, queue and command recording, upload execution, synchronization availability/visibility, shader-readable state, validation layers/API diagnostics, expected pixel outputs, completion observation and resource retirement. It should also name the negative tests: omit one required dependency, use the wrong layout or access scope, retire before completion, or create a resource with an invalid size. Those negative experiments belong in a controlled testing environment, not in an application shipping incorrect synchronization.

A correct learner can now explain why an eight-byte buffer can be allocated but unreadable, why an initialized source can be invisible to a later consumer, why a correct DAG order cannot replace device synchronization, why a global multi-block scan cannot use only an intra-workgroup barrier, why release/acquire publishes host payload while relaxed atomicity alone may not, and why deleting a generational handle does not prove that the GPU is finished with its allocation.
