### GPU-14F — A Vulkan frame is not finished when you call submit

In the previous chapter we learned to open an actual Vulkan instance, enumerate physical devices, choose a compatible queue, create a buffer, query its true memory requirements, and bind physical backing memory. The cross-project GPU-13D executable deliberately separated **synthetic capability policy** from an opt-in real Vulkan device probe. A suitable resource and a usable queue are only the beginning, however. The moment a command refers to that resource, the engine inherits new responsibilities: it must tell the device what to do, order the relevant reads and writes, determine when the work has ended, preserve the resource until then, and release the right storage generation after every remaining user is finished.

We will not turn this into a thirteenth variation of a tiny NES texture. The primary target here is **KairoRenderer's actual Vulkan per-frame architecture**, with **Maveb's actual Metal frame allocator and completion handlers** as a contrasting design. The same rules also apply when the resources contain millions of Gaussian attributes, a GPU-generated collision-pair list, camera depth buffers, or eye-tracking/foveation data. Those aren't arbitrary “applications” tacked onto a list: their lifetimes, resource aliasing patterns and correctness criteria genuinely differ. A texture presented by a swapchain remains involved in the window-system integration protocol after some graphics work is finished; a headless collision-pair buffer does not. A Maveb upload allocation can be owned by a per-frame arena even when its underlying Metal command buffer lives on a different API object's timeline.

This is **Pass 14, GPU-14F**. Its new source is `tools/labs/gpu_course/submission_retirement.hpp`, a portable C++23 *reference state machine*, and `tools/labs/gpu_submit_retire_cpp23_lab.cpp`, a collection of adversarial tests. They are joined by `tools/labs/gpu_course/native_vulkan_submit_probe.cpp`, an **opt-in native Vulkan execution witness**. The native path records `vkCmdFillBuffer` on a real buffer, enqueues it through `vkQueueSubmit`, waits for a real fence, maps host-coherent memory, and compares every resulting word against an independent CPU expectation. This is no longer only a simulated device-creation path—if actually run with a compatible Vulkan runtime it can prove a very small GPU queue command executed correctly. It is emphatically **not** a full shader, swapchain, graphics, synchronization2, multiqueue or timing benchmark.

We inspected actual files in KairoRenderer and Maveb from their main branches, not just their project descriptions. The relevant source includes KairoRenderer's `VulkanCommand.cppm`, `VulkanSync.cppm`, and `VulkanRenderer.cppm`, and Maveb's `engine/metal/src/Renderer.cpp` and `FrameContext.cpp`. #### A frame passes through several different ownership systems

Begin with a windowed renderer's typical trace:

```text
CPU frame slot chosen
    → wait on the prior work's completion fence
    → acquire a swapchain image (image index may differ from slot)
    → reset/reuse the frame's command pool and begin recording
    → encode rendering, transfer or compute operations
    → finalize the command buffer
    → reset the fence that will be signaled by *this* submit
    → queue submit (wait on image acquisition, signal render completion)
    → enqueue presentation waiting on the render-complete semaphore
    → observe GPU command completion using the proper fence/timeline
    → retire per-frame allocations, only after all GPU and CPU users finish
    → separately observe that WSI/presentation has released image-specific uses
    → safely reuse the swapchain image and relevant binary semaphore
```

Some of these operations can be reordered safely within a correct engine—for example, the actual fence reset can be moved closer to a submission, and presenting is usually queued before the CPU waits for the graphics completion. The point is that **each arrow needs a reason**. Merely creating a fence or calling `vkQueuePresentKHR` does not signal that every use of the swapchain image, command buffer, or upload allocation has ended.

Three identifiers must not be merged. The CPU **frame slot** is an index into an arena containing command buffers, staging allocations and related state. The **swapchain image index** is selected by the window-system acquire path and may be unrelated to the CPU slot. The **submission ticket** or fence/timeline value identifies one particular batch of GPU work. In a correctly designed system one may reuse the frame slot while some previously presented image remains under separate WSI ownership; or a swapchain image can become available for a later frame on a different CPU slot. Conflating indices can lead to reusing a binary semaphore while an earlier presentation may still be waiting on it.

Our portable model explicitly has **two CPU frame slots and three presentation images** in the first test. It selects frame slot zero and image index two, proving that their equality is not a legal assumption. The model distinguishes frame generation, swapchain generation and resource generation so a reused slot cannot accidentally accept an old notification. The source's policy is more conservative than an optimized renderer but makes the correct ownership boundary inspectable.

#### A fence and a semaphore are not interchangeable

A Vulkan fence is a host-visible synchronization object associated with work submitted to a queue. A host wait on the relevant signaled fence can establish that the associated queue work completed, subject to the specification's ordering and memory-access rules. A semaphore primarily coordinates work between queue operations, including binary and timeline variants. The two have different allowed uses, signaling behaviors and reuse requirements. A semaphore wait on a graphics queue can establish device-side order without blocking the CPU. An unsignaled fence doesn't become signaled merely because the application decides that enough time has passed.

A **binary semaphore** represents a signaling/waiting handshake rather than a durable count of completed frames. It must not be signaled a second time while a previous unconsumed signal would make the operation invalid. With swapchains, presentation can wait on a render-finished binary semaphore even after the frame's graphics submission fence has been signaled. Therefore a per-frame graphics fence alone is generally insufficient evidence that the presentation engine has finished waiting on its associated binary semaphore. Choosing render-finished semaphores per **swapchain image**, as Kairo's `VulkanFrameSync` visibly does, is one strategy to connect lifetime to the image's reuse pattern. The actual correctness also depends on handling acquire/present results and swapchain recreation.

A **timeline semaphore** carries increasing numeric values and can represent completed batches more flexibly than an array of binary semaphores. But it is not automatically valid for every WSI operation, and an application must enable the supported feature appropriately. For example, Vulkan's ordinary acquire/present WSI synchronization paths use binary semaphore conventions; replacing every binary semaphore with a timeline value is not generally a drop-in transformation. Cross-queue timeline waits must also have compatible pipeline scopes and signal/wait values. A larger number is not a proof of visibility for a resource whose submission wasn't actually associated with that timeline.

Synchronization is a *graph of scopes*, not a magic “GPU finished” flag. A memory dependency answers **which earlier accesses happen before which later accesses**. A queue execution dependency may order commands without making the relevant writes available and visible at the scope needed by a consumer. Stage masks describe where execution waits are applied; access masks describe the relevant memory operations. Neither alone is the same thing as the host being allowed to free an image or read a buffer. The precise Vulkan synchronization vocabulary is established in the [Khronos synchronization specification](https://docs.vulkan.org/spec/latest/chapters/synchronization.html) and the official [Synchronization Examples](https://docs.vulkan.org/guide/latest/synchronization_examples.html).

#### Kairo's real fence-reset failure gap

The inspected KairoRenderer `VulkanRenderer.cppm` constructs a render-graph sequence with a `Retire` pass that waits on `m_Sync.InFlight()`, an `Acquire` pass that obtains a swapchain image, a `Record` pass, a `Submit` pass that calls `vkQueueSubmit`, and a `Present` pass using `vkQueuePresentKHR`. It has a single frame-in-flight fence and explicit per-image render-finished semaphores. These are grounded observations from actual source, not hypothetical engine architecture.

A subtle failure path appears in the `Acquire` pass. After a successful or suboptimal `vkAcquireNextImageKHR`, Kairo calls `vkResetFences`. Only **after that** does the render graph enter `RecordFrameCommands` and `vkQueueSubmit`. If recording throws, command finalization fails, or the submit path rejects the work before acceptance, the fence has already become **unsignaled**. There is no accepted submission to signal it. On the next `DrawFrame`, the `Retire` pass can wait indefinitely on that unsignaled fence. This is a concrete control-flow concern in the observed code, not a claim that a hang was reproduced on a specific GPU.

The better ordering in a simple one-frame implementation is to wait on the fence for prior work, successfully acquire/record the new commands, then reset the relevant fence **immediately before the submission whose completion will signal it**. Even that does not completely eliminate the submit-failure branch: a definite pre-submission rejection after resetting the fence still requires recovering or recreating the now-unsignaled fence, while preserving correct acquire semaphore and WSI image state. A renderer should have an explicit error path, not simply throw after `vkQueueSubmit` and hope the next frame works.

We encode that exact failure as a state: `Phase::failed_before_submit`. Once a frame has performed a modeled fence reset, a definite failed record/submit transition enters that state. It cannot be submitted again or acquired as a fresh frame without explicit recovery. The method `recover_definite_pre_submit(token, backend_proved_quiescent)` requires an externally established proof that there is no in-flight GPU use and that the fence/acquire resources have been safely reconstructed or quiesced. In the CPU model this proof is passed as a Boolean fixture, not generated by the model itself; a production backend must implement the actual native steps, including any necessary semaphore replacement and image handling.

The model deliberately rejects a recovery request supplied with `false`. It also refuses to interpret a **submission whose acceptance is unknown** as a known pre-submit failure. Those are different states: indeterminate acceptance must remain quarantined until a backend independently establishes acceptance or a safe reset/quiescence condition. This preserves the strongest lesson from Pass 12 while connecting it to a real failure branch in Kairo.

#### Command pools own command memory, not finished work

Kairo's `VulkanCommand.cppm` creates one command pool with `VK_COMMAND_POOL_CREATE_RESET_COMMAND_BUFFER_BIT` and a primary command buffer allocated from that pool. Its `Begin()` implementation calls `vkResetCommandBuffer`, then `vkBeginCommandBuffer`. The code comments correctly state the critical precondition: GPU work previously submitted using that command buffer must have completed before it can safely be reset and recorded again. A command pool cannot be casually reset while any command buffer allocated from it remains pending.

With multiple frames in flight, keeping all command buffers in one global pool can add contention and overly broad reset lifetime constraints. Common designs allocate a command pool per frame slot, often separately for recording threads and queue families, and reset it only after the frame's relevant completion evidence is observed. This is not a command to allocate a separate pool for every draw call; that would be a different and generally wasteful allocation policy. The engine must decide the lifetime and concurrency granularity deliberately.

The command-buffer recording state machine includes initial, recording, executable, pending and invalid states with explicit transitions and valid-usage conditions. Our `FrameRetirementModel` is a *separate host-level journal*, not a substitute for native `VkCommandBuffer` states. Its `pending` means “the simulated backend accepted this frame submission,” while its `gpu_complete` means the test supplied a verified completion observation. A native Vulkan backend still must follow native command pool and buffer rules, as defined in [Vulkan Command Buffers](https://docs.vulkan.org/spec/latest/chapters/cmdbuffers.html).

#### Present image lifetime is independent of frame fence lifetime

A key design mistake is to treat the graphics fence as permission to reuse the image-specific presentation semaphore immediately. Presentation is a separate operation, potentially on another queue and controlled in part by WSI. The CPU can observe that the graphics commands finished but still need evidence that the presentation engine has finished consuming the render-complete signal and that the image has been returned to the acquire protocol.

The portable model uses an `Image` state distinct from the `Frame` state. When a test calls `present_enqueued(ticket)`, the image becomes PRESENTED; this means the model was told presentation was queued, not that display occurred or WSI released the image. When it calls `observe_gpu_completion(ticket)`, the frame can move to GPU_COMPLETE. Its `retire_frame(ticket)` can then release the modeled frame's resource holds and return the CPU frame slot to IDLE—but the image remains unavailable. Only `observe_present_release(image, swapchain_generation)`, which represents **separate backend/WSI evidence**, makes that image available to acquire again.

In Vulkan, a robust implementation might use the successful reacquisition of the same image as a safe point for synchronization-object reuse, or use supported presentation-completion extensions and their exact guarantees. Merely calling `vkQueuePresentKHR` and seeing `VK_SUCCESS` does not prove the GPU displayed the frame or that the binary semaphore is instantly reusable. The model's explicit “present release” callback is therefore a conservative seam where a native implementation must supply WSI-specific evidence, not an API call of that exact name.

Swapchain recreation is a further independent generation boundary. Window resize can invalidate extents and image views while GPU work and presentation operations remain in flight. The CPU model refuses to advance its swapchain generation unless **every frame slot is idle and every presentation image has been released**. A production renderer can sometimes do better using deferred generations and specific synchronization, but it must still guarantee that old native objects are not destroyed while their uses remain live. A changed window size is not a safe global `freeAllOldFrames()` instruction.

The test verifies that frame slot zero and image two can have different indices; that a frame slot can retire while image two is still unavailable; that another frame can use a different WSI image; and that the old swapchain generation cannot release a newly created image. These cases are exactly why an engine should not put `frameIndex`, `imageIndex` and `timelineValue` into one unqualified integer and hope callers remember which one it is.

#### Maveb teaches a different resource lifetime

Maveb's actual `FrameContext.cpp` initializes per-frame shared upload and readback buffers plus a private transient heap. Its `beginFrame()` runs deferred cleanup functions, clears the deferred list, and resets upload/readback arena cursors to zero. This is efficient because it can reuse large stable allocations rather than allocate small Metal buffers for every draw. But that optimization depends on a strict precondition: **the frame context must be reusable only after the GPU has finished all work referring to the previous frame's arena slices**.

The inspected `Renderer.cpp` establishes a three-frame semaphore permit system using `dispatch_semaphore_create(3)`. The draw path waits on a permit before selecting a frame context, and a command-buffer completed handler signals the semaphore once the relevant GPU work has finished. The renderer destructor waits for all three permits before releasing the semaphore. These facts matter because the completion-handler lambda captures `this`: the source shows explicit lifetime coordination, not a casually unguarded callback. A future audit should still investigate all early-return paths, callback error states and whether each path balances permits exactly once, but it would be incorrect to claim a proven use-after-free from seeing a `[this]` capture alone.

Kairo's Vulkan design and Maveb's Metal design solve related but not identical problems. Kairo stores the native completion fence in `VulkanFrameSync` and waits on it at a render-graph boundary. Maveb couples per-frame storage reuse to a host semaphore released by a Metal completed handler. Metal's native command buffer status must still distinguish completed from error states, and resource lifetimes must respect Metal's retained reference behavior and, where relevant, Metal 4's different resource retention responsibilities. No amount of Vulkan enum naming makes the two APIs identical.

The C++ model's resource tokens therefore represent **logical allocation generations** without pretending they are either VkBuffer handles or MTL::Buffer pointers. Kairo mesh data, Maveb Gaussian attributes, Kyoto collision output and an XR gaze buffer can all be registered with the same host lifetime journal. Their native allocation semantics differ, but none may be destroyed while an accepted in-flight command still references its storage. We also add explicit CPU reader pins so an application-side diagnostic snapshot or asynchronous editor can keep a resource alive after GPU completion.

#### Lifetime is a join over GPU uses and CPU borrowers

For each logical resource $r$, let $G_r$ be the number of accepted or potentially accepted GPU frames that still retain it, and let $C_r$ be the number of live CPU readers that still borrow it. Let $R_r$ mean that destruction has been requested and the correct generation is still live. The CPU-side retirement predicate is

$$
\operatorname{destroyable}(r)
\iff R_r\ \land\ G_r=0\ \land\ C_r=0.
$$

That condition is necessary but not a complete native destruction proof. The backend must also ensure it accounted for **every** native queue use, descriptor/encoder reference, and presentation dependency. The host journal acts as an auditable place to collect those obligations. Once they are all discharged and a native completion predicate is verified, the owner may destroy the actual object.

Our `ResourceToken` carries owner, slot and nonwrapping generation. When a frame records a reference, `retain(frame,resource)` increments the frame-use count once per unique resource. Requesting destruction marks the resource for deferred retirement but does not make it instantly invalid for an already pending GPU command. A CPU reader pin can independently prevent destruction. After the frame's verified completion, `retire_frame()` releases its resource holds. Only after the last GPU hold and CPU pin disappears does `destroy_if_safe()` accept the request, and the next allocation of that slot receives a higher generation.

This pattern is useful far beyond rendering. A physics broad phase can generate collision-pair buffers while the previous epoch's pairs are being read by a solver or visualizer. Gaussian splat staging can retain old attribute arrays while a new frame's revision is being uploaded. An XR system can keep a gaze-conditioned image and the timestamped gaze data alive until reprojection or readback ends. If any user holds a raw pointer without participating in this protocol, the protocol's count is incomplete and the safety guarantee collapses. Production code should use RAII read leases, not rely only on manual `pin_cpu`/`unpin_cpu` bookkeeping; the model uses explicit methods so its invariant can be tested plainly.

The model does **not** call `vkDestroyBuffer` automatically when `retire_frame()` runs. It instead reports how many resources are eligible for release. The native resource manager is responsible for mapping that eligibility back to actual Vulkan or Metal objects and checking their backend-specific lifetime rules. This deliberate separation prevents an attractive but unsafe abstraction that destroys a real native allocation merely because a synthetic counter happened to reach zero.

#### Every stage and access mask must answer a real hazard

A common early Vulkan mistake is to put `VK_PIPELINE_STAGE_ALL_COMMANDS_BIT` and broad memory access masks around every operation because it “makes sync easier.” That can be conservative in some cases but also obscure actual hazards, consume performance and still fail if the correct ownership/layout/visibility rule was not represented. A memory barrier should express the producer, consumer and resource range precisely enough to be validated.

Consider a compute shader generating candidate collision pairs that a later graphics pass visualizes. The producer writes a storage buffer, the consumer reads it as shader data. The dependency must connect the producer's compute shader writes to the consumer's relevant shader reads. If a separate queue family owns the exclusive buffer, a queue-family ownership transfer may also be required, with release and acquire operations using the correct source/destination family indices and synchronization. A plain dependency edge in our Pass 08 graph is not a VkBufferMemoryBarrier2. It is a **reason to generate and validate** one in the backend.

For Maveb-style Gaussian scanning, the producer could be a compute kernel writing prefix-sum offsets and the consumer another dispatch reading them. A barrier or appropriate queue synchronization must make the offsets visible before the scatter reads, and the scatter must have validated capacity so its computed addresses remain in range. A successful fence wait after all work completes cannot retroactively repair a missing inter-dispatch dependency that allowed the scatter to read stale offsets during execution. GPU synchronization correctness includes ordering **inside** the submitted batch, not just an end-of-frame fence.

For host readback, the producer is a GPU transfer or shader write and the consumer is the CPU. The native optional probe executes `vkCmdFillBuffer`, places an explicit transfer-write to host-read memory dependency, submits and waits for a fence, and then maps a HOST_VISIBLE|HOST_COHERENT allocation. Coherence avoids a separate noncoherent invalidate operation for this fixture, but it does not replace fence completion and the dependency. The result is checked as 64 independent 32-bit words, using `std::memcpy` to avoid assuming a GPU-written byte region already contains constructed C++ `uint32_t` objects. This creates a meaningful small GPU/CPU agreement test without requiring a graphics swapchain.

#### Vulkan synchronization2 is a feature-gated API, not a universal spelling

Modern Vulkan provides synchronization2 APIs such as `vkCmdPipelineBarrier2` and `vkQueueSubmit2`, with `VkDependencyInfo`, `VkMemoryBarrier2`, `VkBufferMemoryBarrier2` and `VkSemaphoreSubmitInfo`. These structures express stage and access scopes in a more regular form. The relevant feature must be available and enabled through the correct Vulkan version or extension and feature chain. A backend may also support the older Vulkan 1.0 `vkCmdPipelineBarrier` and `vkQueueSubmit` paths, which remain useful for learning basic lifetime rules and supporting older devices.

Our native GPU-14F probe intentionally uses the **baseline Vulkan 1.0 submission path** instead of silently calling `vkQueueSubmit2` on a device for which synchronization2 has never been queried or enabled. This isn't an endorsement of using the legacy API forever. It is a strict capability boundary: first prove that a simple command, fence and memory readback work using facilities actually requested from the device, then add synchronization2 after an explicit feature-negotiation step. Kairo's inspected source uses `vkQueueSubmit`, which matches this introductory integration point.

A later native Kairo enhancement should introduce a common typed resource-use description that lowers to either the enabled synchronization2 backend or a carefully checked fallback. The high-level graph cannot directly substitute raw flags from one API into another. The backend owns precise stage/access masks, image aspects and layouts, queue-family ownership transfers and command-pool external synchronization.

#### The real native witness is intentionally narrow

When CMake finds Vulkan, GPU-14F can compile an optional translation unit that uses native Vulkan headers. The ordinary CTest always exercises only the portable CPU model. The native route is invoked separately with `--probe-native` and requires a real Vulkan loader, an enumerable compatible physical device and a queue capable of transfer commands. It creates an instance (with portability enumeration when advertised), a headless logical device, a 256-byte transfer-destination buffer, compatible host-visible host-coherent memory, a command pool and a primary command buffer.

The command buffer begins recording with one-time-submit usage, encodes `vkCmdFillBuffer` with a fixed known 32-bit fill value, encodes a transfer-write→host-read memory dependency, then ends recording. A newly created **unsignaled** fence is associated with the `vkQueueSubmit` call. After a successful native submit, the code waits for that fence with `vkWaitForFences`; it does not mark completion merely because the submit call returned. Only after a successful wait does it map memory and compare every expected 32-bit word. If the comparisons succeed, the probe reports a true native pass.

The native cleanup path owns the instance, device, command pool, fence, buffer and memory. It destroys the buffer before the bound memory, and never destroys an in-flight command pool under ordinary success. On a failure after a submission was accepted, it attempts a device-idle drain before normal destruction, rather than immediately releasing referenced command storage. Device-loss recovery is not completed or certified by that fallback: a failed wait or device idle requires API-specific recovery, and a production engine should make such loss a first-class state.

The native path returns 77 and reports unavailable when the SDK/device or compatible host-coherent memory is absent. It reports failure when an actual API call or byte-level oracle fails. It does not create a surface, acquire a presentable image, execute a shader, test graphics blending, measure GPU duration or validate a full Kairo/Maveb renderer. These must have their own separate tests and profiling receipts. One 256-byte buffer fill cannot establish any claim about multi-million-splat throughput or physics collision correctness.

#### Device loss is not “everything is complete”

A device-loss event can occur while accepted GPU work is pending and while buffers/images still appear live on the host. The correct cleanup and recovery path depends on the native API, which device calls are valid after loss, whether waits return device-lost and how the application recreates the device and its resources. The host must not convert a device-lost status to a success-shaped completion event to satisfy a frame allocator.

Our CPU model has `declare_device_lost()`. After it is invoked, resource and frame mutations fail closed; pending work cannot be turned into GPU_COMPLETE merely by advancing a counter. We deliberately provide no magical “recover and reuse all frames” operation, because that would need a verified backend recovery proof. This also preserves the source-generation rule: a recreated logical device must not reuse old owner/generation tokens in a way that makes a completion from the dead device look valid for a new resource.

A related concern applies to editor or gameplay cancellation. A user can stop wanting a rendered frame or remove a mesh from a scene without invalidating a buffer still referenced by the GPU. That removal becomes a deferred retirement request; actual destruction waits for the last completed native use. The same rule guards a Maveb Gaussian revision swap and a physics broad-phase controller replacing candidate output buffers.

#### What the executable actually challenges

The first test creates two CPU frame slots, three WSI images and distinct logical resources for a Kairo mesh, Maveb Gaussian state, XR gaze state and collision-pair output. Two frames become pending simultaneously. The test explicitly enqueues presentation before graphics completion, confirms that a graphics fence is required to retire frame-scoped resources, and then verifies that a **separately released presentation image** remains unavailable until WSI evidence arrives. It tests generations across frame reuse and swapchain recreation.

The second test mirrors the actual Kairo reset-before-record/submit failure path. It resets a fence, triggers a known failure, rejects next-frame reuse, refuses a recovery lacking external proof, and then permits cleanup only when a deliberate “backend proven quiescent and primitives recreated” condition has been supplied. It also makes sure a resource referenced by the failed frame is retained until the recovery, not destroyed by error-handling optimism.

The third test exercises an indeterminate submission and then independently confirms acceptance. It refuses early completion, retirement or pre-submit recovery while the outcome is unknown. A separate device-lost journal refuses further mutations and resource destruction, rather than claiming that a failed device has signaled all outstanding work.

The fourth test has independent CPU and GPU holds. A resource whose frame use has completed cannot be destroyed while a CPU diagnostic reader still pins it. After the last pin is dropped, the old resource can be destroyed and its slot recreated with a new generation. Foreign owner tokens and stale generations are rejected explicitly, preserving the identity lessons from the earlier C++ chapters.

The fifth test verifies the distinction between a submitted frame and an enqueued presentation, incorrect state transitions, generation changes, frame-slot reuse with another swapchain image and the requirement that all presentation images be released before swapchain replacement. It also shows how the teaching model is deliberately **presented-frame specific**: headless compute tasks need a different finalization policy with no WSI image, even though the resource lifetime and queue completion rules transfer directly.

These authored tests require a real compiler/CTest execution before anyone may say they passed. The GitHub commit is not a binary, and a CMake target registration is not a test result. Evidence collection must record the exact source commit and observed CTest outcome for all cumulative targets. The opt-in native Vulkan run needs its own clearly labeled evidence showing SDK, loader, physical device, queue, fence completion, actual returned word comparison and validation warnings, if any.

#### Reconstruction: design the recovery branch and the GPU evidence

Trace Kairo's current `DrawFrame()` as a dependency graph. Mark when the fence is observed signaled, when it is reset, where command encoding can fail, where `vkQueueSubmit` can fail, and where an acquire semaphore has already been signaled but not yet consumed. Draw a safe state machine for each error. A failure branch that merely logs a message and retries on the next call is not sufficient; it may wait forever on a fence that will never be signaled or reuse a binary semaphore incorrectly.

Then draw the three independent lifetimes of a frame slot, a swapchain image and a submission ticket. Simulate two frames in flight over three images and show why there cannot be a universal equation `frameSlot == imageIndex`. Identify which native operation or WSI extension provides enough evidence to reuse the present-completion semaphore for that image, and why graphics-fence completion alone might not be enough.

Now adapt the same reasoning to Maveb's `FrameContext`. Show precisely why resetting upload/readback cursors is allowed only after all commands using the old slices finish. Show why a deferred cleanup callback must not execute before the last GPU reference, and why a handler capturing the renderer must have its owner alive until callback completion. Read the renderer destructor and its semaphore-drain behavior; do not assume the callback causes a use-after-free without demonstrating a reachable violation.

Next use a GPU collision-pair compaction example. Define buffers for bounds, pair candidates, counters, prefix offsets and compacted output. Write the execution and memory barriers required for each producer-consumer pair. Use the independent CPU exact-pair oracle to validate set equivalence, not just performance. For a Gaussian renderer, replace the candidate-pair output with projected splats, tile pairs, radix-sort offsets and composited outputs. Explain which buffers can be reused within a frame and which require cross-frame retention or a distinct aliased heap lifetime.

Finally modify the optional native witness *in a separate native experiment* to dispatch a compute shader instead of calling `vkCmdFillBuffer`. Query the exact shader feature, create descriptor-set and pipeline layout, compile and validate SPIR-V, bind its storage buffer with correct offsets, submit and wait, then compare GPU output against an independent CPU implementation over edge cases. Record actual validated source hash and hardware identity. The goal is not merely to see the GPU run; it is to be able to explain and independently check every ordering and lifetime boundary that made the result meaningful.

It does **not** claim any native run happened, nor that production Kairo or Maveb was modified, fixed, profiled or passed validation.
