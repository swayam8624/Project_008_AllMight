### NES-08G — Build the frame's dependency proof before asking any processor to execute it

A program may contain correct instructions, correct data and individually correct functions, yet still fail when those functions execute in the wrong order. Our continuing NES system now has owned cartridges, a typed asset loader, a generational registry, a working subset of 6502 instruction execution and a debugger that can record an ordered instruction trace. We can decode an image, mount a cartridge, reset the CPU, execute its program, inspect the resulting RAM, prepare a debugger overlay and eventually submit texture or graphics work. The new question is not which C++ container can hold these operations. It is **which operations must happen before which others, and what evidence establishes that requirement?**

The existing chapter already derives graphs and their adjacency representations, BFS, DFS, topological sorting, strongly connected components, shortest paths, A*, spanning trees, sorting and scans. Its later pages explain API publication contracts, external-resource lifetimes, GPU execution and synchronization, shader buffer layout and kernel work distribution. None of that original narrative needs to be shortened or restated as a list of disconnected definitions. We now bridge those substantial explanations using one real project problem: build a C++23 **CPU-side work dependency planner** around the already implemented emulator and asset pipeline, then use its output as a *description* of future GPU work—not as a false claim that Vulkan or Metal commands have executed.

The shared planner is `tools/labs/nes_course/work_dependency_graph.hpp`. The new executable witness is `tools/labs/nes_work_dependency_graph_cpp23_lab.cpp`. It actually imports a synthetic NROM cartridge and an RGBA8 texture through the **same `Spec<Tag>` decoders and `GenerationalAssetRegistry` from the previous passes**, mounts a fresh NROM-owned bus value, runs the existing `CpuDebugSession` from Pass 07, and verifies the CPU-visible RAM state and instruction traces. It also creates conceptual GPU transfer, compute and graphics tasks whose dependencies can be inspected. Those GPU tasks are deliberately **not dispatched to a device**.

We must distinguish three quantities from the outset. A **CPU instruction dependency** describes the sequential machine-state transitions of one emulated 6502. A **host work dependency** describes when one software task may observe another task's completed work. A **GPU execution-and-memory dependency** is established through specific backend commands, scopes, queues and resource states. A host-side DAG can help plan all three, but an arrow in a C++ vector does not automatically implement a semaphore, flush a cache, make image contents visible to a shader or keep a GPU allocation alive. The distinction is the central contract of this milestone.

#### Derive the graph from an observable failure, not from the name of an algorithm

Consider the operation “execute LDA #$7F, store the accumulator to zero-page address $01, then inspect that memory.” If the debugger runs before a cartridge is mounted, the reset vector cannot be fetched. If it starts executing before reset, its program counter has no declared initial meaning. If the RAM inspector runs before `STA`, it observes an old value. If the graphics stage consumes an overlay before the host has prepared it, the displayed state may describe the wrong CPU step. These are not optional aesthetic ordering preferences; the sequence changes the observable result.

Let task $u$ have to complete before task $v$ begins using its result. We represent that relation as a **directed edge** $u\rightarrow v$. An independent pair of tasks has no ordering edge unless another resource or application invariant requires one. A *task graph* is therefore an abstraction of required happens-before relationships. It is not by itself a thread scheduler, it is not a sequence of native CPU instructions, and it is not necessarily a render graph until its task and resource meanings are specified.

The graph's vertices use a small, distinct `TaskId` value type, and each task records a human-readable name, a `Domain`, an abstract nonzero estimated cost, explicit predecessors and declared accesses. A resource key contains its kind, owner, slot and generation. We retain the generation because two different occupants of a recycled registry slot should not automatically be equated merely because their numeric slot matches. The planner records the resource key rather than a borrowed pointer to a mutable asset. The published `Plan` owns its task ordering and dependency descriptions and contains no raw pointer back into the builder's transient vectors.

The declared task domain is one of `host`, `gpu_transfer`, `gpu_compute` or `gpu_graphics`. These are **intent labels** for the planner. The type does not establish that a GPU has a dedicated transfer queue, that compute and graphics can execute concurrently, or even that a device has been created. Those are backend and hardware questions to answer after planning. On a single physical queue, different logical domains may map to the same submission sequence; on hardware with compatible independent queues, dependencies and ownership rules become more involved.

#### A missing edge can be more dangerous than a detected cycle

Suppose task A initializes CPU state, and task B executes the first instruction. Without an edge A→B, a scheduler may execute B first even though both tasks are individually valid C++ functions. A graph that successfully topologically sorts despite that missing edge is still **semantically wrong**. Topological sorting proves only that the given edges were respected. It cannot infer every data dependency that the programmer failed to describe.

We therefore have two complementary ways to create edges. An **explicit dependency** states an application-level prerequisite even if two tasks do not touch a resource the planner can see. For example, texture-upload planning must not proceed until source validation has declared the asset suitable. A **resource hazard dependency** is generated from the read/write access descriptions of tasks using the same resource identity. These rules express a partial order derived from shared state.

The three classical hazard kinds are worth proving by counterexample rather than memorizing abbreviations:

| Hazard | Prior operation | Later operation | Why ordering matters |
| --- | --- | --- | --- |
| Read after write, RAW | Write X | Read X | Reader must see the intended completed producer value |
| Write after read, WAR | Read X | Write X | Writer must not overwrite a value before the earlier reader finishes |
| Write after write, WAW | Write X | Write X | Final value depends on which writer wins |

Two reads of the same *immutable, ready* resource do not require a mutual ordering edge merely because they share it. That is a crucial optimization. It allows independent consumers to remain simultaneously eligible, provided there are no external unmodeled dependencies. Likewise, if a task both reads and writes a resource, it must declare that combined access rather than pretending to be a pure reader while mutating global state.

Our planner keeps, for each resource key, the last writer and the readers that occurred since that write. When a new reader arrives, it depends on the last writer and joins the pending reader set. When a new writer arrives, it depends on the last writer and on all those intervening readers; the reader set is then cleared and the new task becomes the last writer. This preserves **submission-order conflict semantics** for each resource. It does not mean that submission order is always the desired engine order: the caller must submit operations with an intentional policy and may use explicit edges when the intended cause-and-effect relationship differs from a simple write history.

For example, suppose task 10 writes a texture record, tasks 20 and 30 read it, and task 40 overwrites it. The direct hazard edges are 10→20 and 10→30 for RAW, 10→40 for WAW, and 20→40 and 30→40 for WAR. There is no need for 20→30. If task 40 also explicitly names task 20 as a prerequisite, that is **one ordered pair with two reasons**, not two different dependency edges requiring two artificial indegree decrements. The implementation merges all reasons for a pair into a bitmask. The test asserts each rule separately and proves the read/read absence.

The planner's resource access model is intentionally coarse. One key identifies a resource as a whole, not an arbitrary buffer subrange, image mip/layer, or simultaneous nonaliasing part of a struct. A coarse key can introduce safe but unnecessary edges. A too-fine key can miss a real memory alias and introduce a data race or GPU hazard. A later render-graph implementation must track the relevant resource ranges and actual allocation alias relationships rather than assuming two unequal logical handle keys imply physically disjoint GPU memory.

#### Validate the entire graph before publishing an execution plan

The builder accepts tasks incrementally but does not execute them. It rejects duplicate task IDs, empty names, zero estimated costs, declarations that neither read nor write, and duplicate access declarations for the same resource within one task. Importantly, a task may refer to another task that has not been added yet; the builder allows **forward references** so the caller can construct a graph in whichever source order is convenient. The completed `plan()` operation then checks that every referenced predecessor exists. If an identifier is missing, it returns a typed missing-dependency error rather than silently dropping the edge.

This separation creates an honest failure boundary. A partially assembled task list is not a published schedule. The planning function builds private adjacency and indegree structures. If it finds a missing predecessor, a directed cycle or an arithmetic overflow, it returns an error and produces no partial `Plan`. The submitted task records remain unchanged, allowing the caller to correct the graph or report a useful diagnostic. These semantic guarantees do not turn arbitrary host-memory allocation failures into successful plans: standard containers may allocate while building the plan, and `std::bad_alloc` is allowed to propagate from the planning routine. No task has executed during that failure, which is the essential distinction.

A cycle is not fixed by pretending one task is “the first” and continuing. If A depends on B and B depends on A, neither may start under the declared rules. A renderer's previous-frame feedback might be a real application requirement, but then the graph must introduce a prior-frame resource, explicit temporal delay, iterative solver or other well-specified mechanism. Simply removing the edge to make a topological sorter happy changes the application contract. The test injects a mutual cycle, requires a typed rejection, runs the planner again and confirms that the original graph has not mutated or published partial work.

The current diagnostic identifies a **blocked task** when a cycle prevents completion. It does not pretend that the first unresolved vertex is necessarily a member of the actual cycle; a downstream task can be blocked by a cycle elsewhere. A stronger diagnostic can use DFS on the unresolved subgraph to extract an actual closed directed path. The difference between “some task could not be scheduled” and “this is the concrete cycle witness” matters to a programmer trying to repair an engine's dependency network.

#### Kahn's algorithm earns its place by constructing a valid prefix

Let a vertex's indegree be the number of distinct incoming graph edges. A task with zero indegree has no remaining unsatisfied prerequisite. Kahn's algorithm repeatedly selects a ready task, appends it to the output sequence, removes its outgoing edges from the remaining graph, and makes any newly zero-indegree successors ready. If exactly $V$ vertices are removed, the output is a topological order. If fewer than $V$ can be removed, the unresolved graph contains a directed cycle.

The proof is inductive. Initially, a zero-indegree task is not preceded by any required task in the remaining graph, so it can begin the schedule. Assume the first $k$ emitted tasks respect every edge among the tasks processed so far. When the next task is chosen, it has no incoming edge from any unprocessed predecessor; therefore placing it next cannot violate an input dependency. Repeating this argument constructs a valid full ordering or exposes a remaining cyclic region. The algorithm does not make tasks free of external side effects or infer missing hazards—those are preconditions of the input model.

Kahn's algorithm can yield multiple valid orders when independent tasks are ready together. For deterministic teaching, debugging and reproducibility, our implementation uses a **min-heap ordered by numeric task ID**. Thus for two independent tasks added in order 99 then 3, it emits 3 before 99. This tie-break is not necessarily optimal for throughput or cache behavior; it is a deliberate deterministic choice that makes generated traces and regression failures easier to reproduce.

The graph builder merges edge reasons using a hash index on pairs of bounded task indices, so a single ordered pair has one edge regardless of how many justifications refer to it. With the declared 4,096-task teaching bound, the pair can be represented unambiguously as two 32-bit fields in a 64-bit key. Hash lookup is expected constant time under the usual assumptions; pathological hashing still has a different worst case. Building the access-hazard history costs work proportional to the access declarations and edges it actually generates, while Kahn's min-heap adds a logarithmic ready-selection factor. The implementation favors clarity and determinism over a claim of fixed CPU cycles per vertex.

A task with two outgoing edges can become ready at different times depending on when its predecessors complete, but its indegree is decremented **once per unique edge**. This is why merging explicit and hazard reasons is not cosmetic. Counting duplicate edge objects as independent dependencies can still be made internally consistent if both increments and decrements are duplicated, but it leads to more complicated diagnostics and can obscure the fact that only one predecessor completion is needed.

#### A critical path is not a shortest path

The original chapter already teaches BFS for equal-cost reachability, Dijkstra for nonnegative shortest paths, A* with admissible heuristic conditions and Bellman–Ford for negative-edge settings. Those algorithms answer questions such as “what is the cheapest route to a target?” A work dependency DAG asks a different question: given task costs and precedence constraints, what is the **longest chain of compulsory work** that cannot be overlapped even with unlimited processors?

For a task $v$ with estimated duration $c(v)$, define its earliest possible start in the abstract DAG model by

$$
ES(v)=\max_{u\rightarrow v} EF(u),
$$

with $ES(v)=0$ if it has no predecessors, and its earliest finish by

$$
EF(v)=ES(v)+c(v).
$$

The graph's abstract **critical-path cost** is $\max_v EF(v)$. This is a longest-path dynamic program on a DAG, evaluated in topological order. It must not be confused with running Dijkstra on positive costs or with the actual frame's measured elapsed time.

For the four-task hazard example, suppose task 10 costs 2 abstract units, readers 20 and 30 cost 3 and 4, and task 40 costs 5. After task 10 finishes at 2, the readers can conceptually run concurrently and finish at 5 and 6. Task 40 must wait for both, so its earliest start is 6 and its earliest finish is 11. The critical path is task 10 → task 30 → task 40 with length 11. The alternate path through reader 20 costs only 10. The test checks this exact result, including the distinct hazard edges.

The “cost” in this exercise is an **input estimate in one consistent abstract unit**. It is not automatically a 6502 cycle count, a Vulkan timestamp or a measured millisecond duration. The CPU emulator's `InstructionTrace::total_cycles` counts modeled historical processor costs for a bounded opcode subset, whereas a host scheduler's estimated task costs are numbers chosen for planning. Combining them as if they were the same time unit would make the critical-path result meaningless. Later benchmarking should record actual host durations and GPU timestamps separately, including synchronization overhead and uncertainty.

Before computing $ES+c$, the implementation checks for 64-bit unsigned overflow. A graph with a task of cost `UINT64_MAX` followed by another task of cost one must return a typed arithmetic error, not silently wrap to a tiny and attractive “fast” critical path. This is the same checked-arithmetic principle previously used in ROM layout, mesh sizes and asset budgets, now applied to scheduling.

A topological **layer number** is another derived value, but it is not the same as earliest start. The layer is zero for a task with no predecessor and one more than the largest predecessor layer otherwise. It counts the depth of dependency edges, not the sum of estimated costs. Layering can reveal independent groups of work, yet executing every task in the same layer simultaneously is safe only when every relevant access and side effect has been declared. A single thread or a GPU with limited compute units will not realize the unlimited-parallelism critical-path bound.

#### Execute the real host portion against our existing emulator

The cumulative laboratory constructs a valid one-bank NROM image with a reset vector pointing to `0x8000`. The program contains `LDA #$7F` followed by `STA $01`, then a NOP. The image is imported through the existing typed asset factory into the generational registry; an RGBA8 texture is imported through the same registry with its independent texture validator. No borrowed pointer into either source file is retained by the registry.

Our graph then declares a sequence of host tasks: validate that the cartridge handle still resolves, mount an independent owned NROM value into the existing `CpuBus`, reset the real `CpuDebugSession`, execute the load instruction, execute the store instruction, inspect the RAM result, and prepare an owned debugger overlay from the CPU snapshot. A separate host task validates the texture. We use **one explicit owned-copy policy** at the bus boundary: the registry remains the owner of its stored cartridge, while the bus must have its own independently decoded NROM value. The code does not move the cartridge out of the registry behind the back of a client holding a live handle; it also does not retain a borrowed pointer whose lifetime the registry could end.

The task-access declarations identify which operations read or modify the CPU state, PRG image, CPU RAM and trace. The graph automatically creates an ordering between reset and instruction execution, between two state-mutating instructions, and between `STA` and the RAM inspector. The overlay preparation reads the completed CPU state and trace before marking the overlay's source data ready. The texture validation path remains independent of those CPU-specific operations.

The host executor follows the returned topological plan and dispatches only the tasks labeled `host`. It calls the **actual Pass 07 debugger interface**, not a newly written mock interpreter. The expected final CPU PC is `0x8004`, the accumulator is `0x7F`, the instruction-cost counter is 5, and the trace contains two completed steps. The internal RAM at `0x0001` must read back the value `0x7F`, including through the previously proven mirror `0x1801`.

The graph also describes three potential GPU tasks: upload the texture, run a compute stage consuming the uploaded resource and prepare graphics work consuming the computed result together with the CPU-side debugger overlay. The planner must establish transfer→compute, compute→graphics, and overlay-preparation→graphics dependencies. **Nothing in the executable runs the GPU tasks.** They remain inspected obligations for a later backend. This keeps our project honest while making the dependency structure ready for actual Vulkan or Metal implementations when those systems are introduced.

We also test what happens when the registry changes *after* the plan was constructed. The previously valid cartridge handle may be erased, making its generation stale. The stored DAG is still topologically well formed, but the old handle no longer resolves in the registry. That is why a graph's mathematical validity cannot certify the lifetime of the assets mentioned in its resource keys. At the execution boundary, the handler must revalidate its handles, hold an appropriate lifetime pin or operate on a deliberately owned snapshot. Our demo checks staleness and refuses to rerun the invalidated work. A future streaming scheduler must define cancellation and retirement across async execution rather than hoping that a successful plan permanently freezes its inputs.

#### The GPU side needs more than an arrow

A render graph is particularly prone to seductive simplifications. The planner can tell us “texture upload must precede shader sampling,” but it cannot tell us that the image has the appropriate layout, correct row pitch, a live memory allocation or visible writes on a particular device. The backend must map the dependency to the API's concrete resource usage, access types, execution scopes and queue conditions.

Vulkan explicitly distinguishes **execution dependencies** from **memory dependencies**. Execution ordering alone does not universally prove that producer writes are made available and visible to the consumer. A synchronization description must identify appropriate producer and consumer stages/accesses and any required image layout transitions. If transfer and compute use separate queue families with exclusive ownership, a queue-family ownership transfer may also be required; that is distinct from the abstract DAG edge. Where semaphores or queue submissions provide particular synchronization, the required additional commands depend on the exact resource and command setup. We should derive an actual barrier or semaphore arrangement from the current Vulkan specification and validated command recording, not from an arbitrary mapping such as “every edge means one pipeline barrier.” The official [Vulkan synchronization specification](https://docs.vulkan.org/spec/latest/chapters/synchronization.html) and [synchronization examples](https://docs.vulkan.org/guide/latest/synchronization_examples.html) provide primary evidence.

Metal also requires version- and command-model-specific care. For earlier Metal command interfaces, tracked resources can receive automatic hazard tracking under specified conditions; untracked resources need explicit coordination. Metal 4's command-queue model has its own synchronization rules, and the treatment of a resource's older `hazardTrackingMode` is not a universal shortcut for MTL4 queues. Argument-buffer resource residency introduces further responsibilities. The current [Apple resource synchronization documentation](https://developer.apple.com/documentation/metal/resource-synchronization) describes these distinctions, and [resource residency documentation](https://developer.apple.com/documentation/metal/tracking-the-resource-residency-of-argument-buffers) covers a separate but related contract. The correct teaching rule is **query and respect the exact backend, device and API generation**—not “Metal automatically solves all barriers” or “Vulkan requires one barrier per graph edge.”

Accordingly, our `Plan` includes a collection named `gpu_edges_requiring_backend_review`. It identifies graph edges that touch conceptual GPU work. These entries are **review prompts** rather than prebuilt `VkDependencyInfo` objects, `MTLFence` calls, MTL4 queue operations, ownership transfers or semaphore waits. Some explicit GPU-related ordering edges may require only command-generation sequencing; some resource hazards need multiple stages of device synchronization; and some can be coalesced or satisfied by other valid synchronization already in place. Counting all of them as “barriers implemented” would be an incorrect engineering report.

A real implementation must also distinguish allocation lifetime from logical asset identity. The generational texture handle may refer to an asset that the CPU has logically deleted. A previously submitted GPU command may still read the backing allocation. Invalidating a CPU handle stops future logical lookups but does not necessarily retire the native image. The engine needs a completion-based retirement mechanism and ownership rules for descriptors, queue submissions and any aliased physical allocations. Those details are not optional “optimization later” features; they are part of using asynchronous GPUs correctly.

#### An exact CPU scan is the reference for later GPU compaction

The chapter's GPU work-distribution material develops exclusive prefix scans because many parallel outputs have variable lengths. To keep that derivation attached to a runnable project, our planning library now contains a **checked CPU reference** named `checked_exclusive_scan`. Given nonnegative output counts $c_i$, it constructs offsets

$$
o_i=\sum_{j<i}c_j
$$

and total output count $N=\sum_i c_i$. Item $i$ owns the half-open output interval $[o_i,o_i+c_i)$. Adjacent intervals touch but do not overlap because $o_{i+1}=o_i+c_i$. This is a proof of output-range partitioning, independent of a particular GPU kernel layout.

For counts $(2,0,3,1)$, the correct exclusive offsets are $(0,2,2,5)$, with total six. The zero-count item owns an empty interval at offset two, and the final item's interval ends at six. The test checks every interval boundary, the empty-input case and a count pair that would overflow `std::size_t`. No silent unsigned wrap may allocate an undersized output buffer.

Why is this useful for an engine rather than a detached algorithm lesson? A renderer might count visible primitives per tile, allocate compacted draw records, or expand a mesh into variable numbers of output triangles. It can use a known-good CPU scan as a small-input oracle for a future parallel shader implementation. But this CPU reference does **not** demonstrate a workgroup barrier, subgroup operation, global cross-workgroup synchronization or device memory ordering. A GPU parallel scan must implement a multi-stage dependency protocol and validate both output arithmetic and synchronization on real hardware.

#### Different graph algorithms answer different engine questions

At this point we can place the original chapter's algorithms within one architecture without claiming they are interchangeable. **BFS** can answer whether an unweighted navigation region is reachable and minimize hops. **Dijkstra** can minimize nonnegative path weights, while **A*** uses an admissible lower bound to guide a goal-oriented search. **Minimum spanning trees** minimize the total weight of a connector network, not the travel distance between every pair. **Strongly connected components** identify cyclic regions of a graph. **Topological sorting** orders a DAG of prerequisites. **Longest-path dynamic programming on a DAG** estimates compulsory serial work across the declared critical path. **Exclusive scan** assigns nonoverlapping positions for a known sequence of output counts.

For the same physical game world, those algorithms may all be useful, but only after the meaning of each edge or count is known. A collision graph connecting bodies in contact is not necessarily an instruction dependency graph. A render graph's positive task cost is not a distance metric for pathfinding. A GPU resource hazard edge is not a guarantee of navigability between scene regions. Teaching the words together without preserving those meanings would produce a superficially broad but operationally confused curriculum.

An especially important distinction is that a *dependency graph* typically encodes directed constraints about order, whereas many physics-island or navigation relationships are undirected connections. A topological order cannot be requested of an arbitrary cyclic undirected contact graph; DSU or graph traversal is usually a better basis for finding connected islands. An artist-facing scene hierarchy may be a tree or a DAG depending on instancing semantics and ownership policy. We should model the system before choosing the algorithmic representation.

#### What the executable evidence proves, and what it does not

The C++23 test suite includes five distinct evidence groups. First it checks every direct hazard in a small write/read/read/write graph, including merged explicit/WAR reasons, read/read independence and exact critical-path cost. Second it rejects duplicate task IDs, malformed accesses, duplicate resource declarations, missing prerequisites, directed cycles and critical-path overflow without altering the submitted graph. Third it proves that two different generations of an asset key are not automatically treated as the same logical resource, while separately demonstrating that a stale handle must be rejected by the *actual* asset registry at use time.

Fourth it plans and executes the host side of the synthetic NES/texture workflow and verifies the actual CPU debugger, program counter, RAM mirror, instruction traces and generated GPU obligations. Fifth it generates thirty deterministic acyclic graphs of sixty tasks each—1,800 task declarations in total—and checks an independent topological oracle against every emitted graph edge and every computed predecessor-layer/earliest-start relationship. Those generated cases are reproducible using a fixed pseudo-random state. They are randomized coverage of a constrained DAG family, not a proof for all directed graphs, all possible resource aliasing schemes or arbitrary concurrent execution.

The checked exclusive scan adds a separate arithmetic oracle. The test does not create GPU command buffers, Vulkan barriers, Metal fences, real render targets or a presentation swapchain. Nor does it measure GPU throughput, kernel occupancy, cache pressure, host CPU execution latency or real device completion. The new CMake target reuses the existing separately compiled debugger implementation, ensuring the host side is linked through the same PIMPL interface rather than a parallel simulation stub. Passing that C++ target when eventually executed will be meaningful, but a statement that the source code *contains tests* is not itself evidence that the exact committed build has passed.

One additional testing boundary is worth retaining: a topological-order oracle checking that every emitted edge points forward can confirm the algorithm respects **declared** edges, but it cannot prove that no required edge is missing. For semantic correctness we must independently derive hazard relationships from the declared resource accesses and test those concrete relationships. The deterministic four-task hazard fixture therefore complements the larger generated DAG oracle. A future differential property test could implement a deliberately simple $O(V^2)$ pairwise hazard oracle and compare its ordering constraints against this history-based builder for arbitrary generated resource traces.

#### Reconstruction, adversarial review and the next engine handoff

Reconstruct this project milestone in an order that makes every abstraction necessary. Begin with three concrete operations: mount an owned cartridge, reset the 6502 state and execute a store to RAM. Draw their required dependencies and write down which resource each task reads or writes. Add a RAM inspector and show why it must depend on the store, while two independent inspectors may remain unordered. Then add a texture-validation step, conceptual transfer/compute/graphics stages, and a debugger overlay whose contents depend on completed CPU execution. Draw the final graph before writing an algorithm.

Implement the task record using strong IDs, explicit predecessor values and versioned resource keys. Validate additions before mutating the task set; allow forward references but reject any unresolved predecessor at planning time. Build hazard edges by tracking the last writer and intervening readers for each resource. Merge duplicate ordered pairs and retain their different reasons for diagnostics. Prove Kahn's topological-prefix invariant, choose a deterministic ready-queue tie break, and return a typed cycle error when it cannot emit all tasks. Extend the DAG dynamic program to compute layers and estimated critical-path cost using checked addition.

Then implement a CPU-only dispatcher that actually runs the NES host tasks against the previous lesson's real debugger. Stop before GPU work and inspect the obligation list. Show a counterexample in which the graph remains valid while an asset handle becomes stale after construction; explain the required runtime revalidation or lifetime pin. Build the CPU exclusive scan and derive its nonoverlapping half-open intervals. Finally write a backend-specific synchronization plan *on paper* for Vulkan or Metal, explicitly separating execution order, memory visibility, queue or encoder ownership, layout, residency and resource retirement. Do not claim that the paper plan is compiled or GPU-validated.

A convincing learner can derive the RAW/WAR/WAW constraints, explain why two reads do not need mutual ordering, state precisely what a missing edge does to safety, prove why a directed cycle prevents a topological ordering, calculate the longest-path estimate rather than a shortest path, reproduce the two-instruction NES host trace and the scan offsets, and identify every responsibility that remains between a CPU-generated DAG and an actual GPU submission.
