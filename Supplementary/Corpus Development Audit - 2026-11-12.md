## Navigation and first-use risks found by the live link inventory

The three books contained approximately **23 links into the old archival volumes** at the inspected head: 1 from Mathematics, 11 from Graphics and 11 from Game Engine. The source targets still exist, so these are mostly *legacy detours*, not missing files. Nevertheless they violate the spirit of one reader-facing continuous destination per subject. Their replacement requires determining which in-book heading now owns each prerequisite; a blanket text substitution would break provenance and risk moving a reader to the wrong derivation. Until reconciled, the old link is supporting provenance rather than an instruction to start a fourth book.

A first-pass wiki-link regex reported spurious missing targets such as `nodiscard`, `no_unique_address`, GPU attributes and media paths. Those are often C++/shader syntax, escaped expressions, or images, not Obsidian page links. An audit tool must ignore fenced/inline source and distinguish image attachments from Markdown notes before treating these as missing content. Heading existence itself also proves only the presence of a title, not a coherent implementation.

The Engine source insertion is particularly large and now occupies roughly forty thousand lines before the original mid-engine renderer material. Graphics also contains an early full XR source block. These are **high-priority reading-flow issues** even though the mechanical content-preservation checks are green. Preserve original words, but use linking, carefully justified section placement and substantive bridge explanations to make the story follow a recurring engine problem rather than a pasted source queue.

## Implementation-depth contract for every developed concept

A reader should be able to close the book and build the mechanism. Therefore a concept is not “done” until its first meaningful use provides: the forcing engineering problem; definitions of every symbol, convention and unit; the derivation and its assumptions; the concrete memory/state representation and ownership; the full algorithm and decision branches; a complete documented implementation or a clearly labeled API-specific implementation; a numerical trace with inspectable intermediate state; failure/degeneracy and alternatives; proof of invariants and bounded behavior; and reproducible positive, negative and metamorphic tests. The note itself must contain these, not just a heading, a pointer to a video, or a code file that the reader must discover elsewhere.

**Witness categories must remain distinct.** A CPU-only pedagogical model can prove logic, arithmetic and expected rejection cases. It cannot prove production GPU memory visibility or Apple/NVIDIA driver behavior. A reference engine test cannot establish the current Kairo integration unless the exact Kairo commit and reproducible build are inspected. A mathematically derived assumption is not an observed result; a video transcript's claim is not verified code; the 3,000-part route map is an ownership assignment rather than 3,000 completed reconstructions.

## Current development increment: logical render-graph compiler

The Game Engine volume now carries a full C++20 pass-graph compiler inline at the point where renderer intent becomes backend work. The independent laboratory is `tools/labs/render_graph_contract_lab.cpp`, source-synchronized through `tools/check_continuous_code_sync.py`. It builds a DAG from per-resource last-writer and reader-cohort state, records RAW/WAR/WAW hazards, handles imported history, topologically sorts with deterministic tie-breaking, and rejects duplicate resources, uninitialized transient reads, feedback and explicit cycles. The six-pass G-buffer/shadow/lighting/temporal/tone-map/present trace and negative cases make those semantics inspectable. GCC and Clang compiled/reran the reference locally with `-O1` and `-O2 -DNDEBUG`, warnings-as-errors.

**Boundary:** This is a *single-queue logical whole-resource compiler*, not an implemented Vulkan or Metal render graph. It does not emit stage/access masks, image layout transitions, queue-family ownership, timeline waits, transient aliasing or device-loss recovery. Those remain first-class milestones, not implicit features of this passing laboratory. See the [Vulkan synchronization specification](https://docs.vulkan.org/spec/latest/chapters/synchronization.html) for the separate memory-model obligations.
