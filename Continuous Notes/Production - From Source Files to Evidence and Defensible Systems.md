# Production — From source files to evidence and defensible engine systems

This is the **Phase 30** continuous book, M175–M180, original Parts **2901–3000**. It completes a *teaching route* rather than certifying that any particular author has mastered every earlier phase. Its opening problem is a practical one: an artist exports a camera animation and an image sequence for a reconstructed scene, a Python build process packages them, an engine imports the scene and renders a comparison, and a researcher reports that the new method is faster and more accurate. Every arrow in that apparently routine workflow conceals assumptions about bytes, ownership, timing, coordinates, observation, publication and what counts as evidence.

Imagine that the scene is named **panel**. An artist exports three images, panel.0001.png, panel.0002.png and panel.0003.png. The editor receives a mesh whose vertices originated in a DCC, the renderer produces a reference image, and an experimental script compares the output against an earlier engine revision. It is tempting to treat this as four independent tasks: write a script, import a file, make a plot, present the paper. The engineering reality is that the same datum must cross all four tasks without losing its identity, the validation rules must not change between hosts, and a successful render must not be mistaken for a scientifically supported performance or quality claim.

The reproducible, executable **host-neutral kernel** of this chapter is [[tools/production_evidence.py|production_evidence.py]], exercised by [[tools/tests/test_production_evidence.py|an independent standard-library regression suite]]. It is deliberately not a Blender/Maya/Houdini/Nuke plugin. Those applications supply data and host-specific APIs; the stable core decides what a valid asset, cache, frame sequence, publication and evidence record mean. Before explaining the host adapters, we derive these invariants in full. This chapter distinguishes exact operations present in the laboratory from host APIs and research procedures described but not executed in it.

## The editor should not learn that its cache is broken when a frame is already on screen

A production pipeline begins with an observable contract rather than a filename convention. A source is an identity-bearing object produced at a declared step, in a declared coordinate system or color space, by a declared software version, with declared options. A rendered result is not characterized by an attractive pathname alone. It needs enough information to reproduce the computation, determine whether a cached result is reusable and distinguish original authoring data from derived artifacts.

An **asset manifest** lists independently meaningful inputs: meshes, texture resources, dependencies, unit/axis conventions, transforms, material identifiers and source fingerprints. A **cache manifest** records derived objects, the inputs and algorithms that produced them, compatibility keys and reuse constraints. A **render manifest** connects a scene revision, camera, renderer/backend, resolution, sample budget, color-management choices, random seed, frame range and output hashes. These documents share a schema-versioning problem: a reader must know how to interpret a particular field, not just whether a syntactically valid JSON parser can consume it. A versioned schema cannot silently redefine whether a transform is local-to-world or world-to-local, whether a normal is stored in object space, or whether pixel channels are linear or display encoded.

Our bounded laboratory produces a first-step render/cache manifest for a frame sequence. Its serialized structure has a schema_version, run_id, stem, padding, frame_range and per-frame source filename, SHA-256 and byte count. The exact byte encoding is UTF-8, sorted JSON object keys, compact separators and a final newline. Two plans constructed from the same source set in different input iteration order produce byte-identical manifests. This is **deterministic serialization**, not a guarantee that an actual renderer will produce the same pixels on every GPU.

A diagnostic belongs to the interface, too. The user's application should not need to parse free-form error prose to understand what failed. Each diagnostic in the lab has a stable **code** such as FRAME_GAP, a **severity** such as error, a human-facing message and an optional source path. The program sorts diagnostics consistently. Severity distinguishes a recoverable warning from an error that forbids publication; the code makes it possible to write CI assertions and stable dashboards without relying on English text. For a real renderer, diagnostics would additionally carry a structured run ID, asset ID, frame number, subsystem, stage and possibly a remediation action. Adding a new machine-readable field should be schema managed rather than being smuggled into an unstructured string.

## A path is a proposed location, not an authorization to read or write there

Suppose a DCC script says the exported texture is ../../secrets/key.bin, or a seemingly harmless workspace path is a symbolic link leading outside the allowed project. If the engine blindly concatenates strings, the script may read, overwrite or publish files beyond the intended workspace. Directory traversal is therefore a real security and data-integrity problem, not merely untidy path syntax.

A file path has several layers: its characters, its lexical normalization, its platform-specific interpretation, and the filesystem object it actually resolves to. **Normalization** simplifies a textual representation, such as redundant separators or dot components. **Canonicalization** consults the filesystem, including symbolic-link targets, to identify the underlying path. Simply deleting literal '..' substrings is neither a correct normalization algorithm nor a safe containment test.

The laboratory requires an existing workspace root and resolves it to its canonical real path. An input candidate is resolved, then tested for actual containment inside that root. The frame names themselves must be bare filenames; a supplied path containing directory separators is rejected. A target version name must also be one immediate directory name, never an arbitrary absolute destination. This conservative contract makes the proof easier: a normal frame cannot select a sibling workspace or a nested directory tree just by changing its string.

~~~python
real_root = root.resolve(strict=True)
candidate = (real_root / filename).resolve(strict=False)
if not candidate.is_relative_to(real_root):
    raise ValueError("path escapes workspace")
~~~

Here **is_relative_to** is a containment check on path components, not a string-prefix test. A path named /project/files-evil starts with the text /project/files, yet is not a child of /project/files. The canonical-path check catches that distinction and follows ordinary symlink escapes.

But even this does not establish a malicious-race-proof sandbox. Another process could replace a checked symlink between validation and file open, a classic **time-of-check to time-of-use** race. Secure multi-user services may need directory file descriptors and openat-family operations with platform-specific flags or kernel containment primitives. The lab explicitly assumes a cooperative single-writer local workspace. The stronger OS-security problem belongs in the previously introduced process/filesystem foundations and cannot be claimed solved by one Path.resolve call.

## A cache key is content identity plus the algorithm that interprets it

A file path says where someone looked for data, not which bytes were actually consumed. A name can remain unchanged while its content changes; the same bytes can be copied to a different location. We therefore distinguish **path identity** from **content identity**. SHA-256 is used to fingerprint the bytes of each frame. The lab streams file contents in bounded chunks rather than buffering the entire image in memory, making the extra working-memory cost O(1) with respect to file length, aside from the fixed buffer.

~~~python
digest = hashlib.sha256()
with path.open("rb") as file:
    while chunk := file.read(1 << 20):
        digest.update(chunk)
fingerprint = digest.hexdigest()
~~~

A SHA-256 digest is suitable for content-integrity checking in this teaching system. It is not a signature, proof of provenance, trusted timestamp or license to assume that an arbitrary file is safe to decode. A robust cache identity needs the **input hashes and parameters**: a material shader compiled for a different backend, numerical policy or feature set may not be reusable even if the source shader bytes match. A future cache manifest should include the compiler/renderer version, transformation rules, shader entry, compile flags, target GPU feature assumptions and all relevant dependencies. The rule is simple: every quantity that can change the result must either enter the cache key or be covered by a documented invariant.

For a frame sequence, content fingerprints alone cannot prove structural completeness. The sequence parser separates a stem, separator, integer frame index, padding width and file suffix. The planner rejects malformed filenames; detects repeated numeric frame IDs, mixed padding widths, mixed stems and formats; identifies missing frames in the requested inclusive interval; and rejects values outside that interval. A sequence with frames 0001 and 0003 is not valid for a requested 0001–0003 render because frame 0002 is missing. A sequence containing panel.0001.png and panel-0001.png has two distinct paths but a duplicate logical frame number. These failures are reported deterministically before any output directory is created.

This validation is an important example of **representation invariants**. The file sequence's logical domain is a set of integer frame numbers and its source representation is a set of names. A successful parser establishes a mapping from names into the requested integer interval. A successful publication requires that the mapping is total and injective over the requested frames, and that consistent stem/format/padding policies hold. Merely checking that the number of files equals the number of expected frames is insufficient: duplicates can mask gaps.

## A safe publication is planned first, then committed at one deliberate boundary

The DCC may successfully render two frames, then fail on the third. An importer must not mistake a partially written directory for a completed asset version. This is why **dry runs**, **explicit mutation plans**, **staging** and **atomic publication** are not decorative enterprise patterns; they are mechanisms for preserving a useful invariant.

Before committing, the system constructs a Plan object. It contains the input identities, validated frame range, canonical destination, stable diagnostics and run ID. Creating the plan performs reads and hashing but no writes to the workspace. The Plan's safe_to_publish property is false if any error diagnostic exists. This is the **dry-run** stage: application code can display exactly which source assets would be published, why a plan cannot proceed, and what output identity it would create.

When publication is explicitly requested, the laboratory creates a unique temporary staging directory **inside the same workspace parent**. It rereads and verifies source hashes, copies each source into staging, flushes/fsyncs each file and independently checks the staged hashes. It writes a deterministic versioned manifest. Only after the staging tree is complete does it rename the staging directory to the final, previously unused version destination. If an exception is raised before promotion, the staging directory is removed. Neither the source files nor an older published version need to be rewritten.

The critical implication is that **atomic visibility is narrower than full transactional durability**. A rename within one filesystem can make a completed new directory visible at once to cooperating readers, but a directory containing many files cannot be made into a universally crash-durable transaction just by calling rename. Cross-filesystem moves do not share the same atomicity; concurrent writers can race; existing nonempty directory replacement has different platform rules; power-loss durability may require syncing directories and respecting filesystem semantics. This laboratory intentionally publishes only new immutable version names and requires an external single-writer policy. It does not claim to solve distributed transactions, adversarial filesystem races or power-loss recovery.

**Idempotence** means rerunning an operation has a defined repeated-effect policy. This implementation refuses to republish an already existing immutable output version rather than silently modifying it. A production orchestrator could recognize that the existing output manifest already matches the requested plan and return its identity without copying anything; that behavior must be explicitly implemented and tested, not assumed because both runs used the same input names. Likewise, if a publication fails halfway through staging, rollback removes the staged objects; it is not legitimate to say an in-progress renderer automatically rolled back GPU resources or remote cloud uploads.

## The hosts change; the data contract should not

Now introduce the DCC hosts. A Blender object, Maya DAG path, Houdini geometry node and Nuke Read node are not the same runtime object. Each belongs to a host-specific API with its own identity, evaluation model, graph and filesystem interactions. The stable pipeline should not require a separate validation algorithm for each host.

In **Blender**, Python scripts usually access the scene through bpy, including bpy.data objects, collections, meshes, materials and textures. A mesh may be evaluated through modifiers or an evaluation dependency graph, so an export adapter must declare whether it exports authoring geometry or evaluated geometry. It must preserve object-to-world transforms, unit scale, axis convention, UV sets, normals, material references and animation state. An adapter can iterate collections and retrieve mesh data, but it should hand a neutral record to the common validator instead of reimplementing path and manifest checks in each Blender script. The current laboratory does not import bpy or execute an actual .blend file.

In **Maya**, the DAG represents hierarchical transform/shape relationships; commands operate on named nodes, while DG connections determine data dependency. A mesh object can have a shape beneath a transform, and two DAG paths can refer to instanced underlying geometry. The adapter must distinguish object/shape names, full DAG paths, attribute values, incoming connections and reference boundaries. A naive export script can accidentally bake the wrong transform or omit a referenced asset. A production preflight needs to detect unresolved references and establish which evaluated geometry is sent to the engine. The laboratory describes these contracts but does not execute maya.cmds or open a Maya scene.

In **Houdini**, procedural SOP or other node graphs create data that may vary by frame, node parameters, attributes, cooks and caches. The asset handoff must declare the evaluated node, geometry stream, relevant attributes and versioned cache output rather than treating the existence of a .bgeo file as proof that the intended node cooked successfully. A ROP or other output mechanism must publish the result under the same manifest and integrity rules. No Houdini process is launched by the host-neutral test.

In **Nuke**, Read and Write nodes describe image inputs and output sequences, their knobs determine paths, channels, color operations, frame bounds and other behavior, and the node graph defines processing order. A sequence may have valid files yet not match the frame range requested by the script. An adapter can inspect Read/Write nodes and relevant knobs, then produce the same frame-list manifest used for other hosts. Source color space and encoding must be declared before interpreting numerical pixel comparisons. No Nuke Python API is executed by this repository lab.

The production architecture is therefore a *ports-and-adapters* shape:

~~~text
Blender adapter     Maya adapter     Houdini adapter     Nuke adapter
      \                 |                 |                 /
       \                |                 |                /
        -> canonical asset/frame/manifest validation contract
                          |
                       dry-run plan
                          |
             stage + fingerprint + publish
                          |
                  engine import and verify
                          |
                    measured experiment
~~~

This does not mean every DCC can share a single geometry representation without loss. Mesh modifiers, instancing, skinning, material graphs, color management, simulation caches and node procedural behavior may have no lossless correspondence. The adapter must either preserve the relevant semantics, bake them under declared settings or report an unsupported transformation with a stable diagnostic. This is especially important for editable captured worlds combining meshes, TSDF fields and Gaussian representations: a rendered appearance match alone does not certify editable geometry or persistent identity.

## Engine-side verification begins with bytes but must end with meaning

Once the engine receives a published asset version, it must independently verify its manifest schema, every declared file presence and each fingerprint. The laboratory's verify_published function exercises that content-integrity check. An engine-specific importer must then validate structural and semantic contracts: mesh indices are in range; accessor offsets and strides fit buffers without overflow; normals and tangent spaces obey declared conventions; texture color channels are decoded correctly; scene hierarchy does not contain invalid cycles; animation times are well formed; resource destruction waits for GPU completion.

For meshes, the engine-side check may also recompute bounds, validate finite vertex positions, detect degeneracy, and compare independently generated geometry statistics. For glTF, imported coordinate conventions and material roughness/metallic factors should be validated against the versioned glTF specification, not against one DCC's viewport appearance. For a Gaussian PLY scene, the attribute schema, covariance/rotation representation, opacity transformation and projection convention must be specified and tested. For a TSDF, truncation convention, voxel size and coordinate transform must be in the manifest. These checks depend on the actual artifact type and are **not implemented in the Phase 30 Python frame-file validator**.

The key discipline is to trace one record through the complete chain. Take the byte sequence for a vertex position. Identify the source file and checksum, decode its component type and stride, recover its position under the DCC coordinate convention, transform it through object and world spaces, upload it under the actual shader ABI, and finally explain how it affects a covered sample and its depth. A source file hash proves the file was not silently changed; it does not prove that the engine interpreted those bytes correctly. This is the same separation between preservation and correctness used throughout AllMight.

## Performance results are not screenshots of the profiler

Having made the asset import reproducible, we can compare rendering or pipeline implementations. Define exactly what the stopwatch measures. **Wall-clock elapsed time** measures the interval observed by the caller and includes whatever waiting or overhead surrounds the measured operation. A **monotonic clock** measures elapsed durations without dependence on human wall-clock adjustments. The Python laboratory wraps a callable using perf_counter_ns and returns its result and elapsed nanoseconds. This is a timing instrument, not a calibrated benchmark.

GPU timing requires a different contract. CPU submission can return before GPU execution finishes. A CPU stopwatch around a Vulkan or Metal command submission may measure only encoding and queue work. Device timestamp queries or backend-specific GPU counter facilities measure device execution within their supported stages/clock domains; their availability, validity, timestamp period and synchronization must be checked. GPU timestamps should not be compared numerically to CPU nanoseconds without a valid domain calibration. The current host-neutral lab does **not** execute GPU commands or read timestamp queries.

A structured profiling span normally carries a run ID, operation name, start/end time, parent span, thread/queue identity, and possibly a hardware-counter snapshot. Logging severity, error codes and span context allow an investigator to tie one slow frame to one artifact/scene and reproduce it. Verbose logging can itself alter the performance path, so measurement builds should establish whether instrumentation overhead is included or controlled.

Benchmark **warm-up** has a causal purpose. The first few executions may include page faults, JIT/shader compilation, cache population, allocator initialization, GPU clock ramp-up or resource upload. A warm-up policy must be specified before results are seen. Discarding slow early runs post hoc to make a result attractive is cherry-picking. For a renderer, report cold-start separately when startup is relevant to the user.

For measured runtimes \(t_1,\dots,t_n\), the arithmetic mean is \(\bar t=\frac{1}{n}\sum t_i\). The median is the central order statistic. The mean is affected by rare long stalls; the median better describes a typical execution under many distributions but can conceal tail latency. Percentiles such as p90 and p99 express tail behavior, but with only five observations, the empirical p99 is simply the maximum under a nearest-rank definition. It would be misleading to present five samples as a precise claim about the true 99th percentile. The lab records its particular nearest-rank convention and reports count, mean, median, p90, p99, minimum and maximum. It does not calculate confidence intervals or performance significance.

A valid benchmark should also state hardware, compiler flags, backend, memory placement, input size/distribution, concurrency, power policy, measurement window, repeated-run plan and independent variability. For serious comparative claims, randomized/interleaved A/B ordering and uncertainty analysis reduce sensitivity to time-dependent machine conditions. For microbenchmarks, prevent compiler dead-code elimination by consuming observable results and compare equal work. A tiny numerical difference may be more relevant than a large performance change if the optimized version violates image quality or physics stability.

## Image quality measurements require a data model

Assume two equally shaped arrays of *linear* floating-point pixel channel values, with \(N\) scalar channels each. The mean-squared error is

\[
\operatorname{MSE}=\frac{1}{N}\sum_{i=1}^{N}(R_i-T_i)^2.
\]

Every symbol must be declared: \(R_i\) is one reference channel, \(T_i\) is the corresponding test channel after alignment and linear decoding, and \(N\) counts channels, not necessarily pixels. The comparison must ensure the same spatial crop, exposure, color primaries/transfer function, channel ordering and alpha interpretation. Comparing encoded sRGB values as though they were linear irradiances changes the meaning of MSE.

For an explicitly declared maximum channel value \(L\), the peak signal-to-noise ratio is

\[
\operatorname{PSNR}=10\log_{10}\frac{L^2}{\operatorname{MSE}}.
\]

If the images are identical, MSE is zero and PSNR tends to positive infinity, which the laboratory returns. With reference [0,1], test [0,0] and \(L=1\), MSE is 0.5 and PSNR equals \(10\log_{10}2\approx3.0103\) dB. This synthetic witness is a formula check, not a perceptual-quality claim.

**Exact pixel difference** counts discrete channel values that are not identical. It can be important for deterministic rasterization or serialization tests, but small legal floating-point and backend differences may make exact equality inappropriate for other workloads. **SSIM** compares local luminance, contrast and structure under selected window/scaling policies; it can sometimes track perceptual structure better than MSE, yet it is not an infallible human-judgment model, does not verify geometry, and can reward a blurry or temporally unstable result depending on the scene. A more complete real-time rendering experiment might include LPIPS, temporal flicker, disocclusion error, silhouette alignment, normal/depth validation and task-specific metrics. Their implementations and interpretations require separately cited protocols.

The lab computes MSE, PSNR and exact mismatch for plain arrays; it does **not** decode PNG/EXR, compute SSIM, align cameras or judge temporal consistency. This is exactly why the validation boundary must be written down. A PSNR number with no declared pixel domain is not a reproducible graphics result.

## A benchmark only becomes research when it can falsify a claim

Suppose a new rendering system claims that its uncertainty-aware Gaussian proxy improves geometry editing while preserving visual quality. That is not yet a research hypothesis. We must specify the baseline, measured quantities, dataset and falsifiable direction of change. For example: under a fixed set of captured scenes, cameras, optimizer budget and GPU model, does the uncertainty-aware method reduce edit-region geometry error at a fixed rendering cost, compared with the same system with uncertainty weighting disabled?

The **engineering objective** is to build a working implementation that completes the task. The **research question** asks what is true about an algorithm or system under specified conditions. A working implementation can fail to improve the baseline; it can still be good engineering, but the research claim has not been demonstrated.

A useful experiment defines a null/default behavior, a primary metric, secondary metrics, units, data splits and a decision rule *before* the results are inspected. Hold fixed the elements that could confound the comparison: camera calibration, asset preprocessing, scene subset, random seeds where applicable, sample counts, GPU architecture, training budget, warm-up and evaluation protocol. If a new method changes both an estimator and the sampling budget, a performance or error difference cannot be attributed exclusively to the estimator.

**Ablation** isolates a component. Start with the full method and remove one component at a time, or start with the baseline and add one component at a time under the same budget. One-variable-at-a-time experiments explain local causality but can miss interactions: two changes may only help together. Factorial or targeted interaction studies may be necessary when components are coupled. Avoid selecting only attractive camera views, cherry-picked scenes or convenient random seeds. Clearly separate **measured observations** from synthetic fixtures used for unit tests; synthetic smoke tests can establish code correctness for a special case without establishing generalization or human-perceptual benefit.

For the uncertainty-aware renderer, a strong study records every scene split and excluded failure, error distributions rather than only a mean, per-scene cost/quality tradeoffs, memory use, and negative or inconclusive cases. For a collision broadphase, compare the same trajectories and primitive distributions, count actual candidate pairs and narrowphase calls, measure update versus query time, and include degenerate/high-contact scenes. Never present a reduction in candidate pairs alone as evidence of an end-to-end speedup if the partition maintenance cost exceeded the savings.

**Statistical uncertainty** matters especially when only a few runs can be afforded. A small sample mean has high uncertainty; if runs share the same scene and seed, they are not independent evidence of broad applicability. Confidence intervals or bootstrap intervals require a clear sampling unit. For per-scene paired comparisons, consider paired differences rather than treating every frame from a scene as an independent experimental subject. State whether uncertainty reflects run-to-run noise, scene-to-scene variability or training initialization—these are different quantities.

## Claims must be traceable backward to actual evidence

Build a **provenance chain**: source input hash -> transformation/version/options -> intermediate cache hash -> final output hash -> measurement script/version -> metric and report. Each chain should include the observation type. A command that compiled successfully demonstrates syntactic/linking feasibility under the tested toolchain. A passing unit test establishes behavior only for covered cases. An image comparison supports a claim about a declared pixel domain and dataset. A user study supports claims about its participants and procedure, not arbitrary graphics-engine correctness.

The presentation layer is downstream from this evidence. A beautiful figure is not a substitute for verified input records. Likewise, the audit ledger should never interpret a saved research-paper excerpt as proof that a corresponding engine implementation currently contains the described algorithm. The actual source revision, code path, configuration and executed checks must be inspected before converting a conjecture into a verified statement.

A reproducibility package should contain the method implementation or reproducible build instructions, exact dependency versions, tested platform, parameter configuration, dataset IDs and permitted access route, source/derived file fingerprints, seeds, analysis scripts, raw metric tables, failed runs and plotting instructions. If a file or proprietary dataset cannot be redistributed, disclose the limitation rather than manufacturing an equivalent-looking trace.

When reading a paper, begin with its assumptions and problem definition. Reconstruct the notation, derive the objective and investigate units and limiting cases. Determine whether an estimator is biased, whether a convergence proof uses assumptions the engine violates, and whether the reference implementation contains numerical safeguards absent from the pseudocode. To reimplement responsibly, build a slow oracle on a tiny analytically tractable case, compare intermediates, then optimize. If code disagrees with an equation, identify whether the paper contains an approximation, a different coordinate convention or an implementation-specific stabilization before changing either one.

## The oral capstone: reconstruct one unknown system, not a glossary

Now imagine a reviewer provides a small unfamiliar renderer that loads a mesh, creates a hierarchy, computes contact candidates, submits geometry to a GPU backend, and measures a frame. The repository is initially closed. You must reason from observable behavior, documented contracts and simple test cases, and then inspect the implementation to confirm or reject your predictions.

The reconstruction starts with a **datum**, not an acronym. Pick the mesh vertex at index 17. State its source offset and component format, its owner after loading, its physical memory address lifetime, its transform convention, and which GPU resource and shader input eventually consume it. If the shader produces a clip-space point, derive the projection and tell the reviewer which operations preserve projective equivalence and which do not. If the point is behind the near plane, predict the clipping behavior. If the mesh undergoes skeletal animation, identify when morph deformation and skinning occur and what previous-frame data is needed for velocity.

Next choose a contact candidate. Explain how a BVH query can emit a potential pair but cannot by itself establish physical overlap or a stable contact manifold. Derive a contact Jacobian from relative point velocity, compute the inverse effective mass, explain why the normal impulse is clamped to nonnegative accumulated force and why a friction impulse is limited by the normal impulse. Trace the cache identity across frames and show what goes wrong if a geometric feature changes but the cached impulse is reused. Then explain how the engine prevents one worker from writing the same body velocity concurrently with another solver task.

Next choose one render pass. Draw its actual resource lifetime: creation, CPU visibility, upload, descriptor/reference binding, command recording, GPU execution, synchronization and retirement. State which operations run concurrently and which dependencies must exist for memory visibility, not merely execution order. A render graph's dependency edge cannot automatically replace all API-specific barrier requirements. If the pass writes history for TAA, explain the validity conditions after camera cuts, resolution changes and proxy/representation edits.

For **any hot loop**, give five numerical quantities before claiming performance: operations per element, bytes moved per element, number of allocations, synchronization events and expected parallel scheduling grain. From those derive a lower bound under the relevant compute or bandwidth model; then compare to measured wall/GPU time. An algorithm asymptotically O(N) may still be dominated by cache misses, branch divergence, atomic contention or one expensive global allocation.

The strongest response to repeated 'why?' is to descend to the next lower contract. Why is a handle safe? Because lookups validate identity and generation. Why is generation enough only within a pool? Because two catalogs may reuse the same slot/generation. Why might a typed handle still be unsafe on GPU? Because a CPU liveness check says nothing about GPU completion. Why is a fence needed? Because producer/consumer memory visibility requires a defined dependency. Why might the fence be insufficient? Because the queue and resource ownership model may require additional barriers or signaling. A word such as 'synchronization' is not itself a proof.

Finally compare **at least three designs**, each under the same semantics. For asset ownership, contrast raw pointers, generation-checked pools and stable-reference indirection; show their memory/CPU cost, invalidation, debugging and concurrency tradeoffs. For broadphase, contrast naive all-pairs, uniform grids and BVHs under sparse, clustered and rapidly moving scenes. For rendering, contrast conventional rasterization, exact ray tracing and Gaussian proxy composition in regimes where each is appropriate. A research-capable answer does not force one winner across all workloads; it states a falsifiable rule for choosing one.

The final oral task is therefore to **defend, derive, implement, profile, debug and redesign** an unfamiliar subsystem from first principles. A useful assessment lets the reviewer change one assumption at a time: increase N tenfold, change scene scale, remove temporal coherence, change the coordinate convention, force a GPU device loss, alter color space, insert a stale handle or make an allocator throw. The candidate should predict which invariants still hold, which tests fail and what design modification is justified. The objective is not memorizing a large library of jargon; it is being able to reconstruct the system when the vocabulary has been forgotten.
