First-use completion — from one Gaussian’s footprint to the final pixel

The ellipse test q ≤ 9 only determines whether a projected Gaussian is a candidate contributor. It does not yet calculate the final pixel, because several Gaussians can overlap the same sample and obscure each other. For a projected Gaussian i , let q i = ( x − μ i ) T Σ 2 D , i − 1 ( x − μ i ) be its squared elliptical distance at pixel sample x ; μ i is its projected center and Σ 2 D , i is the screen covariance, assumed positive definite. The unnormalized weight is g i ( x ) = e − q i / 2 . If its stored opacity is o i ∈ [ 0 , 1 ] , a common splatting convention defines the effective sample opacity as

α i ( x ) = min ( α max , o i e − q i / 2 ) ,

where α max < 1 may be a deliberate numerical clamp. The cutoff and clamp are separate approximations: q i > 9 skips the contribution, whereas the clamp caps the contribution of a retained Gaussian. Neither operation turns the Gaussian into an opaque mesh surface.

With overlapping splats, order them from near to far using one declared camera-depth convention. Reversed-Z may encode near objects with a larger stored depth, so blindly sorting an API depth value ascending is not universally front-to-back. For the sorted contributors, let T 0 = 1 be the fraction of light not yet blocked, and let C 0 = ( 0 , 0 , 0 ) be accumulated linear RGB. For the next Gaussian:

C i + 1 = C i + T i α i c i , T i + 1 = T i ( 1 − α i ) .

Here c i is its view-dependent RGB contribution in the declared linear working space. A background C b g enters after the last contributor as C = C n + T n C b g . This is front-to-back premultiplied-alpha compositing written without pretending that stored Gaussian colors were already premultiplied. The product form

T i = ∏ j < i ( 1 − α j )

explains the recurrence: a farther Gaussian contributes only through the surviving transmittance from every nearer one.

For two overlapping center samples, take a near red splat with α 0 = 0.6 , and a far blue splat with α 1 = 0.5 . Start with T = 1 , C = ( 0 , 0 , 0 ) . Red contributes ( 0.6 , 0 , 0 ) and leaves T = 0.4 . Blue contributes only 0.4 ( 0.5 ) ( 0 , 0 , 1 ) = ( 0 , 0 , 0.2 ) , leaving T = 0.2 . The result before background is C = ( 0.6 , 0 , 0.2 ) . Reverse the order and you obtain C = ( 0.3 , 0 , 0.5 ) , still with T = 0.2 . Thus sorting is a visible mathematical requirement, not an optional optimization. Overlapping equal-depth or intersecting splats require a declared approximation/tie policy; one global center-depth ordering cannot reproduce all possible volumetric occlusion.

#include <array>
#include <algorithm>
#include <cmath>
#include <span>

struct SplatSample {
    double ellipticalDistanceSquared; // q, already computed in screen space.
    double opacity;                    // Stored amplitude in [0,1].
    std::array<double, 3> linearRGB;   // At this viewing direction.
};

struct PixelState {
    std::array<double, 3> linearRGB{0.0, 0.0, 0.0};
    double transmittance = 1.0;
};

// Caller guarantees near-to-far order, finite inputs and valid opacities.
// This CPU reference deliberately shows the exact sequential dependency.
PixelState composite_front_to_back(std::span<const SplatSample> sorted)
{
    PixelState pixel;
    for (const SplatSample& s : sorted) {
        const double q = s.ellipticalDistanceSquared;
        if (q > 9.0) continue; // Explicit 3-sigma squared-distance policy.
        const double alpha = std::clamp(s.opacity * std::exp(-0.5 * q),
                                        0.0, 0.999);
        for (int channel = 0; channel < 3; ++channel)
            pixel.linearRGB[channel] +=
                pixel.transmittance * alpha * s.linearRGB[channel];
        pixel.transmittance *= (1.0 - alpha);
        if (pixel.transmittance < 1e-4) break; // Declared approximation.
    }
    return pixel; // Add T * background before display encoding.
}

Why stop at a small T ? If every remaining source and the background have channels in [ 0 , 1 ] , the maximum missing residual contribution in any channel is bounded by the surviving T . Stopping at 10 − 4 therefore gives a conditional channel-error bound of at most 10 − 4 in that working range; unbounded HDR radiance has no such numerical error bound without an additional radiance limit. Likewise, q ≤ 9 encloses 1 − e − 9 / 2 ≈ 98.89 % of the total probability mass of an ideal normalized two-dimensional Gaussian. That is not a guarantee about image error: learned amplitudes, overlap, colors, sorting and pixel footprints affect the actual rendered result. Keep the cutoff a measured quality/performance parameter.

A GPU tile renderer can assign Gaussian references to screen tiles and sort the tile’s references by depth, but it must still evaluate each pixel’s q i , opacity, RGB and the recurrence above. The tile list is a conservative candidate structure, not a composited pixel. A prefix sum builds disjoint reference ranges; sorting and sequential transmittance then answer a different question. For correctness, compare a scalar CPU oracle against the GPU’s color and T on tiny scenes with one splat, two reversed-order splats, zero opacity, footprint cutoff, overlapping centers, invalid covariance and early termination. The first-use C++ witness (Mathematics for Visual Computing, Part 1, Ch. 1) checks the two-splat numeric example. First-use completion — schedule the projected ellipse into actual tile work

We already know the screen-space center, conic, bounding radius, depth, color and source identity. A projected Gaussian is now a bounded screen-space workload. The remaining questions are concrete: which pixels might it affect, how do GPU threads find the Gaussians relevant to their tile without testing every Gaussian in the scene, and how do those contributors reach the pixel in an order suitable for transmittance compositing? We can answer them here, without deferring tiling and sorting to another numbered pass.

Let a render target have width W , height H , and square tile width T pixels. Give tiles integer coordinates ( t x , t y ) , with 0 ≤ t x < ⌈ W / T ⌉ and 0 ≤ t y < ⌈ H / T ⌉ . The conservative circular bound derived from the screen covariance is a circle of radius r = 3 λ max around projected center ( u , v ) . The actual Gaussian ellipse may cover much less area; the circle is useful because it allows cheap rejection without missing the entire three-sigma ellipse. Clip its screen rectangle to the viewport. If the rectangle is empty, the Gaussian contributes no tile references.

For a nonempty clipped rectangle, conservatively map the minimum and maximum screen coordinates to tile indices by dividing by T and taking the floor, clamped to valid tile coordinates. The exact upper-bound formula depends on whether the rectangle uses inclusive or exclusive pixel bounds. Never mix conventions: using an exclusive upper bound with an inclusive floor can either generate an unnecessary extra tile or, worse, omit a boundary sample after a mismatched clamp. Conservative overcount only wastes work; undercount removes contributions.

For example, let W = H = 64 , T = 16 , the center be ( 20 , 20 ) and radius be 10 pixels. Its bound runs from coordinate 10 through 30 on each axis, so it intersects tile columns 0 and 1 and tile rows 0 and 1. It emits four references, one each for tiles ( 0 , 0 ) , ( 1 , 0 ) , ( 0 , 1 ) , ( 1 , 1 ) . Those references do not copy the full Gaussian record: they name the Gaussian (by a stable index or validated handle) and the tile that may need it.

A scalable implementation is a count–scan–scatter pipeline. In the count stage each visible Gaussian reports how many tile references it requires. Suppose three Gaussians request counts [ 2 , 0 , 1 ] . An exclusive scan constructs offsets [ 0 , 2 , 2 , 3 ] . The first Gaussian owns output slots 0 and 1, the second owns an empty range beginning and ending at 2, and the third owns slot 2. The last offset is the required capacity K = 3 . This is a memory-allocation proof: before scattering, the producer knows how many references exist and which nonoverlapping range belongs to each Gaussian. A parallel GPU scan must establish that these offsets are ready before the scatter dispatch reads them. A workgroup barrier alone does not complete a cross-workgroup scan.

stable_sort(references, by tile_id then near_to_far_depth then tie_policy)
for each tile:
    for each pixel sample in tile:
        C = (0,0,0); transmittance = 1
        for each reference of this tile in the established depth order:
            compute conic distance q for this pixel and referenced Gaussian
            if q > cutoff: continue
            alpha = opacity * exp(-q/2), with declared clamping
            C += transmittance * alpha * linear_color
            transmittance *= (1-alpha)
            if transmittance < cutoff_T: break
        C += transmittance * linear_background

This pseudocode makes each intermediate state explicit. Count is one integer per input Gaussian. Scan owns a prefix array of N + 1 entries. Scatter writes exactly K = ∑ i c o u n t i references. Sort groups those references by tile and establishes the compositing order. Raster evaluates the actual conic at individual pixel samples, eliminating false positives left by the conservative tile bound. The tile list is therefore an acceleration structure for contributors, not a final visibility answer.

A naive renderer considers all N splats for each of the M tiles, producing O ( N M ) potential pair tests. A tiled pipeline instead emits K actual overlap references and sorts or bins them. A small compact Gaussian can touch very few tiles; a giant close-up Gaussian can touch nearly all of them. This changes both the asymptotic work and the memory budget. Use a counter width that can represent the total K , check multiplication/addition overflow, and set a deliberate policy for unreasonably large footprints. Prefix-sum and sorting are not free, so on small workloads the simplest CPU or GPU path may still be faster. Measure count, scan, scatter, sort and raster time separately.

Depth ordering is not implied by the GPU’s stored depth convention. Choose a monotone near-to-far key in the declared camera space, then encode or compare it consistently. A reversed-Z depth buffer, a positive-Z computer-vision camera and a negative-Z graphics camera may all represent the same physical scene with different numeric depth order. At equal depths use a deterministic tie policy if reproducibility matters, while recognizing that per-Gaussian center-depth sorting is only an approximation when spatially extended kernels intersect.

Finally, the dependency graph is executable, not decorative: projected records must be ready before count; scan must finish before scatter; references must be complete and sorted before raster; and output attachments must survive until the final consumer. The source Gaussian buffer must remain allocated while references still contain its indices. A resize invalidates tile geometry and may require reallocation. An edit that changes Gaussian count, covariance, opacity or camera pose requires rebuilding the affected candidate ranges; reusing old ranges without a proof of conservativeness can silently remove pixels.

The immediate reconstruction test is now possible: for the 64-by-64 target, independently enumerate the four tile coordinates of the ( 20 , 20 ) radius-10 Gaussian, verify the count–scan–scatter ranges on [ 2 , 0 , 1 ] , and compare the final two-Gaussian pixel against the earlier front-to-back CPU oracle. This proves separate facts about indexing, memory safety, order and color rather than accepting one plausible-looking screenshot as evidence for every stage.

The current Maveb path is unusually useful pedagogically because its CPU oracle and Metal implementation track one another closely. The canonical asset preserves trained log-scale/logit values; PLY loading is strict and supports ASCII and binary little-endian; quaternion normalization and SH degrees 0–3 are explicit; CPU and GPU construct R d i a g ( s 2 ) R T , transform it into camera space, use the analytically derived perspective Jacobian, add the same 0.3 I low-pass covariance, invert the same 2×2 matrix and use the same three-sigma maximum-eigenvalue bound.
