Monte Carlo convergence test

Suppose ground-truth/reference image is:

R .

Render:

I 1 ,   I 4 ,   I 16 ,   I 64 ,   I 256 .

Compute errors:

E N .

For ordinary Monte Carlo we expect approximately:

E N ∝ 1 N .

Thus quadrupling samples should approximately halve stochastic error.

Do not assert strict monotonic error per single realization

Because rendering is stochastic, it is possible:

E 64 > E 16

for one particular random sample set even when the estimator is perfectly correct.

A robust convergence test can:

  • use nested sample prefixes,
  • average across several seeds,
  • test approximate slope statistically,
  • assert high-SPP error is substantially below low-SPP error rather than every step monotonically improving.

The mathematical convergence trend matters more than one accidental fluctuation.

Log-log convergence slope

Take:

log ⁡ E N

versus:

log ⁡ N .

If:

E ∝ N − 1 / 2 ,

then:

log ⁡ E = − 1 2 log ⁡ N + C .

Expected slope for root-mean-square error with finite variance and independent samples:

− 0.5 .

Mean-square error instead has expected slope − 1 . Correlated sampling, heavy tails and reference noise can change the observed curve; a plateau is a diagnostic clue, not proof of a particular bug.

This is a surprisingly powerful test.

If the curve stops dropping and plateaus:

you likely hit bias .

Examples:

  • wrong BRDF,
  • incorrect MIS,
  • fixed-depth truncation,
  • clamping,
  • missing indirect path family.

Duplicate AABB testing

Current closest traversal tests a node when popped.

For an internal node, it then tests both child AABBs to determine near/far ordering.

Those children are pushed.

When a child is later popped, its AABB is tested again.

So child bounds can be evaluated twice.

A traversal stack can instead store:

{ nodeIndex, tNear }

and avoid repeating a test already performed at the parent.

This trades stack size for fewer slab tests.

Benchmark it.

Precompute inverse direction

AABB slab intersection repeatedly computes:

1 D x , 1 D y , 1 D z .

A ray traversal can precompute:

i n v D = ( 1 / D x , 1 / D y , 1 / D z )

and signs once.

Then each box intersection becomes mostly:

  • subtract,
  • multiply,
  • min/max.

Across dozens of AABB tests per ray, that matters.

Handle zero/near-zero components carefully.

Node memory layout

Traversal performance is often memory-bound.

A BVH node should be compact.

Each unnecessary byte means fewer nodes per cache line.

Potential improvements include:

32-byte nodes , implicit child indices , leaf bit packing , contiguous depth-first layout .

A sophisticated CPU renderer may use:

B V H 4

or:

B V H 8

instead of binary BVH so SIMD lanes test several child boxes simultaneously.

BVH4/BVH8 intuition

Binary node:

2

8

This can improve:

  • traversal depth,

Triangle intersection optimization

Möller–Trumbore currently recomputes:

E 1 = B − A , E 2 = C − A

for every test unless geometry representation has them precomputed.

For static ray-tracing meshes, store triangle data optimized for intersection rather than only traditional raster vertex/index representation.

Possible representations precompute:

A , E 1 , E 2

or use specialized watertight intersection formulations.

The best representation depends on memory bandwidth and SIMD strategy.

Watertight triangle intersection

Möller–Trumbore can produce precision inconsistencies on shared edges.

Two adjacent triangles may disagree about whether a ray exactly on their common edge intersects.

This can create tiny cracks.

Production ray tracers often use watertight ray-triangle intersection algorithms designed so adjacent triangles agree under floating-point arithmetic.

That becomes important for:

  • distant geometry,
  • large coordinate magnitudes,
  • shadow rays,
  • thin meshes.

Packet ray tracing

A CPU SIMD core can process multiple rays together.

A packet:

R 0 , R 1 , R 2 , R 3

for SSE-like 4-wide processing, or larger vectors for AVX.

Store origins as structure of arrays:

Ox = [Ox0 Ox1 Ox2 Ox3 ...]
Oy = [Oy0 Oy1 Oy2 Oy3 ...]
Oz = [...]

Then AABB computations operate on multiple rays in one SIMD instruction.

Why primary rays make good packets

Neighboring primary pixels have coherent directions.

They tend to traverse similar BVH nodes.

Therefore a packet can traverse:

one node

for many rays simultaneously.

This improves SIMD utilization.

Shadow rays toward the same light can also be coherent.

Why diffuse path rays destroy packet coherence

After a diffuse bounce:

ω i

is randomly sampled.

Neighboring camera paths can fly in completely different directions.

Then within one packet:

ray 0 → left subtree
ray 1 → right subtree
ray 2 → miss
ray 3 → left

SIMD lanes diverge.

Eventually packet tracing can spend time processing inactive lanes.

This is one reason packet tracing is more naturally effective for coherent primary/secondary rays than for deep diffuse path tracing.

Megakernel path tracing

The simplest GPU design:

One GPU thread owns one path.

It performs:

intersect
shade
sample light
shadow
sample BSDF
repeat

inside one large shader/kernel.

This is called a megakernel architecture.

Advantages:

  • simple path state,
  • low queue traffic,
  • straightforward control flow.

Disadvantage:

Different threads take different branches and bounce counts.

SIMT divergence can become severe.

Suppose a GPU warp/wave contains:

lane 0 → diffuse
lane 1 → mirror
lane 2 → glass
lane 3 → miss
...

The GPU may have to execute multiple branch paths while masking inactive lanes.

So although each ray is independent logically, executing all ray types together can waste hardware throughput.

Wavefront path tracing

400 k

100 k

500 k

Wavefront compaction can process homogeneous batches.

That improves:

Especially on GPUs.

Queues require:

  • memory for path state,
  • atomic/parallel append,
  • compaction,
  • synchronization,
  • more global memory traffic.

So wavefront is not automatically faster.

For short coherent workloads, a megakernel may win.

For deeply divergent, complex BSDF workloads, wavefront often becomes attractive.

Core BSDF interface

enum class BSDFEvent : uint32_t
{
    None         = 0,
    Diffuse      = 1 << 0,
    Glossy       = 1 << 1,
    Delta        = 1 << 2,
    Reflection   = 1 << 3,
    Transmission = 1 << 4
};

struct BSDFSample
{
    Vec3 Wi;

    Color F;

    // Directional density in sr^-1 for continuous lobes.
    // For delta events this field follows the renderer's
    // chosen discrete/delta convention.
    float Pdf = 0.0f;

    BSDFEvent Event =
        BSDFEvent::None;

    float Eta = 1.0f;

    [[nodiscard]]
    bool IsDelta() const
    {
        return HasFlag(
            Event,
            BSDFEvent::Delta);
    }
};

Complete MIS-ready path loop

Color TracePath(
    const Scene& scene,
    Ray ray,
    Sampler& sampler)
{
    Color L =
        Color::Black();

    Color beta =
        Color::White();

    MediumStack media =
        MediumStack::Air();

    // Data needed to MIS-weight a light/environment
    // reached by the previous BSDF sample.
    float previousBSDFPdf = 0.0f;
    bool previousWasDelta = true;

    for (uint32_t bounce = 0;
         bounce < MaxDepth;
         ++bounce)
    {
        //-----------------------------------------------------
        // 1. Closest visibility query.
        //-----------------------------------------------------
        const auto hit =
            scene.IntersectClosest(ray);

        //-----------------------------------------------------
        // 2. Environment miss.
        //-----------------------------------------------------
        if (!hit)
        {
            const Color Le =
                scene.EnvironmentRadiance(
                    ray.Direction);

            if (bounce == 0 ||
                previousWasDelta)
            {
                L +=
                    beta * Le;
            }
            else
            {
                const float lightPdf =
                    scene.EnvironmentPdf(
                        ray.Direction);

                const float weight =
                    PowerHeuristic(
                        previousBSDFPdf,
                        lightPdf);

                L +=
                    beta *
                    Le *
                    weight;
            }

            break;
        }

        const Material& material =
            scene.Material(
                hit->MaterialIndex);

        const Vec3 wo =
            -ray.Direction;

        //-----------------------------------------------------
        // 3. Surface emission.
        //-----------------------------------------------------
        if (material.IsEmitter())
        {
            const Color Le =
                material.Emission;

            if (bounce == 0 ||
                previousWasDelta)
            {
                L +=
                    beta * Le;
            }
            else
            {
                const float lightPdf =
                    scene.PdfLightHit(
                        ray,
                        *hit);

                const float weight =
                    PowerHeuristic(
                        previousBSDFPdf,
                        lightPdf);

                L +=
                    beta *
                    Le *
                    weight;
            }
        }

        //-----------------------------------------------------
        // 4. Explicit direct-light sample.
        //
        // Skip ordinary NEE for pure delta BSDFs because an
        // arbitrary light direction has zero BSDF support.
        //-----------------------------------------------------
        if (!material.IsPureDelta())
        {
            const LightSample light =
                scene.SampleOneLight(
                    *hit,
                    sampler);

            if (light.Pdf > 0.0f)
            {
                const float cosTheta =
                    std::max(
                        Dot(
                            hit->ShadingNormal,
                            light.Wi),
                        0.0f);

                if (cosTheta > 0.0f)
                {
                    const Ray shadow =
                        SpawnShadowRay(
                            *hit,
                            light.Wi,
                            light.Distance);

                    if (!scene.Occluded(shadow))
                    {
                        const Color f =
                            EvaluateBSDF(
                                material,
                                *hit,
                                wo,
                                light.Wi,
                                media);

                        const float bsdfPdf =
                            PdfBSDF(
                                material,
                                *hit,
                                wo,
                                light.Wi,
                                media);

                        const float misWeight =
                            light.Delta
                            ? 1.0f
                            : PowerHeuristic(
                                light.Pdf,
                                bsdfPdf);

                        L +=
                            beta *
                            f *
                            light.Radiance *
                            (
                                cosTheta *
                                misWeight /
                                light.Pdf
                            );
                    }
                }
            }
        }

        //-----------------------------------------------------
        // 5. Sample the BSDF to continue the path.
        //-----------------------------------------------------
        BSDFSample bs =
            SampleBSDF(
                material,
                *hit,
                wo,
                media,
                sampler);

        if (!bs.IsValid())
            break;

        //-----------------------------------------------------
        // 6. Throughput update.
        //-----------------------------------------------------
        if (bs.IsDelta())
        {
            // Delta BSDF routines normally return an F/PDF
            // convention already designed for the exact event.
            beta *=
                bs.F /
                bs.Pdf;
        }
        else
        {
            const float cosine =
                std::abs(
                    Dot(
                        hit->ShadingNormal,
                        bs.Wi));

            if (cosine <= 0.0f ||
                bs.Pdf <= 0.0f)
            {
                break;
            }

            beta *=
                bs.F *
                (cosine / bs.Pdf);
        }

        if (!IsFinite(beta) ||
            MaxComponent(beta) <= 0.0f)
        {
            break;
        }

        //-----------------------------------------------------
        // 7. Update medium ONLY after transmission.
        //-----------------------------------------------------
        if (HasFlag(
                bs.Event,
                BSDFEvent::Transmission))
        {
            UpdateMediumStack(
                media,
                *hit,
                material);
        }

        previousWasDelta =
            bs.IsDelta();

        previousBSDFPdf =
            bs.Pdf;

        //-----------------------------------------------------
        // 8. Spawn robustly offset next ray.
        //-----------------------------------------------------
        ray =
            SpawnSurfaceRay(
                *hit,
                bs.Wi,
                HasFlag(
                    bs.Event,
                    BSDFEvent::Transmission));

        //-----------------------------------------------------
        // 9. Russian roulette.
        //-----------------------------------------------------
        if (bounce >= 3)
        {
            const float survival =
                std::clamp(
                    MaxComponent(beta),
                    0.05f,
                    0.95f);

            if (sampler.Next1D(
                    SampleDimension::Roulette) >
                survival)
            {
                break;
            }

            beta /=
                survival;
        }
    }

    return L;
}

∫ p ( ω ) d ω = ? 1.

BRDF fault isolation

Use known directions.

Test:

f ≥ 0.

For reciprocal BRDF:

f ( ω i , ω o ) ≈ f ( ω o , ω i ) .

Numerically integrate hemispherical reflectance:

∫ f ( ω i , ω o ) cos ⁡ θ i d ω i ≤ 1 + ϵ .

Use reference spheres.

Use white-furnace tests.

If the BSDF itself is wrong, no sampler can repair it.

White furnace test

Place material inside a uniform unit-radiance environment:

L i = 1.

For a perfectly energy-conserving opaque material with no absorption in the considered model, outgoing result should not exceed expected energy bounds and should exhibit predictable behavior.

This is especially useful for:

  • microfacet energy conservation,
  • layered materials,
  • transmission models.

If roughness changes cause unexplained brightness gain/loss, the furnace test exposes it.

Visibility fault isolation

Disable occlusion temporarily.

If direct lighting becomes correct, investigate shadow rays.

Check:

t min , t max , origin bias , any-hit BVH , light distance .

Compare:

Occluded B V H

against brute force.

Visibility bugs often look like BRDF bugs because they simply remove or add radiance.

Accumulation fault isolation

Render one deterministic sample and inspect it directly.

Then render the same sample through progressive accumulation.

They should agree.

Verify:

μ n = 1 n ∑ X i .

Make sure tone mapping is not inside the accumulation loop.

Check sample count.

Check whether pass restarts accidentally reuse identical sample sequences.

Check for NaN/Inf.

A perfectly correct path contribution can be destroyed by incorrect accumulation.

Rendering equation and numerical integration

At surface point x , outgoing radiance in direction ω o consists of emitted light and reflected incoming light:

L o ( x , ω o ) = L e ( x , ω o ) + ∫ Ω f r ( x , ω i , ω o ) L i ( x , ω i ) | n ⋅ ω i | d ω i .

L e is emitted radiance, L i incoming radiance, f r the BRDF, n the normal, and Ω the hemisphere above the surface. The cosine accounts for projected area. Visibility determines whether geometry blocks a sampled direction. Incoming radiance depends on radiance leaving other surfaces, so the equation is recursive. Expanding it produces paths of light bounces: direct light reaches a surface then camera; indirect light includes more interactions. The transport equation remains the same for every material; material response changes through the BRDF. Fresnel reflection makes many dielectrics more reflective at grazing angles. CMU-16 (Vision, XR, and Playable Worlds, Part 1, Ch. 5)

An integral accumulates a continuous range of contributions. Midpoint quadrature evaluates the center of each interval; trapezoidal quadrature joins endpoint samples; Simpson’s rule fits a quadratic. These deterministic rules work well for smooth low-dimensional functions. Visibility boundaries create discontinuities, and multidimensional light paths become expensive for tensor grids: m samples per dimension require m d evaluations in dimension d . CMU-17 (Vision, XR, and Playable Worlds, Part 1, Ch. 5)

Monte Carlo integration uses random samples. If X is drawn from density p ( x ) , then

∫ f ( x ) d x = E [ f ( X ) p ( X ) ] ≈ 1 N ∑ i = 1 N f ( X i ) p ( X i ) .

The weighting follows from expectation: E [ f ( X ) / p ( X ) ] = ∫ ( f ( x ) / p ( x ) ) p ( x ) d x = ∫ f ( x ) d x . Density must be positive wherever f contributes and measured in the same domain as the integral. The estimator is unbiased, but random error remains. For independent samples Y i = f ( X i ) / p ( X i ) , variance of the mean is Var ( Y ) / N , so standard deviation decreases as 1 / N . Four times as many samples roughly halves noise. For a small numerical trace, integrate f ( x ) = x 2 over the unit interval; the exact answer is 1 / 3 . Uniform samples 0.2 , 0.5 , 0.9 produce mean square ( 0.04 + 0.25 + 0.81 ) / 3 = 0.3667 . The discrepancy is sampling error. A proposal density p ( x ) that resembles the integrand makes weighted samples less variable. For f ( x ) = 2 x , the exact integral is 1. Uniform sampling has contribution 2 X and variance 1 / 3 . Sampling instead from p ( x ) = 2 x makes f ( X ) / p ( X ) = 1 for almost every sample, yielding zero variance. Real rendering integrals are more complex, but the example explains importance sampling (Mathematics for Visual Computing, Part 2, Reference notes: Monte Carlo rendering estimators and variance). From the rendering equation to paths

Use operator notation L = L e + K L , where K represents one reflection-and-visibility step. Substitution yields L = L e + K L e + K 2 L e + K 3 L e + ⋯ . The term L e is direct emission at the point. K L e includes paths that reflect once before reaching emission. K 2 L e includes two reflections, and so on. Path tracing estimates this infinite series by following random directions and accumulating weighted contributions. Absorption and energy loss usually make long-path contributions diminish, but some environments preserve light for many bounces.

Direct-light sampling selects a source and tests visibility to it. If the source is small, sampling a random hemisphere direction may almost never hit it. Conversely, sampling only the light may miss glossy paths where material response concentrates energy. The path formulation clarifies that the challenge is to place probability mass on path configurations that carry large contribution. One-bounce Monte Carlo estimator

For a surface point, estimate reflected radiance by sampling directions ω i from density p ( ω i ) and evaluating the BRDF, incoming radiance, and cosine. For N samples, the estimate is

L ^ o = L e + 1 N ∑ k = 1 N f r ( x , ω k , ω o ) L i ( x , ω k ) | n ⋅ ω k | p ( ω k ) .

Each symbol has a specific role: L e emits from the surface; f r redirects incoming light; L i is the radiance arriving from the sampled direction; n is the surface normal; p is the directional sampling density; and the cosine is projected area. Visibility is included in L i by making it zero when geometry blocks that direction. If the PDF is expressed per unit area rather than per unit solid angle, it must first be converted. CMU-16 (Vision, XR, and Playable Worlds, Part 1, Ch. 5) · CMU-18 (Vision, XR, and Playable Worlds, Part 1, Ch. 5)

The estimator is an expectation written as a sample average. If directions are drawn uniformly over a hemisphere, the probability density per unit solid angle is 1 / ( 2 π ) , because the hemisphere has solid angle 2 π . Substituting that density into the one-sample contribution multiplies the integrand by 2 π . The cosine still matters: a ray arriving nearly tangent to a surface contributes little projected flux, while a ray arriving near the normal contributes more. This gives a useful importance distribution. Since ∫ H 2 cos ⁡ θ d ω = π , the density p ( ω ) = cos ⁡ θ / π is normalized. Sampling with this density cancels the cosine in the estimator, leaving π L i for each sampled direction. The code becomes simpler and, when incident radiance is roughly constant, the samples are allocated in proportion to the part of the integrand that matters. Another proposal samples a finite area light directly. Let x be the shaded point and y a point on the emitter. Write r = ‖ y − x ‖ for their distance, and let θ y be the angle between the emitter’s normal and the direction from y toward x . A patch of emitter area d A y subtends solid angle

d ω = cos ⁡ θ y r 2 d A y .

This is a change of variables (Mathematics for Visual Computing, Part 2, Reference notes: Probability density and change of measure): the same visible set of light samples is being described on the emitter surface instead of as directions at x . Therefore the integrand must acquire the Jacobian cos ⁡ θ y / r 2 . The surface’s own projected-area cosine at x remains as well, along with visibility, which is zero when an occluder blocks the segment. With uniform area samples, the estimator multiplies the average by the emitter area. This avoids wasting most rays on empty sky when the emitter subtends only a small part of the hemisphere. In the lecture’s square-light / blocker / ground-plane comparison, 100 uniform hemisphere samples are grainy, while 100 area-light samples produce a much smoother shadow and illumination field; the area-light result remains strong at 16 samples, and even its one-sample result compares favorably to uniform sampling. The path version multiplies a throughput term by the sampled BRDF, cosine, and inverse density at each bounce. A path contribution might be written C = L e ∏ j = 1 b f j | n j ⋅ ω j | / p j . Here b is bounce count, and each factor belongs to one interaction. Long paths can have very small throughput; Russian roulette terminates them stochastically and compensates survivors by dividing by continuation probability. This is an estimator design choice, not a physical event that must occur in the scene. Why does path tracing recurse? At one surface, the rendering equation asks for incoming radiance from every direction. A ray in one sampled direction either reaches an emitter or hits another surface; in the second case, the next surface has the same integral to evaluate. Thus one random path is a chain of surface interactions from the camera toward an emitter. Even a single path estimate has the correct expected value when every sampled direction is weighted by its probability density, but individual paths are noisy; averaging many independent paths reduces variance. Limiting paths to direct illumination gives hard, dark regions wherever a surface receives no direct source. Adding indirect bounces fills some of those regions. Longer paths matter selectively: a glass lantern may look black if paths stop before the sequence of reflection and refraction events that transports light through it, while four-bounce paths can reveal its glass structure. CMU-18 (Vision, XR, and Playable Worlds, Part 1, Ch. 5)

Russian roulette makes path termination probabilistic. Suppose a candidate path has contribution C and the renderer keeps it with probability q . On a surviving path, use C / q ; on a terminated path, use zero. The expected result is

q C q + ( 1 − q ) 0 = C .

The estimate therefore remains unbiased even though some paths are skipped. A deterministic rule such as “discard every contribution below a threshold” would systematically remove dim light and bias the answer. In the lecture’s example, more aggressive termination shortens rendering time while making shadows noisier; the useful setting depends on how much remaining throughput the scene carries and how much variance the renderer can tolerate. CMU-18 (Vision, XR, and Playable Worlds, Part 1, Ch. 5)

Bidirectional path construction

Camera-only path tracing launches a path from the camera and samples successive surface directions. This is effective when important paths are easy to find from the camera side. It struggles with difficult light connections, such as a small opening that admits illumination into a room or a caustic where light focuses through specular events. Bidirectional path tracing also launches subpaths from emitters and connects light-side and camera-side vertices. It can discover a connection even when neither a camera-only nor a light-only random walk would likely create the entire path.

The estimator must account for the probability of generating a path by every strategy that could have produced it. Multiple importance weights compare those path densities so the same contribution is not overcounted. Path length is itself a sampling decision: short paths often represent direct illumination; longer ones capture more indirect transport but may have diminishing contribution and higher cost. Russian roulette can end long low-throughput paths without a fixed bounce cutoff. CMU-19 (Vision, XR, and Playable Worlds, Part 1, Ch. 5)

Metropolis-Hastings sampling creates a Markov chain whose states are light paths. From current path x , propose new path y with transition density T ( y | x ) and accept it with probability

α ( x , y ) = min ( 1 , π ( y ) T ( x | y ) π ( x ) T ( y | x ) ) ,

where π is the target path-contribution distribution. The ratio corrects for asymmetric proposal probabilities. Rejected proposals keep the current path, maintaining the desired stationary distribution. Photon mapping and radiosity

Photon mapping traces particles of light from sources and stores where they hit surfaces. At a shading point, nearby photon contributions estimate incoming illumination. The estimate is a density estimate: using too large a neighborhood blurs detail, while too small a neighborhood has high variance. Photon maps can represent caustics that camera-side random paths rarely find. They are often biased at finite neighborhood radius, with bias decreasing as the estimate is refined.

Radiosity divides diffuse surfaces into patches and solves for energy exchange among them. A form factor describes what fraction of energy leaving one patch reaches another. The discrete system couples all patches; dense systems can be expensive, while spatial hierarchy or iterative methods reduce work. Radiosity assumes diffuse response and typically solves a global energy balance, whereas path tracing samples individual transport paths. These approaches target related light transport from different numerical angles. CMU-19 (Vision, XR, and Playable Worlds, Part 1, Ch. 5)

Recursive light paths: shadows, mirrors, glass, and sampled effects

A shadow query asks whether any blocker lies between a surface point and a light. This is a binary visibility test, so a shadow ray can stop at its first valid hit instead of finding the closest blocker. The local illumination may still contain an ambient term, but ambient light in this basic model is a constant hack that prevents completely black unlit regions; it is not a simulation of bounced light. A point light yields hard shadow boundaries. An area light is a continuum of positions, each with a different visibility result; sampling M positions and averaging estimates the lit fraction. Fully blocked samples form the umbra, fully visible samples the lit region, and a mixture forms the penumbra. If a shadow ray starts exactly at the hit, floating-point error may report the surface itself as a blocker, creating self-shadow speckles. Start at p + ϵ n or require a candidate parameter t > ϵ , with ϵ chosen relative to scene scale. MITG-11 (Vision, XR, and Playable Worlds, Part 1, Ch. 5) (00:07:40–00:20:20)

For an ideal mirror, reflect the incoming direction across the surface normal. Given a unit normal n and incident unit direction d pointing toward the surface, the outgoing direction is

r = d − 2 ( d ⋅ n ) n .

The formula subtracts twice the normal projection, flipping its sign while leaving the tangential component unchanged. A secondary ray from the hit point travels along r ; its returned radiance contributes to the original hit color. This is recursive: the reflected ray may strike another mirror and launch another ray. Real surfaces are imperfect. Fresnel reflection describes the increase in reflectance at grazing angles, where a surface looks more mirror-like. Schlick’s inexpensive approximation is F ( θ ) = F 0 + ( 1 − F 0 ) ( 1 − cos ⁡ θ ) 5 , where F 0 is the normal-incidence reflectance. It retains the angle trend with only a dot product and a fifth power. MITG-11 (Vision, XR, and Playable Worlds, Part 1, Ch. 5) (00:20:20–00:30:20)

Refraction changes direction across an interface because light travels at different speeds in different materials. Snell’s law is n i sin ⁡ θ i = n t sin ⁡ θ t , where n i , n t are refractive indices and angles are measured relative to the normal. To compute the new vector without inverse trigonometric functions, take unit incident direction i pointing toward the viewer in the lecture’s convention and a suitably oriented unit normal n . Define η = n i / n t and c = i ⋅ n . The transmitted direction can be written

t = − η i + ( η c − 1 − η 2 ( 1 − c 2 ) ) n .

The tangential component is scaled according to Snell’s law; the normal component is chosen to keep ‖ t ‖ = 1 and point into the second medium. The sign convention for i and n must be consistent—many implementations use an incident vector pointing toward the surface and flip the normal when exiting. As a worked case, for air to glass with η = 1 / 1.5 and incidence angle 30 ∘ , Snell gives sin ⁡ θ t = ( 1 / 1.5 ) ⋅ 0.5 = 1 / 3 , so θ t ≈ 19.47 ∘ : the ray bends toward the normal. From glass to air at a sufficiently grazing angle, the square-root radicand becomes negative; there is no real transmitted direction, and the event is total internal reflection. Fiber optics use repeated internal reflections to guide light. MITG-11 (Vision, XR, and Playable Worlds, Part 1, Ch. 5) (00:30:20–00:54:55)

Reflection and refraction are only some of the possible branches. Rainbows require wavelength-dependent refraction plus internal reflection in water droplets; tracing only one RGB ray cannot reproduce the full dispersion without modeling several wavelengths. Caustics—bright focused patterns from curved reflective or refractive surfaces—are hard for camera-launched paths because the important light paths occupy a small set of directions. Sampling adds realistic variation and computational cost. Perturbing a perfect mirror ray can approximate a rough or brushed surface, but a single independent random direction per pixel appears as white noise. Repeating samples and averaging reduces variance. Choosing random points on an area light estimates soft shadows; choosing positions in a lens aperture gives depth of field; sampling scene time gives motion blur; multiple samples within a pixel reduce jagged edges. If each branch creates b new rays to depth k , a full ray tree may contain 1 + b + b 2 + ⋯ + b k rays, so costs grow rapidly. Renderers cap recursion depth or terminate branches whose remaining energy is negligible. Direct lighting accounts for light that reaches a surface from explicit sources. It misses the red tint that a red wall contributes to a nearby floor, soft indirect fill, and many caustics. Backward ray tracing starts at the eye because rays that reach the eye are the ones worth computing, but physical light travels from source to eye. Reversing path direction is valid for ordinary reciprocal reflection; it does not mean the algorithm has simulated every light path. Rotate around an arbitrary line by aligning it to a known axis

A 3D rotation needs an axis, which is a line specified by a point P = ( x p , y p , z p ) and direction V = ( x v , y v , z v ) . The coordinate-axis rotation matrices from P3-03 are easy to construct, so transform the arbitrary axis until it coincides with the z axis, rotate by the desired angle α , then undo those alignment transforms. For row vectors, the sequence is

M = T ( − P ) R y ( − θ ) R x ( ϕ ) R z ( α ) R x ( − ϕ ) R y ( θ ) T ( P ) .

A row point is multiplied on the right: Q ′ = Q M . The rightmost operation in this written row-vector product happens last. Reading from the left, the point is first translated so the axis passes through the origin. Then a y rotation removes the direction’s x component, placing the axis in the yz plane. An x rotation removes its y component, aligning it with +z. After R z ( α ) , reverse the x and y alignments and translate the axis back. Seven 4×4 matrices can be composed into one matrix that performs the rotation. This is an example of using simple transformations as building blocks for a less obvious one. (P3-04)

For direction V , a robust choice of alignment angles is

θ = atan 2 ( x v , z v ) , ϕ = atan 2 ( y v , x v 2 + z v 2 ) .

The lecture derives these angles from right triangles and corrects its diagram/sign setup while teaching. atan2 preserves quadrant information more reliably than a one-argument inverse tangent. If the axis is already parallel to y, the first angle is unnecessary; if the direction is zero, it does not define an axis at all. These are useful implementation edge cases beyond the chalkboard walkthrough. (P3-04)

Example: let the axis pass through P = ( 1 , 2 , 0 ) in direction V = ( 0 , 1 , 1 ) , and rotate Q = ( 2 , 2 , 0 ) by 90 ∘ . Here θ = 0 and ϕ = 45 ∘ . Translate Q relative to the axis to get ( 1 , 0 , 0 ) . The x alignment leaves that point unchanged; the z-axis quarter-turn changes it to ( 0 , 1 , 0 ) . Undoing the x alignment gives ( 0 , 1 2 , − 1 2 ) . Translating back yields

Q ′ = ( 1 , 2 + 1 2 , − 1 2 ) ≈ ( 1 , 2.707 , − 0.707 ) .

A direct right-hand check gives the same result: the unit axis is ( 0 , 1 / 2 , 1 / 2 ) , and rotating the offset ( 1 , 0 , 0 ) by 90 ∘ adds its cross product ( 0 , 1 / 2 , − 1 / 2 ) . This independently checks the sequence and sign convention. (P3-04; numeric example derived from the source construction.)

Color and the simplified local-lighting model

A physical surface does not simply “have” a color independent of illumination. Light has a spectrum; a material absorbs and reflects portions of it; the eye integrates the resulting spectrum. The course reduces this continuous process to three RGB channels because it is practical for graphics hardware. In normalized RGB, each channel ranges from 0 to 1: red is ( 1 , 0 , 0 ) , green ( 0 , 1 , 0 ) , blue ( 0 , 0 , 1 ) , white ( 1 , 1 , 1 ) , black ( 0 , 0 , 0 ) . Equal channel values lie along the gray diagonal. An 8-bit-per-channel buffer stores 256 3 = 2 24 RGB combinations. RGB is additive light: red plus green light can appear yellow. Pigments and printing are better described with subtractive CMY/CMYK, so mixing crayon colors is not the same operation as adding display light. HLS/HSL and HSV-like models rearrange color coordinates into hue and intensity/saturation controls that are easier for a person to choose. HSL lightness and HSV value are not the same coordinate, despite the lecture’s shorthand. (P3-08)

The full light-transport problem contains repeated bounces: a wall illuminates a table, the table illuminates another wall, and those contributions continue. Physically based global illumination can approximate this energy exchange, but the introductory fixed-function model makes a deliberately simple local approximation. It treats background illumination as a constant ambient term, a point light as a source with a position and RGB color, and a material as a set of per-channel response coefficients. This is a teaching model, not an accurate description of metals, glass, or all real surfaces. (P3-08)

For diffuse reflection, let N be a unit surface normal and L a unit direction from the surface toward the light. Lambert’s cosine law gives the orientation factor N ⋅ L = cos ⁡ θ . When the light grazes the surface, the cosine approaches zero; when it faces the normal, it is one. The useful rendering form clamps the back-facing case: D = max ( 0 , N ⋅ L ) . If N = ( 0 , 1 , 0 ) and L = ( 0.6 , 0.8 , 0 ) , then D = 0.8 . A red diffuse material with coefficient k d = 0.6 under unit red light contributes 1 × 0.6 × 0.8 = 0.48 red before ambient and specular terms. A unit normal matters: otherwise the dot product also scales by vector lengths and ceases to be the cosine. Polygon normals can be found from the cross product of two edges; reverse edge order reverses the normal. (P3-08)

Ambient light is a shortcut for many indirect bounces. It brightens surfaces even when the explicit point light does not reach them, but because it is constant it cannot create realistic spatially varying indirect illumination or cast shadows. The lecture’s per-channel local model can be written in an explanatory normalized form:

C o u t = k a ⊙ C a m b i e n t + k d ⊙ C l i g h t max ( 0 , N ⋅ L ) + k s ⊙ C l i g h t max ( 0 , N ⋅ H ) m .

Here each RGB triple is evaluated channel by channel, ⊙ means component-wise multiplication, k a , k d , k s are material ambient/diffuse/specular responses, and C l i g h t colors the direct light. The first term is constant ambient, the second is Lambertian diffuse, and the third makes a view-dependent highlight. Clamp the final channels to the supported range. Exact coefficient names and multiplication order vary across legacy APIs; the equation captures the lecture’s simplified model. (P3-08)

For a shiny highlight, classical Phong compares the view direction V with the ideal reflected direction R and raises their cosine to a gloss exponent. The power makes the peak narrow: for 0 ≤ c ≤ 1 , c 100 drops far more quickly away from c = 1 than c 5 . Blinn’s practical variant uses the halfway direction H = normalize ( L + V ) and the factor max ( 0 , N ⋅ H ) m . The halfway vector is easy to compute and yields the Blinn–Phong model used in many introductory renderers. A larger exponent m narrows the highlight and makes the object look glossier; it does not mean the material is physically more reflective at every angle. The highlight is tinted by the light and scaled by a specular material coefficient. (P3-08)

This model explains why a plastic toy can look convincing but a metal or dielectric is harder: it compresses complex microfacet behavior into a few tunable values. The instructor maps those values to creative controls. A texture changes surface color; bump mapping perturbs the normal used by the lighting calculation, changing apparent small-scale relief without changing the silhouette; moving the light changes L and highlight position; changing m alters gloss. The orange example makes the normal role intuitive: perturb normals over a smooth orange-colored sphere and the light response starts to resemble textured peel. (P3-08)

Shadow representations: geometry, volumes, and depth maps

A shadow is a visibility question from the light. A surface point is directly lit if the segment from that point toward a light source is unobstructed. Three representation choices in the 2009 lectures answer that question in different spaces: project a fake shadow polygon onto a floor, construct a 3D shadow volume and count crossings, or render a depth map from the light and compare depths. (P3-18, P3-19)

For a point light L , object point P , and receiver plane through Q with normal N , the ray from the light through the object is X ( t ) = L + t ( P − L ) . A projected shadow point lies on the plane, so

N ⋅ ( X ( t ) − Q ) = 0 , t = N ⋅ ( Q − L ) N ⋅ ( P − L ) .

Then X = L + t ( P − L ) . If the denominator is zero, the line is parallel to the plane (or lies wholly in it), so there is no unique projected point. For a simple numeric check, let the floor be z = 0 , light L = ( 0 , 0 , 4 ) , and object point P = ( 1 , 0 , 2 ) . Along the ray the z coordinate is 4 + t ( 2 − 4 ) = 4 − 2 t . Setting it to zero gives t = 2 , so the projected point is ( 2 , 0 , 0 ) , farther from the light’s vertical axis than the object because the light ray diverges. The projected polygon can be drawn dark and offset slightly from the floor to avoid z-fighting. It is efficient and useful for contact shadows, but it cannot cast a shadow over a curved body or arbitrary receiver because its construction assumes one plane. A fuzzy texture or an ellipse under a character is a deliberate approximation, not a visibility solution. (P3-18)

A shadow volume is the region behind a caster as seen from a light. For a polygonal caster, extrude its silhouette away from the light and close the resulting shape. To test a camera ray, count each entry into the volume as +1 and each exit as −1. If the ray reaches the visible surface with count zero, it is outside all volumes and lit; a positive count means it is inside at least one shadow. The crossing sign can be determined from the ray direction’s dot product with the volume face normal. This supports arbitrary receiving geometry, but every caster polygon may create one or more extra faces. Overlapping volumes lead to many crossings, so the stencil/counting method may be manageable while volume construction, storage and fill work become expensive. (P3-18)

An area light has extent. A point in the umbra is blocked from every part of the source; a point in the penumbra sees some of it. A single point-light projection cannot express that gradual transition. Repeated or layered shadow volumes can approximate partial coverage, but at a high geometry cost. This explains why shadows are a balance between accurate visibility and practical sampling or storage. (P3-18)

Shadow mapping stores the closest depth visible from a light in a depth texture. During the eye-view pass, transform each visible point into the light’s clip space, divide by its homogeneous w , map x/y into the light’s texture coordinates and compare its light-space depth with the stored depth at that location. If the point is farther than the stored blocker, it is in shadow. If it is nearer or equal (within a bias), the light is visible. For example, if the map stores depth 0.42 and the receiver’s projected depth is 0.67 , the receiver lies behind the surface seen by the light and is shadowed. With depth increasing away from the light, “farther” is a larger value; exact comparisons depend on the depth convention. A small depth bias avoids self-shadowing caused by quantization and interpolation, but too much bias detaches shadows from casters. (P3-18, P3-19)

The lecture’s 2009 derivation walks between eye and light image spaces with inverse view/projection matrices. It emphasizes retaining homogeneous w : once a clip point is divided by w , that scale is lost and cannot simply be inverted to recover the same homogeneous point. Reconstruct in homogeneous coordinates, transform back through inverse projection and view, then project into the other camera’s space. This makes the coordinate relationship explicit; a typical modern shadow-map shader instead computes light-space coordinates directly from the world-space position before the eye-space projection. (P3-19)

Shadow maps have two coupled resolution limits. A narrow light frustum clips casters or receivers outside its stored view; a very wide frustum spreads a fixed number of texels across more world area, so a single texel covers a larger region and shadows look blocky. Higher resolution helps but costs memory and rendering work. Several lights generally need several maps. Point lights may need multiple views around the source, while a directional light can use an orthographic view; these choices constrain coverage. A point mapped between texel centers also creates aliasing. Percentage-closer filtering (PCF) compares a neighborhood of depth samples and averages the visibility results. A 4×4 filter averages sixteen binary comparisons; if four samples are lit, the fractional result is 4/16. This softens jagged boundaries and can suggest an area light, but ordinary PCF blurs the visibility edge rather than physically integrating all directions from a source. (P3-19)

OpenGL era note. The 2009 lecturer speaks of an OpenGL function for shadow maps and discusses the fixed-function transform pipeline. That is historical context. In modern programmable OpenGL, a common route is to render a depth texture from the light, pass light-space coordinates to a shader, and use a GLSL shadow sampler with depth comparison; the official OpenGL Shading Language 4.60 specification defines these shadow sampler comparisons. Thus the geometric algorithm remains relevant while the API path has changed. (P3-19)

A programmable, differentiable rendering system

Connect to: Monte Carlo rendering; optimization; inverse rendering; physical light transport; CPU/GPU execution.

Mitsuba 2 is a renderer-system paper, not a new surface representation. Its central design problem is how to add different execution modes—scalar, vectorized, GPU, spectral, polarized, and differentiable—without maintaining separate copies of every sampling and shading algorithm. The authors build generic renderer code on Enoki, a C++ array and program-transformation library. A developer writes operations on array-like values; compile-time types choose how those values are represented and which transformations apply. The same high-level algorithm can then be retargeted to scalar values, CPU packets, or GPU arrays.

On the GPU, ordinary eager execution would launch a kernel for each small arithmetic operation. A path tracer performs many simple operations between irregular scene queries, so launch and memory-transfer overhead can dominate. Enoki instead records operations symbolically in a single-static-assignment graph. Reading or otherwise observing the array triggers just-in-time (JIT) compilation of the accumulated graph into a GPU kernel. The first rendering may pay the compilation cost; identical kernels can be cached for later iterations. The approach fuses small operations while allowing a large renderer to build its graph at runtime, without describing the entire codebase in advance.

A renderer’s control flow is irregular. Different rays hit different materials and take different branches. Enoki uses masks to mark which lanes of a vector are active. A vectorized branch computes only for lanes that satisfy its condition. To avoid synchronizing the GPU for every step, code should keep many operations vertical (per-lane) and use horizontal reductions such as all(mask) sparingly. Dynamic method dispatch is more difficult because a vector of rays may point to many material objects. Enoki groups lanes by unique object pointer, calls that material’s method for its active subset, then scatters results back. Gather and scatter also need special derivative rules: in reverse mode, a gather’s gradient becomes a scatter-add, while a scatter’s gradient becomes a gather.

Differentiable rendering creates a second systems problem: reverse-mode automatic differentiation (Light Transport and Image Synthesis, Part 1, Reference notes: Automatic differentiation and backpropagation) (AD) must retain intermediate values until the output loss is known. A wavefront renderer can store large intersection records and sampled values; at image-scale sample counts, the memory cost can reach multiple gigabytes. Enoki simplifies its computation graph at JIT boundaries. It collapses interior nodes by multiplying derivative weights along paths, trading extra arithmetic for fewer stored nodes. A greedy rule collapses low-cost nodes first. This makes the method a hybrid of forward and reverse differentiation rather than a strict traversal of the original graph. The authors’ Cornell Box measurement shows JIT alone lowers runtime substantially; graph simplification further reduces memory from 2.43 GiB to 1.36 GiB in the reported setting, with a small timing change. This is a benchmark of their 2019 implementation, not a current performance promise.

The system can also change the meaning of its radiance values without duplicating the renderer. For polarization, it represents light with Stokes vectors and material transformations with Mueller matrices. Each Mueller matrix is tied to incident and outgoing reference frames, so those frames must be rotated consistently when light scatters. The renderer uses Mueller-matrix values throughout to keep its interfaces symmetric, even though this performs some unnecessary arithmetic. The paper demonstrates a dielectric between crossed linear polarizers: the glass changes the polarization state so some light passes the second filter. It also enables spectrum-aware transport rather than treating every ray as three fixed RGB numbers; the paper’s renderer samples four wavelengths per ray across 360–830 nm by default.

Differentiable caustics and media

A differentiable renderer can optimize a scene parameter to make a rendered image match a target. For caustics, one example changes a refractive height field so focused light forms a desired image. Another changes a spatially varying refractive index. In a gradient-index medium, rays curve because the index varies with position. The paper writes the ray equation as

d 2 x d t 2 = n ( x ) ∇ n ( x ) .

The implementation integrates this equation with a Leapfrog step while tracing light. Gradient descent then updates the height field or index grid from the image error. These demonstrations show that a general renderer can support inverse design with a custom differentiable simulation; the authors explicitly say their height-field results do not match purpose-built methods in contrast and precision.

Sampling the distance to the next event normally uses a parameter-dependent probability distribution. Directly differentiating through that sampling transform can fail when it becomes discontinuous—for example, when the sampled event leaves the volume bounds. The paper’s solution is to differentiate the integral before changing variables into primary-sample space, then detach the sampling transform and its probability from the AD graph. This keeps the derivative on the integrand while avoiding an invalid derivative through a discontinuous sampling map.

The authors initially explored delta tracking, which supports unbiased event sampling but can take a variable number of steps and create incoherent GPU execution. They use regular ray marching instead. This gives more coherent GPU work but introduces a small rendering bias. Their smoke-density experiment is synthetic: one view is ambiguous and creates artifacts; matching nine views constrains the density better. Their translucent-slab experiment is also simplified: extinction is homogeneous and monochromatic, while voxel albedo varies. Differentiable rendering improves on a naive color-to-albedo initialization because multiple scattering couples neighboring voxel values.

Coherent bundles for Markov-chain rendering

Mitsuba 2’s vectorization also supports a path-sampling method designed for coherence. A conventional packet tracer may launch many rays together, but their paths quickly diverge into different branches and memory locations. Markov-chain Monte Carlo light transport explores nearby points in primary sample space, the random numbers that define a path. The paper’s coherent pseudo-marginal Metropolis light transport (CPMMLT) smooths the target function by convolving it with a Gaussian in that space:

π ( u ) = ∫ U G ( δ ) f ( u − δ ) d δ .

It estimates this smoothed target with a bundle of nearby paths, evaluating them together in vector lanes. The Gaussian width trades exploration against coherence: nearby samples are more likely to take similar path branches, so the CPU’s vector units and caches do more useful work. The method uses pseudo-marginal MCMC: an unbiased estimate of the smoothed target can be used while preserving the chain’s target distribution. The paper then weights the bundle’s contributions to reconstruct an unbiased estimate of the original, unblurred image. In its tests, CPMMLT evaluates about two to six times more rays per second than the PSSMLT baseline, depending on the scene. Those tests ran on 28-core Intel Xeon Gold 6132 machines; the result is specific to that hardware and comparison.

Practical limits. Reverse-mode AD stores state and may run out of memory as resolution, samples, and path depth grow. Rendering losses have poor local minima, so parameter initialization matters. Ray marching trades a small bias for GPU coherence. The 2019 paper’s software and interfaces are historical: describe the architecture and evidence from the paper, but do not treat its Enoki/Mitsuba 2 API as the current Mitsuba 3 or Dr.Jit API. Its examples demonstrate system flexibility; they do not establish that every inverse-rendering problem is well posed or that one view determines a unique scene.
